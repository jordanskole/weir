# Open questions

Things raised in the design conversation that were not resolved — as opposed to items in [getting-started.md](getting-started.md#deferred-on-purpose-dont-build-yet), which are resolved in design but deliberately postponed in implementation order.

- **Sleep / wait.** Is a delay a property of an edge (e.g. a `DelayedOrder` that resolves later), a special node type, or a runtime concern outside the node model entirely? Ties into the "nothing polls, only origin nodes introduce nondeterminism" rule — a wait is a kind of origin.

- **"No loop construct" is a real gap in the runtime, not just an unimplemented nicety — surfaced by an outside reader (a friend's ChatGPT session, 2026-09-24, sketching a SOC-triage app built *on* weir) testing the claim against actual code rather than taking `design-history.md`'s word for it.** `design-history.md` ("Weir has no loop construct, and needed none") and `design.md` §3 hold that a repeated node name in a `.topology` file (`birthday.then.birthday`) is "a legitimate distinct application, not a cycle," and that recurrence should be modeled as fresh forward execution rather than control-flow looping. That's the stated design intent, but the runtime doesn't implement it: `runtime.ts:162` maintains `const fired = new Set<string>()` keyed by bare node name, and `runtime.ts:166` (`if (fired.has(nodeName)) return false`) means a node that appears twice in a topology fires **once**, full stop — verified directly against the code, not taken on the outside reader's word. So today, `birthday.then.birthday.then.birthday` doesn't run three times; it runs once, silently. This matters for exactly the kind of workload the "ActiveCampaign for agents"/SOC-triage direction needs — "keep gathering evidence and reassessing until the investigation is complete" is a natural recurring `assess → request more evidence → assess` shape, and it's unbuildable today except by hand-unrolling distinct node names per iteration (`assess1`, `collect1`, `assess2`, ...), which the same outside reader correctly called "obviously not ideal."
  - **A concrete, not-yet-designed candidate answer, from the same conversation:** stop keying "has this fired" by bare `nodeName`, and key it by `(nodeName, correlationId, consumed input edge-instance ids)` instead. Under that identity, the same node can fire again validly whenever it's now facing genuinely new input edge instances it hasn't consumed before — turning "loop until done" into an emergent fixpoint ("keep firing every node whose particular input edge instances haven't previously been consumed by that node, until nothing new is produced") rather than a control-flow primitive, consistent with the log-as-source-of-truth model (§5) rather than bolted onto it. A terminal condition falls out for free too: a topology reaches quiescence when no node has unconsumed-and-satisfying input left, or an explicit terminal edge (`InvestigationComplete`-shaped) appears.
  - **Substantially resolved in design 2026-09-24 — see design-history.md, "Iteration: it's a Petri net, and the loop was never the missing piece."** Three corrections to this entry as written. First, the diagnosis above blames `runtime.ts`'s `fired: Set<string>`, but that is the *second* problem: `InMemoryLog` keeps one instance per `(edgeName, correlationId)` and `append` overwrites, so even with firing identity fixed there would be no distinct instances to key on. Latest-wins is the banned ambient mutable cell, sitting in the runtime rather than in a node. Second, the candidate answer below presumes edge instances that are individually identified and retained; they are neither today. Third, the framing "no loop construct" conflated a construct with a capability — `while` needs ambient state, recursion does not, and a node feeding itself with a `oneOf` base case is already the recursive form. Settled: fire once per unconsumed instance (a Petri net's transition rule), consumption tracked per node, `allOf` joined by shared lineage rather than a declared key, iteration bounded by the host rather than the language. Vocabulary settled too — a **token** is one edge instance in flight, a **run** is one traversal (`correlationId`), and lineage is `causationId`, currently a `null` placeholder. Now decomposed into four specs in dependency order: (1) the log becomes a log, (2) causation is real, (3) `allOf` joins by lineage, (4) composite nodes / "enroll in workflow".
  - **Resolved in code too, 2026-09-24 — piece (1) is implemented** ([spec](superpowers/specs/2026-09-24-instance-retention-and-iteration.md), status: implemented). `InMemoryLog` retains every instance instead of overwriting; `runtime.ts`'s driver is a real pulse loop that snapshots readiness once per pulse; a `single`-input node fires once per unconsumed instance reaching it along a declared arc in `wiring.feeds`, not on its input edge's latest instance; and `envelope.step` is the pulse number rather than a hardcoded `0`. The canonical example still fires each node exactly once, and a genuine cycle — a node wired back to itself whose `Fn` emits a continue-branch until a `oneOf` base case — now runs to quiescence instead of firing once, bounded by the host's `budget` (firings) and a `maxPulses` backstop (pulses) rather than by the language. What this entry called remaining, piece (3) — `allOf` joining by lineage — is now also resolved; see below. One limitation surfaced building piece (1), not anticipated when it was scoped: a node that is both an origin and a `feeds` target can never iterate — the runtime checks `origins.has(nodeName)` first and always routes an origin to its once-only branch, so it is never offered instance candidates regardless of how the topology wires it. This matches prior (pre-piece-(1)) behaviour and is not a regression, but it means a fixture exercising a self-feeding node needs a separate seed node feeding it, not the origin doubling as the looped node itself.
  - **Relationship to work already in flight:** `docs/superpowers/specs/2026-09-23-invocation-records-and-replay.md` (actively being implemented as of this week — `Envelope`, `Trace`, version pinning) is adjacent infrastructure — it's the machinery that would need to exist for a real "consumed input edge-instance ids" identity to be recorded and checked — but its own "Explicitly out of scope" section names `causationId` as staying a placeholder `null` and doesn't touch node-firing identity at all. So this isn't redundant with that spec, and it isn't blocked by it either exactly — but it's the natural next layer on top of it, worth flagging to whoever picks up invocation-records next rather than designing in isolation.
  - **Resolved in code too, 2026-09-24 — piece (2), causation, is also implemented** ([spec](superpowers/specs/2026-09-24-causation-is-real.md), status: implemented). The vocabulary note above ("lineage is `causationId`, currently a `null` placeholder") is stale: `Envelope.causationId: string | null` became `causationIds: string[]` — the runtime supplies it for a `single`-input node, the membrane derives it for an `allOf` node during its own resolution (one entry per declared edge), and a rejected attempt records it too, since the envelope is now built before the input is asserted. `replayInvocation` re-feeds it for a `single`-input node; the membrane overrides it for `allOf`. `ancestorsOf` (`src/lineage.ts`) walks it transitively, deduplicated by instance id. What the note above (10) called still-open is now resolved too: piece (3), `allOf` joining *by* that lineage, is implemented — see the next bullet.
  - **Resolved in code too, 2026-09-25 — piece (3), `allOf` joining by lineage, is also implemented** ([spec](superpowers/specs/2026-09-25-allof-joins-by-lineage.md), status: implemented). An `allOf` node now fires once per **lineage group** rather than once per run: the runtime gathers each declared edge's unconsumed candidates, groups them by nearest common ancestor (the highest-`seq` member of the intersection of each candidate's self-and-ancestor set, `joinRows` in `src/lineage.ts`), and zips a complete group's candidates positionally by `seq` — one firing per complete row, ragged leftovers left unconsumed. A candidate is held out of a group when it has a strictly nearer ancestor that is currently incomplete *and* a peer instance of that ancestor's node holds an edge it is missing (spec §2's correction, added by the branch's final review: without the hold, two arms stalled in opposite directions fall through to the run origin and fire cross-item rows). `firedAllOf` is deleted; an `allOf` firing consumes its row the same way a `single` firing consumes its one instance. When no candidate on any declared edge carries an envelope there is no lineage to join on and resolution falls back to latest-wins, same as before — a tier no production caller reaches, since `invokeWithInput` passes its bag straight to the membrane and never calls `joinRows`; a host staging envelope-less instances into a real `Log` is the only route in, which today means tests. The membrane no longer resolves `allOf` inputs itself; it asserts the bag the runtime already chose, and an incomplete bag through the direct path now surfaces as `Failed<In>` rather than the readiness `undefined` it used to return. So a fan-out/fan-in diamond iterates now, not just single-input chains — once per **lineage group**, which is not the same thing as once per element of a `many` collection (see "There is no fan-out primitive" below). Two limitations this uncovers, neither anticipated by the spec that built it, are recorded as their own entries below ("A fan-in fed by two independent origin nodes never fires" and "There is no fan-out primitive").
  - Piece (4), composite nodes, is the one genuinely remaining piece of this line of work — not started.

- **Positional identity in a topology: `birthday.then.birthday.then.birthday` should run three times.** Split out of the "no loop construct" entry above, which conflated two different features. This one is not data-driven iteration — it's that two *mentions* of one node in a `.topology` are two distinct instances, and `Wiring`'s flat parent→children adjacency map can't represent the difference between "run it three times" and "run it forever" once nested YAML is collapsed into it. `examples/person-birthday/README.md` already flags the same gap from the other side ("Instance identity is `node-name#n`"), and `netlist.ts`'s `serializeNetlist` already emits `${nodeName}#1` ids that nothing yet makes meaningful. More todo than open question — the answer is probably just "give `Wiring` real positional instance identity and key firing on that" — but it needs doing deliberately rather than falling out of the iteration work, since the two have different termination stories: this one terminates by construction, iteration terminates by quiescence. **Unblocked in design 2026-09-25** (design-history.md, "A join is a topology boundary"): this entry's rule — a repeated bare name means another instance — used to contradict the diamond, which needs a repeated name to mean *the same* node. Once joins live at topology boundaries nothing needs a name to mean "the same node again", so the contradiction is gone and this becomes a build task rather than a design question.

- **The membrane bounds behaviour, not control — `nodeDef.fn` is still directly reachable.** `membrane(nodeDef, ...args)` no longer hands out a detached invoker (it used to return a callable the caller invoked later, so "invocation only happens through the membrane" was enforced by every call site happening to comply, not by the structure). That closed one gap and left the larger one: `fn` is a public field on `NodeDef`, and `implementation.ts`, `fuzz.ts` and `accept.ts` all pass whole `NodeDef`s around, so nothing prevents calling it directly and skipping the assert, the envelope and the `Failed<In>` conversion. The membrane's guarantee is therefore "if you call me, these things happen" rather than "these things happen". Making it structural means `fn` not being readable from the type consumers hold — resolution constructs it, nothing else can reach it — which touches how implementations are resolved and handed to the runtime, and how the fuzz and acceptance paths invoke candidates. Not attempted; recorded because the gap between what the name claims and what the code enforces is exactly the kind of thing that stops being obvious once the shape looks right.

- **`Failed<In>.input` is typed as validated data it never was.** Surfaced auditing casts while reordering the membrane's envelope construction (2026-09-24), pre-existing and left unfixed. When an input is rejected at the boundary, the membrane returns `{ input: payload as InputPayload<In>, reason }` — but that payload is precisely the value that *failed* validation, cast to the type meaning "a valid payload of this shape". The consumer that makes this more than cosmetic is the one `design.md` §3 names: *"Retry is a node consuming `Failed<In>`"*, carrying the original payload so a retry node has something to re-emit. A retry node reading `failed.input` is handed data the type promises is valid and the runtime knows is not, and re-emitting it puts it back on the wire under that promise. Nothing dereferences it today, which is why this is recorded rather than fixed. Candidate answers: type it `unknown` and make a retry node re-assert explicitly (honest, and pushes the check to where the value re-enters), or give `Failed<In>` two shapes distinguishing "rejected before validation" from "threw during execution" — the second already carries a genuinely validated input, which is why one type covering both is what forces the lie.

- **A fan-in fed by two independent origin nodes never fires.** Surfaced building piece (3), `allOf` joining by lineage ([spec](superpowers/specs/2026-09-25-allof-joins-by-lineage.md), status: implemented), shipped 2026-09-25. Grouping an `allOf` node's candidates by nearest common ancestor requires the candidates to *have* a common ancestor. An origin instance's `causationIds` is always `[]` — nothing produced it, so it has nothing to descend from — which means two instances descending from two *different* origin nodes share no ancestor at all, not merely the wrong one. No lineage group ever forms for that combination, so the fan-in never fires. Nothing errors: the run simply reaches quiescence with those candidates sitting unconsumed, so the only symptom is a node that silently never runs. This matters because it is not a contrived edge case — `design.md` §5 explicitly blesses exactly this topology: *"a graph with several origin-shaped inputs doesn't trigger them independently at different times — there is exactly one call to the graph's outer membrane per external event, and every origin-shaped edge it declares needing resolves from that single payload at once."* One event, several origin-shaped edges, is a named-legitimate shape, and joining-by-lineage now breaks it silently for the `allOf` case. Candidate fix: represent the external event itself as a token, rather than leaving it unrepresented — a run-root instance that every origin node records as its own causation, so that any two origins triggered by the same event genuinely share an ancestor (the run root) to group on. **What the final review's hold rule adds here (2026-09-25).** The join now refuses to group a candidate at an ancestor while a strictly nearer ancestor of it is incomplete and a peer of that ancestor holds a missing edge (spec §2). That is the same question this entry asks, arriving from the other side: today two independent origins' descendants share *no* ancestor, so nothing groups them and the limitation is a consequence of disjoint lineage rather than of the hold; under the run-root fix they would share exactly one ancestor — the root — and the hold rule is then what stops the root becoming the pairing free-for-all the alert already was before it was fixed. So the fix does not need a second mechanism to keep multi-origin runs honest: one rule, ancestry, covers both "no common ancestor yet" and "a nearer group still forming". One caveat worth carrying into that work: two instances of the *same* origin node are peers and would be held apart, while two *different* origin nodes are not peers, which is precisely where the hold rule's peer approximation stops covering the case — see the spec's own statement of that limit. This is adjacent to the next entry below (whether direct invocation should just be a one-node topology) — both gaps trace back to the same root cause, an external trigger that isn't represented as a first-class thing in the log, just surfacing on two different paths (direct invocation vs. multi-origin fan-in).

- **Should a node ever be invoked directly, or is that just a one-node topology?** Hunch recorded 2026-09-25 while designing the lineage join (piece 3): `invokeWithInput` exists so a caller can run one node against a supplied bag, outside any graph — the path `fuzz.ts`, `accept.ts`, `replay.ts` and an agent tool call all take. It *used to* stage those values into a scratch `InMemoryLog` with **no envelope**, because nothing produced them; since piece (3) §5 the membrane takes the bag as an argument, so `invokeWithInput` passes it straight through and stages nothing at all. The alternative is that there is no such thing as direct invocation: you build a one-node topology in memory and run it, the supplied values arrive as origin payloads, and every instance gets a real envelope like any other.

  **What makes it more than tidiness: two separate bypasses exist only because staged instances have no envelope, and both would disappear.** The arc rule (`eligibleInstances`, 2026-09-24-instance-retention-and-iteration.md §4) treats an envelope-less instance as eligible by type alone, since it has no producer to check against the wiring. The lineage join (piece 3) needs a second tier for the same reason, since an instance with no lineage cannot be grouped by a nearest common ancestor. Neither bypass is wrong, but both are the same concession made twice. **Corrected 2026-09-25 (piece (3)'s final review):** this entry used to add that both are "load-bearing for the tool-calling path rather than merely for tests". That is true of the arc-rule bypass and *not* of the join's second tier — piece (3) §5 removed the staging that would have carried a tool call into `joinRows`, so the tool-calling path no longer reaches the tier at all. Collapse direct invocation into a one-node run and the concession is not needed anywhere; the second tier would simply have no callers left, which it very nearly has none of already.

  **Not resolved, and the plumbing is where it gets real.** `runNetlist` takes `originPayloads` keyed by *node* name, while an `allOf` node needs several *edges* satisfied at once — which is exactly `design.md` §5's "every origin-shaped edge it declares needing resolves from that single payload at once", so the model already allows it but the shape does not yet express it. Also unresolved: whether a pulse loop per tool call is acceptable overhead, and whether `accept.ts` running candidates through the full runtime changes what the acceptance gate is actually testing. Related: the `correlation_id` lifetime question above becomes concrete rather than hypothetical if a tool call mints a real envelope, because then it has to belong to some run.

- **There is no fan-out primitive: a `many` output is one token, not N.** Surfaced 2026-09-25 by the same outside reader whose SOC-triage sketch surfaced the loop gap above — this time with the repo checked out, writing real `.edge`/`.node`/`.topology` files rather than reasoning from the docs. Reading the README's claim that a fan-out/fan-in diamond now "iterates per item", they proposed the natural next shape: *one alert → `many` entities → N investigation diamonds → reassembly*. It doesn't run, and nothing says so. `runtime.ts`'s `logOutput` handles `single` and `many` identically — one `log.append` under the declared edge's name — because "a `many` result is already one collection payload, never N separate instances" (design-history.md, "`many` is a collection, keyed by index, not an array"). A downstream node therefore fires **once**, holding the whole collection, not once per element.

  **"Per item" means per lineage group, and the only ways to get N groups are a cycle or N declared origin nodes.** Neither is data-driven: a cycle iterates until it emits a branch nothing routes back to, and N origin nodes must be hand-written into the topology, which is the same hand-unrolling the "no loop construct" entry above already calls out as obviously not ideal. So the shape weir cannot express today is precisely the one every worked example keeps reaching for — take a collection *computed at runtime* and apply a subgraph to each element. The lineage join is what makes that shape safe once it exists (per-element diamonds can't cross-pair), which is why the gap only became visible after piece (3) shipped: the join arrived before anything that produces the groups it joins.

  **Candidate answers, none decided.** (a) A `many` output spreads into N instances at log time, keyed by the edge's declared `index` — this makes `many` the fan-out primitive its name already implies, and is the only option that makes the coordinate model's x axis (design-history.md, "Three axes and a clock") load-bearing at runtime rather than only in the netlist. (b) A separate spread/map construct in `.topology`, leaving `many` a single payload and keeping "one firing, one output instance" intact. (c) Composite nodes (the unbuilt piece (4)) absorb it — a subgraph applied per element, with the per-element scope falling out of the composite's own boundary. (a) is the smallest change and the most likely to be wrong in ways only a real program finds; (c) is the most principled and the furthest away. Worth resolving against a real topology rather than in the abstract, since the outside reader's SOC diamond is now concrete enough to serve as one.

  **Re-scoped 2026-09-25 — this is the per-item-lineage feature, not the streaming one** (design-history.md, "Fan-out and pipes are duals, not variants"). The entry above was written as though `many`-as-one-token were the defect blocking bulk data work. It isn't: a node whose input is the whole collection is the *vectorized* path, which is both the natural shape for an Arrow RecordBatch and the one whose instance-retention cost is per-batch rather than per-row. What is genuinely missing is the *scalar* path — one firing per element — and the case that needs it is per-item lineage (the SOC per-entity investigation, where each entity takes its own treatment and rejoins), never bulk transformation. A pipe, meanwhile, needs nothing new at all: N tokens on one arc is what piece (1) already built. Two consequences for whoever picks this up: the ergonomic default should be the batch with explosion opted into, not the reverse; and the keyed-versus-ordered collection question below has to be settled first, because "one element at a time" means different things over a keyed set and an ordered sequence.

- **A collection is keyed, and streamed data is ordered — `many LogEvent` will not elaborate.** Surfaced 2026-09-25 alongside the entry above, working out what an Arrow file or a log stream would look like in weir. `many` makes two commitments (design-history.md, "`many` is a collection, keyed by index, not an array"): every element carries an author-chosen unique `index`, enforced at elaboration by `elaborate.ts`'s `requireIndex`; and order is explicitly non-load-bearing, a property the coordinate model then builds on by defining **x** as the collection key rather than a position (design-history.md, "Three axes and a clock"). Both hold for domain entities and both fail for rows. A log line has no natural unique identifier — two identical lines in the same millisecond are distinct rows that would collapse to one key — and an Arrow RecordBatch is positional, 0..N-1, where the order is the information. So the first thing a log-ingestion topology needs is the first thing that won't elaborate. The earlier rejection of synthetic keys — *"a key nobody chose carries no more meaning than a position does"* — was correct for `Ingredient` and `Todo` and inverts for a table row, where position is exactly the meaning; the conclusion was sound and its scope was narrower than it read. Not decided: whether this is a second collection kind beside `many` (an ordered sequence, identity by position, consuming position 3 and position 7 as distinct even with identical payloads), or a flag on `many`, or a real edge of its own that carries rows alongside batch metadata the way a RecordBatch carries schema and a watermark. The third is what a pipe's unit probably wants to be. Note the knock-on: an ordered collection makes **x** positional for those edges, which amends a settled decision rather than adding beside it.

- **"System nodes": a category for nodes whose contract determines their implementation.** Raised 2026-09-25, after three separate documented gaps turned out to want the same missing thing. The defining property — and the reason this is a category rather than a wish list — is that if a node's contract admits exactly one sensible function, there is nothing for an agent to draft and nothing for the acceptance gate to accept: no `fn`, no implementation file keyed by contract hash, no declared examples, no `∀ p . …` property assertions, no §10 acceptance run at all. An author node is the opposite by construction: if two reasonable implementations exist, it isn't a system node. That test is what decides membership, not "the framework happens to ship it".

  **The motivating evidence: an identity-shaped node immediately after the origin is currently the only way to build a fan-in.** `examples/recipe`'s `gatherIngredients: Recipe → Recipe` looks like dead weight — a node that transforms nothing. It is load-bearing. A fan-in fires once per lineage group, grouped by nearest common *ancestor*, and an ancestor is an instance in the log; an origin node's output carries `causationIds: []`, because nothing produced it. So `gatherIngredients` exists to mint the one `Recipe` instance that `mix` and `preheatOven` both descend from, and without it `bake`'s join has nothing to group on. Confirmed by execution 2026-09-25 while reshaping `examples/todo-list`: an origin with an `allOf` output emitting `TodoList` and `NewTodo` together gives *both* instances `causationIds: []`, so `selfAndAncestors(TodoList) ∩ selfAndAncestors(Todo)` is empty and the run reached quiescence with 3 of 4 nodes fired and no error. Two edges from one origin firing share the *invocation*, which is not a token. This is the same root cause as the two entries above, sighted a third way — and it reframes the cost: not "a rare topology breaks" but "every fan-in in weir pays for it with a workaround node".

  **`spread` (`many X` → N × X).** The missing data-driven fan-out (see the entry above). The only one of the three that makes a currently-unbuildable program buildable rather than an existing one tidier, which is the argument for doing it first.

  **A run root.** One token per run that every origin node records as its own causation, so origins triggered by the same external event genuinely share an ancestor. Dissolves the identity-node workaround above, the multi-origin fan-in gap, and plausibly the direct-invocation question, all at once. Two known costs. First, a run-root *node* has nothing upstream of it, so it needs exactly the `Unit`-shaped input `design-history.md` ("The membrane") already floated and rejected — unless its input is the trigger payload itself, which is coherent but makes it structurally unlike every other node; the cheaper variant is to seed a run-root *instance* in the log and not call it a node at all, trading uniformity for a special case. Second, it moves the pairing problem rather than removing it: once everything shares the root, the root becomes the free-for-all the hold rule was added to prevent, and two *different* origin nodes aren't peers — precisely where that rule's peer approximation is documented to stop covering. `spread` is what would actually supply well-formed groups underneath it.

  **`noop` (`X` → `X`).** Names the workaround rather than removing it: `noop_Recipe` reads as structural where `gatherIngredients: Recipe → Recipe` reads as a bug, and it needs no implementation written or accepted. No polymorphism required — `elaborate.ts`'s `synthesizeFailedEdges` already generates one `Failed_X` edge per declared edge, and synthesizing `noop_X` nodes is the same linear scan, so the declaration language needs no generics. The risk worth deciding before building it: `noop` is an escape hatch for `assertWiringTypes`. When Rule A rejects an arc, inserting a noop will sometimes silence the error without fixing the model — the `any`-in-a-type-system problem — and that is much harder to withdraw later than to decline now.

  **Sequencing — superseded 2026-09-25, `noop` moves to first** (design-history.md, "A membrane closes on terminal markers"). The ranking below was argued on the wrong job for `noop`: legibility for the identity-origin workaround, which a run root would mostly delete. Marking branch completion is the real job — it is what makes a composite node's closure decidable, nothing else substitutes for it, and it is what the exit-side `allOf` needs to have a definite shape. The superseded argument, kept because its reasoning about the other two still holds: spread, then run root, then noop. Spread is the one nothing substitutes for. The run root then removes most of what `noop` would have been for — with a root, `mix` and `preheatOven` could both be origins and `bake` would still join — so building `noop` first risks making a workaround ergonomic immediately before making it unnecessary. Note also that `noop` does *not* fix `examples/todo-list`: that needs one node emitting two different edges from a shared ancestor, which no identity node does.

- **`.topology` authoring format — resolved in design, open only in what "the log" is scoped to at a boundary.** Both framing and mechanism are now settled and recorded in design-history.md ("A join is a topology boundary", and "A membrane closes on terminal markers, and a topology-as-node is handed the log"): a single topology only fans out, reconvergence happens at a membrane, the join sits at the producing topology's *exit*, a repeated bare name means another instance, a composite node closes on declared terminal markers rather than inner quiescence, and a topology-as-node resolves its inputs from the log rather than from arcs. This entry restores a section `elaborate.ts`'s `Wiring` doc comment has been citing while it did not exist, The scoping question this entry previously held open — whether a topology-as-node sees its producer's exports or the whole log — was resolved 2026-09-25 in favour of the whole log, recorded there. Nothing is left open here; the entry remains as the resolvable citation target.


- **Prose blocks on node declarations.** Floated as a plain-language description alongside a node's typed contract — directly useful as the tool-calling "description" field once nodes are exposed as agent tools (see design-history.md's note that nodes-are-tools, edges-are-schemas mapping). Not decided: whether this is required, optional, machine-checked against behavior, or purely documentation. A sibling project's `prediction_prompt` field (design-history.md, "`correlation_id` origin/lifetime") is a concrete candidate instance of this content — doesn't settle the mechanism question, just gives it a real example to check any answer against. `contract.ts`'s `SealedContract.description` (design-history.md, "Sealed contract export and implementation metadata") is now a second, real instance — still optional there, not machine-checked — same open question, one more data point, not a resolution.

- **`correlation_id` origin/lifetime for multi-invocation tool-calling threads.** Surfaced by a sibling project's two-call agent-tool pattern (design-history.md, "`correlation_id` origin/lifetime: a gap surfaced by a sibling project's tool contract") — one external trigger produces an edge, a second, later, genuinely separate external trigger needs `allOf:` to find it, which only works if both invocations resolve against the same `correlation_id`. "`every` lands" (design-history.md) assumed a fresh external trigger always mints a fresh `correlation_id`, reasoning aimed at ruling out loop-shaped recurrence within one invocation — not a considered decision about multi-call threads. Not decided: whether `correlation_id` can be caller-supplied (an agent/tool-runtime passing the same session/thread identifier across calls) rather than always framework-minted, and what its lifetime is (one request vs. a whole tool-calling session). Nothing already decided blocks resolving this either way; it just hasn't been decided yet. A candidate answer exists, found outside weir rather than designed here (design-history.md, "`mental-museum`'s answer: identity minted by the earlier node's own payload") — sidesteps `correlation_id` entirely in favor of a node-minted id carried as ordinary payload data, with once-only consumption enforced by node logic. Leaves its own thread open: whether the lookup this implies (`SetupId -> SetupRecord`) needs to be an ordinary node/edge to keep "effects are data" intact, or is a legitimate exception.

- **Should `Failed<In>` be tagged like `oneOf`'s other branches?** `membrane.ts` now resolves a rejected assert or an uncaught `Fn` throw to `Failed<In>` (design-history.md, "`Failed<In>` built: a plain union, not retroactively tagged like `oneOf`") — but as a bare `{ input, reason? }` object unioned into the return type, not wrapped in the `{edge, payload}` tag `oneOf`/`allOf` branches carry. §3's "every node's real output signature is `one of {successes, Failed}`" doesn't specify the wire-format precisely enough to settle this either way. Live consequence, not just theoretical: a caller currently can't distinguish a genuine `single`-output success payload that happens to have a field named `input` from a real `Failed<In>` by shape alone — there's no discriminant. Revisit once a real `.edge` collides on that field name, or once `.topology`/the runtime need to route a `Failed<In>` branch the same mechanical way an `oneOf` tag gets routed.

- **Serialization format for the netlist/log.** JSON was used for illustration throughout, but never chosen deliberately. Matters more than it looks: whatever format is picked has to carry schema hashes, envelope fields, and (per design-history.md) a strict boundary where no type variable ever appears in an emitted netlist.

- **Which host language elaborates.** TypeScript, OCaml, a DSL, and Rust macros were all named as candidates early on (23:38) with no follow-up decision. Current lean is OCaml, not settled. A TS spike exists ([`spikes/ts-prototype/`](../spikes/ts-prototype/)) to validate the edge/hash design cheaply — it's a prototype for the *ideas*, not a claim on the eventual language, and the identity-function inference trick it relies on (`defineField`/`defineEdge`) is TS-specific and won't carry over to OCaml as-is.

- **Where do client/server and PII-obfuscation-at-the-client map onto nodes and edges?** Originally raised as unresolved with no obvious node/edge mapping — existing prior art (an earlier project's design that labels fields as PII and obfuscates client-side). A later pass (2026-09-10) split "client" into three physically distinct targets that all execute the same compiled node artifact: in-browser (JS/WASM), locally installed (e.g. a Claude Code plugin/CLI), and deployed (Deno Sandbox or self-hosted, see the micro-VM sub-bullet below). An initial framing — that the locally-installed case "needs zero isolation, since the user is running their own code" — was corrected on the spot: the user only authors the *declaration* (the sealed contract); `Fn`'s body is a black box even to the person installing it (design-history.md, "Sealed contract export and implementation metadata" — "the human doesn't write node bodies"). So the thing being defended against is the same in every zone — the black-box `Fn` — not "other tenants of a multi-tenant platform"; what differs per zone is only whose machine sits on the other side of the boundary: other tenants (deployed), the installing user's own machine (local), or the user's machine plus other page scripts (browser). That means local install doesn't get isolation *for free* the way npm-style "just trust what you installed" does — it gets isolation *cheaply*, because "effects are data" (§5) already means a node needs no host capabilities to satisfy its contract, so denying fs/network to the sandboxed `Fn` costs zero legitimate functionality (unlike a real npm postinstall script, where sandboxing routinely breaks intended behavior). Also argues JS-level isolation isn't sufficient across all three zones on its own: if "nodes as compiled distributable units" (below) means nodes compile to native binaries rather than staying JS, a V8 isolate can't sandbox that artifact at all — only OS/VM-level isolation (seccomp, gVisor, a Firecracker-style microVM) can, which suggests the same KVM-shaped mechanism recurring in the locally-installed zone, not only the hosted one. Browser stays the one genuine exception, since there's no native-code path there regardless. Not decided: whether PII-obfuscation-at-the-client is specific to the browser zone (the only one combining "code runs somewhere the platform doesn't control at all" with "the user is a passive page visitor, not someone who chose to install anything") or applies uniformly across zones; still a candidate "upstream" node, still a guess not a decision.

- **Nodes as compiled, distributable units.** Raised as "every node compiles to its own binary," motivated by portability and distributed compute, and explicitly flagged by the raiser as early/not fully thought through — several distinct directions got bundled under one sentence and deserve separating rather than designing together:
  - *Sandboxed eval of DB-stored, user-authored node source* (Deno/V8-isolate-style) — a different execution model from ahead-of-time compilation (interpret at invoke time vs. compile once), with its own determinism/security tradeoffs, not yet weighed. One real affinity worth keeping: "effects are data" already means a node body needs no host capabilities (no filesystem, no network), which is exactly what makes safe sandboxing tractable — most code is hard to sandbox because it needs a laundry list of permissions; weir nodes structurally don't. Real system checked (2026-09-10) rather than speculated: Deno's actual sandbox product (not classic Deploy) wraps each tenant in its own Firecracker microVM rather than a bare V8 isolate — a concrete data point that isolate-only multi-tenancy wasn't sufficient once running arbitrary code with native bindings, which collapses this sub-bullet and the Kubernetes/micro-VMs sub-bullet below into one mechanism rather than two competing execution models. See the client/server bullet above for why the same KVM-shaped mechanism plausibly recurs in the locally-installed zone too, not just the hosted one.
  - *RTOS/embedded targets* — this one isn't just a deployment detail, it presses on the already-open "which host language elaborates" question directly. A GC'd runtime is often a poor fit for a memory-constrained embedded target, which suggests implementation-per-target behind one `.node.yaml` contract, rather than one host language — multiplying §10's versioning by platform as well as by contract hash. Not designed; flagged as changing an existing open question, not just extending §10.
  - *Kubernetes / micro-VMs* — closer to an already-tractable deployment/isolation-mechanism question once nodes are independently invocable units at all (same content-addressed artifact, different place it runs), and doesn't obviously require new core decisions the way the embedded case does.
  - *A package system* — largely a free consequence of §10's content-addressed `<contract-hash>.ts` artifacts (Nix/cargo-shaped) plus a registry/distribution layer on top, not a new mechanism to design from scratch.
  - *Monolith vs. distributed as a deployment axis, not a design-time commitment* — parallel to §9's "same substrate, only the wiring decision changes": because a node's contract is total (no `this`, no ambient access), the same topology should be runnable in-process (one Rails/Express-style application) or distributed, without the design needing to pick one. **Zones (§7) may already be the right mechanism for expressing this** — "annotate where a node runs, topology unchanged, cross-zone edges are the network hops" is already exactly the shape of "which node runs on which target"; extending zones' vocabulary (an `embedded` zone, a `cluster` zone) rather than inventing a parallel "deployment target" concept would keep one mechanism doing both the privacy-boundary job and this one.
  - *Composition syntax may already be a literal execution strategy, not just notation, for the linear case.* `birthday | birthday` (§3's sequential composition) reads exactly like a Unix pipe, and a pipe is a real, decades-proven implementation of that same semantic — stdin/stdout, no shared state. If primitives compile to binaries, a linear chain isn't just analogous to a shell pipeline, it could literally be one. Doesn't resolve fan-out/fan-in, though — plain pipes are one-in-one-out, and `oneOf`/`allOf`/`many` would need something closer to `tee`/named-pipes/process-substitution. Multi-input's `allOf:` (design-history.md, "The membrane") resolved how a node *reads* several logs at once; it says nothing about how a node *emits* to several downstream consumers, which is the piece this bullet is actually about — a concrete reference implementation to study when that gets picked up, not a shortcut past it.

- ~~**Does `scope` subsume `allOf:`, or stay a separate declaration?**~~ **Resolved 2026-09-24 — see design-history.md, "`scope` subsumes `allOf:` — same mechanism, `scope` just doesn't wait."** They're the same mechanism: both declare a set of edges that must all be present; `allOf:` waits for missing instances to arrive, `scope` fails immediately as a scope-mismatch failure edge, and `scope` alone carries optional field-level narrowing. `allOf: [A, B]` is sugar for `scope: [read:A, read:B]` with waiting turned on and no narrowing — not a second thing to reconcile against `scope`. (Earlier text, for the record: `Fn` receiving only the specific field(s) a node's `scope` names, never the whole edge, was already settled — a durable-functions auth middleware from an earlier project scoped required env vars this precisely, though it notably didn't apply the same narrowing to the authenticated-user object it passed through, part of what prompted designing this more tightly here.)

- **Should the generator (`generate.ts`, docs/superpowers/specs/2026-09-10-generator-and-fuzz-harness.md) generate `null` for nullable fields, and explore cross-field combinations?** Neither was named in that spec, surfaced instead by the final whole-branch review that implemented it. `null` is arguably the canonical boundary value for a `nullable: true` field — "the case a hand-written example set is least likely to include" (the spec's own rationale for boundary bias generally) — but adding it wasn't part of the approved design. Separately: every field in one generated payload currently shares a single `caseIndex`, so per-field boundary coverage is thorough but cross-field *combinations* are never explored (a bool and a 2-value enum on the same edge only ever see 2 of their 4 possible combinations, no matter how large `count` is) — `generateManyValue`'s own `caseIndex + i` fix (design-history.md, "The generator mechanism, built") is the visible precedent for a general remedy, not yet generalized beyond collections. Neither is a defect in what was built; both are candidate scope for a follow-up spec.

- **Which parts of a node declaration are contract, and which are commentary?** Surfaced putting property assertions in the contract hash (`hash.ts`'s `fingerprintNode`, docs/superpowers/specs/2026-09-23-property-assertions.md) — precisely to avoid an implementation sitting accepted against a strengthened invariant it was never checked against, the same reasoning `closure` was already included for. That choice made two existing omissions look like an inconsistency rather than an oversight. **One of the two is now closed:** `scope` is fingerprinted. It is *behavioural* — it feeds `narrowIdentity`, so it decides what data `Fn` actually receives at runtime. Change `read:Identity:sub` to `read:Identity:iss` and, unhashed, the previously-accepted implementation resolves unchanged and reads `env.identity.sub` as `undefined`, silently, with `acceptImplementation` declining to re-check it because the hash says nothing changed. Replay made the same hole worse: `replayInvocation`'s drift refusal is only as good as `fingerprintNode`'s coverage, so a declaration whose `scope` had widened since the recorded invocation passed the drift check untouched, resolved the very same pinned implementation, and replayed "successfully" with the newly-declared field simply absent from the replayed `identity`. The stated reason for deferring — "changing what's in the hash shifts every existing accepted hash" — turned out to be vacuous on inspection: no `implementations/` tree exists in this repo and no `<contract-hash>.ts` file lives anywhere outside a test's temp directory, so there were no accepted hashes to shift and the fix cost nothing. Scope is sorted and de-duplicated before hashing (order carries no meaning; a repeated scope is redundant but unambiguous), and an empty array hashes identically to no `scope` at all.

  **Still open: `examples`.** It stays out of the hash, deliberately, per `NodeFingerprint`'s own doc comment ("examples gate acceptance, they don't define the hash being accepted against"). The asymmetry with `scope` is the point — `examples` is a *verification* artifact, not behaviour — but the consequence is still real: adding an example to a node doesn't invalidate its accepted implementation, so an implementation can sit marked accepted while an example it was never run against sits right there in its contract. Leaving it unhashed weakens a gate rather than corrupting a result, which is why it didn't ride along with `scope`; what's undecided is whether that weakened gate is acceptable long-term, or whether acceptance should instead re-run examples against an already-accepted implementation without re-deriving its hash — a third option that keeps the hash meaning "the contract" while closing the hole.

- **`Log` is doing two jobs under one interface.** Surfaced building invocation records (docs/superpowers/specs/2026-09-23-invocation-records-and-replay.md §2): `Log.append` both records what a node actually emitted — provenance-carrying, an `InstanceEnvelope` attached — and stages inputs so an `allOf`-input node's readiness check has something to find (`invoke.ts`, and several tests, appending a payload with no invocation behind it at all). That second use is why `envelope` had to become optional rather than required: a staged input has nothing to attach. Making the parameter optional kept every existing caller working, but it means one interface is quietly standing in for two different kinds of entry. Not decided: whether staging deserves a mechanism of its own, separate from the Log, or whether a "staged" instance — envelope absent, by construction rather than by omission — is a legitimate kind of log entry in its own right. **Related, deliberately recorded alongside this — and half of it is now stale.** `runtime.ts`'s `tryFire` was said to rebuild an `allOf` node's input bag with its own `log.latest` loop, duplicating a read the membrane's `allOf` invoke performed internally, so the two could drift once reads stopped being same-tick; the fix was for `membrane()` to return its resolved input. **That double read no longer exists.** Piece (3) §5 stopped the membrane resolving `allOf` inputs — it takes the bag as an argument and only asserts it — so there is one read, and the hazard is absent rather than dormant. Verified 2026-09-26 while speccing the durable log: `membrane.ts` contains no `log.latest` call outside the interface declaration and `InMemoryLog`'s own implementation. What stays live is the first half of this entry: `append` both records a provenance-carrying emission and stages an input with no invocation behind it, and a durable store makes that ambiguity permanent rather than per-process. Addressed by [the durable-log spec](superpowers/specs/2026-09-26-a-log-that-outlives-the-process.md) §3, which gives staging its own method and an explicit marker.

- **Should `membrane()` build the envelope before asserting input, so every attempted invocation is observable?** Surfaced deciding the envelope's optionality (docs/superpowers/specs/2026-09-23-invocation-records-and-replay.md §4). The envelope is built *after* the input assert, so a rejected input returns `Failed<In>` before any envelope exists — which is why the returned envelope is optional, with the rule "present iff `Fn` actually ran." That rule is clean and gives the trace a precise meaning: it records *invocations*, never attempts. The cost is observability, and it is larger than it first appears. A rejected input produces **no trace entry at all**, and its `Failed_*` log instance carries **no provenance** (`instanceEnvelope` returns `undefined` without an envelope) — leaving it shaped exactly like a *staged* input, which `Log.append`'s own doc comment says never happens for a real emitted instance. So two failures that look identical in the log (`{input, reason}` under the same synthesized edge) have opposite provenance depending on whether `Fn` ran: a thrown `Fn` gets a trace entry and a provenance-carrying instance, a rejected input gets neither. The only thing distinguishing them is the *absence* of provenance — a real signal, but an accidental one rather than a designed one. Replaying a run therefore reproduces its invocations and silently skips its rejections. Not decided: whether to build the envelope first (making it non-optional and every attempt observable, at the cost of changing error precedence — a bad `scope` declaration would surface ahead of a bad input, breaking existing tests — and running `hashNode` for inputs about to be rejected anyway), or to keep the current ordering and distinguish rejections some cheaper way, e.g. a marker on the `Failed_*` instance saying "rejected before invocation" that closes the looks-like-a-staged-input confusion without touching ordering. Current read is that observability probably does want the first option eventually; this pass was implemented correctly under the second, and the choice deserves its own decision rather than being folded into a branch about replay.

  **Resolved, 2026-09-24: build the envelope first.** `buildEnvelope` now runs before `assertPayload` in both the `single` and `allOf` branches of `membrane()`, and `Invocation.envelope` (`membrane.ts`) is non-optional — an envelope exists for every *attempted* invocation, not only every completed one. `LoggedInstance.envelope` (also `membrane.ts`) stays optional; that one is about a genuinely staged input with no invocation behind it at all, a different case entirely. Costs, taken as intended rather than avoided: **(1)** error precedence flips — a node with both a bad `scope` and a bad input now reports the scope error, since `buildEnvelope` runs and throws first. Judged correct: a bad `scope` is a declaration bug (the node is malformed regardless of input), a bad input is a runtime condition (the node is fine, the data isn't), and reporting the declaration bug first matches the project's existing split between declaration bugs (throw) and implementation failures (collected). **(2)** `hashNode` now runs for every input about to be rejected, not just accepted ones — accepted as the price of a real `contractHash` on every attempt's envelope. **(3)** the trace now records attempts, not only completed `Fn` runs — `replayInvocation` on a rejected-input entry re-asserts and re-rejects deterministically, which is honest (proved in `replay.test.ts`, "replays a rejected input deterministically"), but means a trace entry no longer implies `Fn` ran to completion; `runtime.ts`'s `tryFire` already had this looseness in its return-boolean semantics before this change (a rejected input already counted as a "firing"), so this doesn't introduce a new inconsistency there so much as make the trace agree with it. The one remaining case with no envelope at all: `buildEnvelope` itself throwing (the bad-`scope` case above) still resolves to `Failed<In>` with no envelope to attach — nothing was ever built, so there is nothing to record, and `runtime.ts`'s trace-recording gate (`envelope !== undefined`) and `instanceEnvelope`'s `!envelope` branch both stay in place for exactly that one case rather than becoming unconditional.

- **Declarations acceptance gate — required human sign-off on `declarations/`, exact loosening mechanism undecided.** `design-history.md` ("Acceptance gating, generalized one layer up") generalizes §10's existing accept-before-persist mechanism from implementations to declarations: a change to `.edge`/`.node`/`.topology` isn't accepted until a human signs off, independent of who drafted it — buildable today as required review on `declarations/**`, CODEOWNERS-shaped. Decided to ship this as a required gate rather than optional from the start (a constraint that's optional from day one never gets pressure-tested). Not designed: the loosening mechanism itself — who's allowed to be the accepting reviewer once a project has earned enough trust to relax it, whether that's a `.node`-file-shaped permission (§7's PDP shape) or a repo-level setting entirely outside weir's own contract, and whether the gate applies uniformly to all of `declarations/` or per-file/per-directory/per-edge individually.
