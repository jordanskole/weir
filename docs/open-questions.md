# Open questions

Things raised in the design conversation that were not resolved — as opposed to items in [getting-started.md](getting-started.md#deferred-on-purpose-dont-build-yet), which are resolved in design but deliberately postponed in implementation order.

- **Sleep / wait.** Is a delay a property of an edge (e.g. a `DelayedOrder` that resolves later), a special node type, or a runtime concern outside the node model entirely? Ties into the "nothing polls, only origin nodes introduce nondeterminism" rule — a wait is a kind of origin.

- **Prose blocks on node declarations.** Floated as a plain-language description alongside a node's typed contract — directly useful as the tool-calling "description" field once nodes are exposed as agent tools (see design-history.md's note that nodes-are-tools, edges-are-schemas mapping). Not decided: whether this is required, optional, machine-checked against behavior, or purely documentation. A sibling project's `prediction_prompt` field (design-history.md, "`correlation_id` origin/lifetime") is a concrete candidate instance of this content — doesn't settle the mechanism question, just gives it a real example to check any answer against.

- **`correlation_id` origin/lifetime for multi-invocation tool-calling threads.** Surfaced by a sibling project's two-call agent-tool pattern (design-history.md, "`correlation_id` origin/lifetime: a gap surfaced by a sibling project's tool contract") — one external trigger produces an edge, a second, later, genuinely separate external trigger needs `every:` to find it, which only works if both invocations resolve against the same `correlation_id`. "`every` lands" (design-history.md) assumed a fresh external trigger always mints a fresh `correlation_id`, reasoning aimed at ruling out loop-shaped recurrence within one invocation — not a considered decision about multi-call threads. Not decided: whether `correlation_id` can be caller-supplied (an agent/tool-runtime passing the same session/thread identifier across calls) rather than always framework-minted, and what its lifetime is (one request vs. a whole tool-calling session). Nothing already decided blocks resolving this either way; it just hasn't been decided yet. A candidate answer exists, found outside weir rather than designed here (design-history.md, "`mental-museum`'s answer: identity minted by the earlier node's own payload") — sidesteps `correlation_id` entirely in favor of a node-minted id carried as ordinary payload data, with once-only consumption enforced by node logic. Leaves its own thread open: whether the lookup this implies (`SetupId -> SetupRecord`) needs to be an ordinary node/edge to keep "effects are data" intact, or is a legitimate exception.

- **Should `Failed<In>` be tagged like `oneOf`'s other branches?** `membrane.ts` now resolves a rejected assert or an uncaught `Fn` throw to `Failed<In>` (design-history.md, "`Failed<In>` built: a plain union, not retroactively tagged like `oneOf`") — but as a bare `{ input, reason? }` object unioned into the return type, not wrapped in the `{edge, payload}` tag `oneOf`/`allOf` branches carry. §3's "every node's real output signature is `one of {successes, Failed}`" doesn't specify the wire-format precisely enough to settle this either way. Live consequence, not just theoretical: a caller currently can't distinguish a genuine `single`-output success payload that happens to have a field named `input` from a real `Failed<In>` by shape alone — there's no discriminant. Revisit once a real `.edge` collides on that field name, or once `.topology`/the runtime need to route a `Failed<In>` branch the same mechanical way an `oneOf` tag gets routed.

- **Serialization format for the netlist/log.** JSON was used for illustration throughout, but never chosen deliberately. Matters more than it looks: whatever format is picked has to carry schema hashes, envelope fields, and (per design-history.md) a strict boundary where no type variable ever appears in an emitted netlist.

- **Which host language elaborates.** TypeScript, OCaml, a DSL, and Rust macros were all named as candidates early on (23:38) with no follow-up decision. Current lean is OCaml, not settled. A TS spike exists ([`spikes/ts-prototype/`](../spikes/ts-prototype/)) to validate the edge/hash design cheaply — it's a prototype for the *ideas*, not a claim on the eventual language, and the identity-function inference trick it relies on (`defineField`/`defineEdge`) is TS-specific and won't carry over to OCaml as-is.

- **Where do client/server and PII-obfuscation-at-the-client map onto nodes and edges?** Raised directly as unresolved — existing prior art (an earlier project's design that labels fields as PII and obfuscates client-side) doesn't have an obvious node/edge mapping yet. Possibly resolves as an "upstream" node, but that was a guess, not a decision.

- **Nodes as compiled, distributable units.** Raised as "every node compiles to its own binary," motivated by portability and distributed compute, and explicitly flagged by the raiser as early/not fully thought through — several distinct directions got bundled under one sentence and deserve separating rather than designing together:
  - *Sandboxed eval of DB-stored, user-authored node source* (Deno/V8-isolate-style) — a different execution model from ahead-of-time compilation (interpret at invoke time vs. compile once), with its own determinism/security tradeoffs, not yet weighed. One real affinity worth keeping: "effects are data" already means a node body needs no host capabilities (no filesystem, no network), which is exactly what makes safe sandboxing tractable — most code is hard to sandbox because it needs a laundry list of permissions; weir nodes structurally don't.
  - *RTOS/embedded targets* — this one isn't just a deployment detail, it presses on the already-open "which host language elaborates" question directly. A GC'd runtime is often a poor fit for a memory-constrained embedded target, which suggests implementation-per-target behind one `.node.yaml` contract, rather than one host language — multiplying §10's versioning by platform as well as by contract hash. Not designed; flagged as changing an existing open question, not just extending §10.
  - *Kubernetes / micro-VMs* — closer to an already-tractable deployment/isolation-mechanism question once nodes are independently invocable units at all (same content-addressed artifact, different place it runs), and doesn't obviously require new core decisions the way the embedded case does.
  - *A package system* — largely a free consequence of §10's content-addressed `<contract-hash>.ts` artifacts (Nix/cargo-shaped) plus a registry/distribution layer on top, not a new mechanism to design from scratch.
  - *Monolith vs. distributed as a deployment axis, not a design-time commitment* — parallel to §9's "same substrate, only the wiring decision changes": because a node's contract is total (no `this`, no ambient access), the same topology should be runnable in-process (one Rails/Express-style application) or distributed, without the design needing to pick one. **Zones (§7) may already be the right mechanism for expressing this** — "annotate where a node runs, topology unchanged, cross-zone edges are the network hops" is already exactly the shape of "which node runs on which target"; extending zones' vocabulary (an `embedded` zone, a `cluster` zone) rather than inventing a parallel "deployment target" concept would keep one mechanism doing both the privacy-boundary job and this one.
  - *Composition syntax may already be a literal execution strategy, not just notation, for the linear case.* `birthday | birthday` (§3's sequential composition) reads exactly like a Unix pipe, and a pipe is a real, decades-proven implementation of that same semantic — stdin/stdout, no shared state. If primitives compile to binaries, a linear chain isn't just analogous to a shell pipeline, it could literally be one. Doesn't resolve fan-out/fan-in, though — plain pipes are one-in-one-out, and `oneOf`/`allOf`/`many` would need something closer to `tee`/named-pipes/process-substitution. Multi-input's `every:` (design-history.md, "The membrane") resolved how a node *reads* several logs at once; it says nothing about how a node *emits* to several downstream consumers, which is the piece this bullet is actually about — a concrete reference implementation to study when that gets picked up, not a shortcut past it.

- **Does `scope` subsume `every:`, or stay a separate declaration?** Resolved that `Fn` receives only the specific field(s) a node's `scope` names (`read:Identity:sub`), never the whole `Identity` object — real prior art (a durable-functions auth middleware, generalized in design-history.md) scoped required env vars this precisely via a `Record<Required[number], string>`-shaped generic, though notably did *not* apply the same narrowing to the authenticated-user object it passed through, which is part of what prompted designing this more tightly here. Not resolved: whether `scope`'s `verb:edge:field` shape (`read:Identity:sub`, `read:UserProfile:email`) is actually the *same* mechanism as `every:`'s edge-presence check, generalized with field-level narrowing and applied uniformly to every edge (system-provided or ordinary) — or a genuinely separate declaration (permission vs. data dependency) that happens to resolve through the same membrane and look syntactically similar. If they're the same mechanism, `every: [A, B]` might just be sugar for `scope: [read:A, read:B]` with no field narrowing; if they're different, a node ends up with two lists to reconcile (`input`/`every` and `scope`) that can name overlapping edges for different reasons.

- **Declarations acceptance gate — required human sign-off on `declarations/`, exact loosening mechanism undecided.** `design-history.md` ("Acceptance gating, generalized one layer up") generalizes §10's existing accept-before-persist mechanism from implementations to declarations: a change to `.edge`/`.node`/`.topology` isn't accepted until a human signs off, independent of who drafted it — buildable today as required review on `declarations/**`, CODEOWNERS-shaped. Decided to ship this as a required gate rather than optional from the start (a constraint that's optional from day one never gets pressure-tested). Not designed: the loosening mechanism itself — who's allowed to be the accepting reviewer once a project has earned enough trust to relax it, whether that's a `.node`-file-shaped permission (§7's PDP shape) or a repo-level setting entirely outside weir's own contract, and whether the gate applies uniformly to all of `declarations/` or per-file/per-directory/per-edge individually.

- **Partial input, partial node-pinned default — no mechanism for either yet.** Surfaced hand-authoring `CreateTodo.node` (`examples/todo-list/`): creating a `Todo` should only take `title`/`description` from the caller — `is_complete` should always start `false`, not be caller-suppliable. `closure` (§10) only handles all-or-nothing baked-in values (an origin's entire output, an `expect`'s entire comparison value); nothing covers "some fields from the input, one field pinned by the node itself." Worked around for now by making `input: Todo` the full shape and having the caller pass `is_complete: false` explicitly — not wrong, just unenforced (a caller *could* pass `true` at creation and nothing stops it). Real fix, not designed: something like a node declaring which of its input edge's fields it actually accepts, with the rest defaulted — closer to spread (§2's `...Animal`) applied to a node's input than to `closure`, but spread today is additive-only (build a new edge's fields), never subtractive/exclusionary, and has never applied to a node's `input:` at all, only to `.edge` field maps.
