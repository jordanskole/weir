# Open questions

Things raised in the design conversation that were not resolved — as opposed to items in [getting-started.md](getting-started.md#deferred-on-purpose-dont-build-yet), which are resolved in design but deliberately postponed in implementation order.

- **Sleep / wait.** Is a delay a property of an edge (e.g. a `DelayedOrder` that resolves later), a special node type, or a runtime concern outside the node model entirely? Ties into the "nothing polls, only origin nodes introduce nondeterminism" rule — a wait is a kind of origin.

- **"No loop construct" is a real gap in the runtime, not just an unimplemented nicety — surfaced by an outside reader (a friend's ChatGPT session, 2026-09-24, sketching a SOC-triage app built *on* weir) testing the claim against actual code rather than taking `design-history.md`'s word for it.** `design-history.md` ("Weir has no loop construct, and needed none") and `design.md` §3 hold that a repeated node name in a `.topology` file (`birthday.then.birthday`) is "a legitimate distinct application, not a cycle," and that recurrence should be modeled as fresh forward execution rather than control-flow looping. That's the stated design intent, but the runtime doesn't implement it: `runtime.ts:162` maintains `const fired = new Set<string>()` keyed by bare node name, and `runtime.ts:166` (`if (fired.has(nodeName)) return false`) means a node that appears twice in a topology fires **once**, full stop — verified directly against the code, not taken on the outside reader's word. So today, `birthday.then.birthday.then.birthday` doesn't run three times; it runs once, silently. This matters for exactly the kind of workload the "ActiveCampaign for agents"/SOC-triage direction needs — "keep gathering evidence and reassessing until the investigation is complete" is a natural recurring `assess → request more evidence → assess` shape, and it's unbuildable today except by hand-unrolling distinct node names per iteration (`assess1`, `collect1`, `assess2`, ...), which the same outside reader correctly called "obviously not ideal."
  - **A concrete, not-yet-designed candidate answer, from the same conversation:** stop keying "has this fired" by bare `nodeName`, and key it by `(nodeName, correlationId, consumed input edge-instance ids)` instead. Under that identity, the same node can fire again validly whenever it's now facing genuinely new input edge instances it hasn't consumed before — turning "loop until done" into an emergent fixpoint ("keep firing every node whose particular input edge instances haven't previously been consumed by that node, until nothing new is produced") rather than a control-flow primitive, consistent with the log-as-source-of-truth model (§5) rather than bolted onto it. A terminal condition falls out for free too: a topology reaches quiescence when no node has unconsumed-and-satisfying input left, or an explicit terminal edge (`InvestigationComplete`-shaped) appears.
  - **Substantially resolved in design 2026-09-24 — see design-history.md, "Iteration: it's a Petri net, and the loop was never the missing piece."** Three corrections to this entry as written. First, the diagnosis above blames `runtime.ts`'s `fired: Set<string>`, but that is the *second* problem: `InMemoryLog` keeps one instance per `(edgeName, correlationId)` and `append` overwrites, so even with firing identity fixed there would be no distinct instances to key on. Latest-wins is the banned ambient mutable cell, sitting in the runtime rather than in a node. Second, the candidate answer below presumes edge instances that are individually identified and retained; they are neither today. Third, the framing "no loop construct" conflated a construct with a capability — `while` needs ambient state, recursion does not, and a node feeding itself with a `oneOf` base case is already the recursive form. Settled: fire once per unconsumed instance (a Petri net's transition rule), consumption tracked per node, `allOf` joined by shared lineage rather than a declared key, iteration bounded by the host rather than the language. Vocabulary settled too — a **token** is one edge instance in flight, a **run** is one traversal (`correlationId`), and lineage is `causationId`, currently a `null` placeholder. Now decomposed into four specs in dependency order: (1) the log becomes a log, (2) causation is real, (3) `allOf` joins by lineage, (4) composite nodes / "enroll in workflow".
  - **Resolved in code too, 2026-09-24 — piece (1) is implemented** ([spec](superpowers/specs/2026-09-24-instance-retention-and-iteration.md), status: implemented). `InMemoryLog` retains every instance instead of overwriting; `runtime.ts`'s driver is a real pulse loop that snapshots readiness once per pulse; a `single`-input node fires once per unconsumed instance reaching it along a declared arc in `wiring.feeds`, not on its input edge's latest instance; and `envelope.step` is the pulse number rather than a hardcoded `0`. The canonical example still fires each node exactly once, and a genuine cycle — a node wired back to itself whose `Fn` emits a continue-branch until a `oneOf` base case — now runs to quiescence instead of firing once, bounded by the host's `budget` (firings) and a `maxPulses` backstop (pulses) rather than by the language. What remains open from this entry is piece (3), `allOf` joining by lineage: an `allOf` node still fires at most once per run, resolving its bag by `latest` as before, so **iteration works for single-input chains only**. One limitation surfaced building piece (1), not anticipated when it was scoped: a node that is both an origin and a `feeds` target can never iterate — the runtime checks `origins.has(nodeName)` first and always routes an origin to its once-only branch, so it is never offered instance candidates regardless of how the topology wires it. This matches prior (pre-piece-(1)) behaviour and is not a regression, but it means a fixture exercising a self-feeding node needs a separate seed node feeding it, not the origin doubling as the looped node itself.
  - **Relationship to work already in flight:** `docs/superpowers/specs/2026-09-23-invocation-records-and-replay.md` (actively being implemented as of this week — `Envelope`, `Trace`, version pinning) is adjacent infrastructure — it's the machinery that would need to exist for a real "consumed input edge-instance ids" identity to be recorded and checked — but its own "Explicitly out of scope" section names `causationId` as staying a placeholder `null` and doesn't touch node-firing identity at all. So this isn't redundant with that spec, and it isn't blocked by it either exactly — but it's the natural next layer on top of it, worth flagging to whoever picks up invocation-records next rather than designing in isolation.

- **Positional identity in a topology: `birthday.then.birthday.then.birthday` should run three times.** Split out of the "no loop construct" entry above, which conflated two different features. This one is not data-driven iteration — it's that two *mentions* of one node in a `.topology` are two distinct instances, and `Wiring`'s flat parent→children adjacency map can't represent the difference between "run it three times" and "run it forever" once nested YAML is collapsed into it. `examples/person-birthday/README.md` already flags the same gap from the other side ("Instance identity is `node-name#n`"), and `netlist.ts`'s `serializeNetlist` already emits `${nodeName}#1` ids that nothing yet makes meaningful. More todo than open question — the answer is probably just "give `Wiring` real positional instance identity and key firing on that" — but it needs doing deliberately rather than falling out of the iteration work, since the two have different termination stories: this one terminates by construction, iteration terminates by quiescence.

- **The membrane bounds behaviour, not control — `nodeDef.fn` is still directly reachable.** `membrane(nodeDef, ...args)` no longer hands out a detached invoker (it used to return a callable the caller invoked later, so "invocation only happens through the membrane" was enforced by every call site happening to comply, not by the structure). That closed one gap and left the larger one: `fn` is a public field on `NodeDef`, and `implementation.ts`, `fuzz.ts` and `accept.ts` all pass whole `NodeDef`s around, so nothing prevents calling it directly and skipping the assert, the envelope and the `Failed<In>` conversion. The membrane's guarantee is therefore "if you call me, these things happen" rather than "these things happen". Making it structural means `fn` not being readable from the type consumers hold — resolution constructs it, nothing else can reach it — which touches how implementations are resolved and handed to the runtime, and how the fuzz and acceptance paths invoke candidates. Not attempted; recorded because the gap between what the name claims and what the code enforces is exactly the kind of thing that stops being obvious once the shape looks right.

- **Prose blocks on node declarations.** Floated as a plain-language description alongside a node's typed contract — directly useful as the tool-calling "description" field once nodes are exposed as agent tools (see design-history.md's note that nodes-are-tools, edges-are-schemas mapping). Not decided: whether this is required, optional, machine-checked against behavior, or purely documentation. A sibling project's `prediction_prompt` field (design-history.md, "`correlation_id` origin/lifetime") is a concrete candidate instance of this content — doesn't settle the mechanism question, just gives it a real example to check any answer against. `contract.ts`'s `SealedContract.description` (design-history.md, "Sealed contract export and implementation metadata") is now a second, real instance — still optional there, not machine-checked — same open question, one more data point, not a resolution.

- **`correlation_id` origin/lifetime for multi-invocation tool-calling threads.** Surfaced by a sibling project's two-call agent-tool pattern (design-history.md, "`correlation_id` origin/lifetime: a gap surfaced by a sibling project's tool contract") — one external trigger produces an edge, a second, later, genuinely separate external trigger needs `allOf:` to find it, which only works if both invocations resolve against the same `correlation_id`. "`every` lands" (design-history.md) assumed a fresh external trigger always mints a fresh `correlation_id`, reasoning aimed at ruling out loop-shaped recurrence within one invocation — not a considered decision about multi-call threads. Not decided: whether `correlation_id` can be caller-supplied (an agent/tool-runtime passing the same session/thread identifier across calls) rather than always framework-minted, and what its lifetime is (one request vs. a whole tool-calling session). Nothing already decided blocks resolving this either way; it just hasn't been decided yet. A candidate answer exists, found outside weir rather than designed here (design-history.md, "`mental-museum`'s answer: identity minted by the earlier node's own payload") — sidesteps `correlation_id` entirely in favor of a node-minted id carried as ordinary payload data, with once-only consumption enforced by node logic. Leaves its own thread open: whether the lookup this implies (`SetupId -> SetupRecord`) needs to be an ordinary node/edge to keep "effects are data" intact, or is a legitimate exception.

- **Should `Failed<In>` be tagged like `oneOf`'s other branches?** `membrane.ts` now resolves a rejected assert or an uncaught `Fn` throw to `Failed<In>` (design-history.md, "`Failed<In>` built: a plain union, not retroactively tagged like `oneOf`") — but as a bare `{ input, reason? }` object unioned into the return type, not wrapped in the `{edge, payload}` tag `oneOf`/`allOf` branches carry. §3's "every node's real output signature is `one of {successes, Failed}`" doesn't specify the wire-format precisely enough to settle this either way. Live consequence, not just theoretical: a caller currently can't distinguish a genuine `single`-output success payload that happens to have a field named `input` from a real `Failed<In>` by shape alone — there's no discriminant. Revisit once a real `.edge` collides on that field name, or once `.topology`/the runtime need to route a `Failed<In>` branch the same mechanical way an `oneOf` tag gets routed.

- **Serialization format for the netlist/log.** JSON was used for illustration throughout, but never chosen deliberately. Matters more than it looks: whatever format is picked has to carry schema hashes, envelope fields, and (per design-history.md) a strict boundary where no type variable ever appears in an emitted netlist.

- **Which host language elaborates.** TypeScript, OCaml, a DSL, and Rust macros were all named as candidates early on (23:38) with no follow-up decision. Current lean is OCaml, not settled. A TS spike exists ([`spikes/ts-prototype/`](../spikes/ts-prototype/)) to validate the edge/hash design cheaply — it's a prototype for the *ideas*, not a claim on the eventual language, and the identity-function inference trick it relies on (`defineField`/`defineEdge`) is TS-specific and won't carry over to OCaml as-is.

- **Where do client/server and PII-obfuscation-at-the-client map onto nodes and edges?** Originally raised as unresolved with no obvious node/edge mapping — existing prior art (an earlier project's design that labels fields as PII and obfuscates client-side). A later pass (2026-09-10) split "client" into three physically distinct targets that all execute the same compiled node artifact: in-browser (JS/WASM), locally installed (e.g. a Claude Code plugin/CLI), and deployed (Deno Sandbox or self-hosted, see the micro-VM sub-bullet below). An initial framing — that the locally-installed case "needs zero isolation, since the user is running their own code" — was corrected on the spot: the user only authors the *declaration* (the sealed contract); `Fn`'s body is a black box even to the person installing it (design-history.md, "Sealed contract export and implementation metadata" — "the human doesn't write node bodies"). So the thing being defended against is the same in every zone — the black-box `Fn` — not "other tenants of a multi-tenant platform"; what differs per zone is only whose machine sits on the other side of the boundary: other tenants (deployed), the installing user's own machine (local), or the user's machine plus other page scripts (browser). That means local install doesn't get isolation *for free* the way npm-style "just trust what you installed" does — it gets isolation *cheaply*, because "effects are data" (§5) already means a node needs no host capabilities to satisfy its contract, so denying fs/network to the sandboxed `Fn` costs zero legitimate functionality (unlike a real npm postinstall script, where sandboxing routinely breaks intended behavior). Also argues JS-level isolation isn't sufficient across all three zones on its own: if "nodes as compiled distributable units" (below) means nodes compile to native binaries rather than staying JS, a V8 isolate can't sandbox that artifact at all — only OS/VM-level isolation (seccomp, gVisor, a Firecracker-style microVM) can, which suggests the same KVM-shaped mechanism recurring in the locally-installed zone, not only the hosted one. Browser stays the one genuine exception, since there's no native-code path there regardless. Not decided: whether PII-obfuscation-at-the-client is specific to the browser zone (the only one combining "code runs somewhere the platform doesn't control at all" with "the user is a passive page visitor, not someone who chose to install anything") or applies uniformly across zones; still a candidate "upstream" node, still a guess not a decision.

- **Nodes as compiled, distributable units.** Raised as "every node compiles to its own binary," motivated by portability and distributed compute, and explicitly flagged by the raiser as early/not fully thought through — several distinct directions got bundled under one sentence and deserve separating rather than designing together:
  - *Sandboxed eval of DB-stored, user-authored node source* (Deno/V8-isolate-style) — a different execution model from ahead-of-time compilation (interpret at invoke time vs. compile once), with its own determinism/security tradeoffs, not yet weighed. One real affinity worth keeping: "effects are data" already means a node body needs no host capabilities (no filesystem, no network), which is exactly what makes safe sandboxing tractable — most code is hard to sandbox because it needs a laundry list of permissions; weir nodes structurally don't. Real system checked (2026-09-10) rather than speculated: Deno's actual sandbox product (not classic Deploy) wraps each tenant in its own Firecracker microVM rather than a bare V8 isolate — a concrete data point that isolate-only multi-tenancy wasn't sufficient once running arbitrary code with native bindings, which collapses this sub-bullet and the Kubernetes/micro-VMs sub-bullet below into one mechanism rather than two competing execution models. See the client/server bullet above for why the same KVM-shaped mechanism plausibly recurs in the locally-installed zone too, not just the hosted one.
  - *RTOS/embedded targets* — this one isn't just a deployment detail, it presses on the already-open "which host language elaborates" question directly. A GC'd runtime is often a poor fit for a memory-constrained embedded target, which suggests implementation-per-target behind one `.node.yaml` contract, rather than one host language — multiplying §10's versioning by platform as well as by contract hash. Not designed; flagged as changing an existing open question, not just extending §10.
  - *Kubernetes / micro-VMs* — closer to an already-tractable deployment/isolation-mechanism question once nodes are independently invocable units at all (same content-addressed artifact, different place it runs), and doesn't obviously require new core decisions the way the embedded case does.
  - *A package system* — largely a free consequence of §10's content-addressed `<contract-hash>.ts` artifacts (Nix/cargo-shaped) plus a registry/distribution layer on top, not a new mechanism to design from scratch.
  - *Monolith vs. distributed as a deployment axis, not a design-time commitment* — parallel to §9's "same substrate, only the wiring decision changes": because a node's contract is total (no `this`, no ambient access), the same topology should be runnable in-process (one Rails/Express-style application) or distributed, without the design needing to pick one. **Zones (§7) may already be the right mechanism for expressing this** — "annotate where a node runs, topology unchanged, cross-zone edges are the network hops" is already exactly the shape of "which node runs on which target"; extending zones' vocabulary (an `embedded` zone, a `cluster` zone) rather than inventing a parallel "deployment target" concept would keep one mechanism doing both the privacy-boundary job and this one.
  - *Composition syntax may already be a literal execution strategy, not just notation, for the linear case.* `birthday | birthday` (§3's sequential composition) reads exactly like a Unix pipe, and a pipe is a real, decades-proven implementation of that same semantic — stdin/stdout, no shared state. If primitives compile to binaries, a linear chain isn't just analogous to a shell pipeline, it could literally be one. Doesn't resolve fan-out/fan-in, though — plain pipes are one-in-one-out, and `oneOf`/`allOf`/`many` would need something closer to `tee`/named-pipes/process-substitution. Multi-input's `allOf:` (design-history.md, "The membrane") resolved how a node *reads* several logs at once; it says nothing about how a node *emits* to several downstream consumers, which is the piece this bullet is actually about — a concrete reference implementation to study when that gets picked up, not a shortcut past it.

- ~~**Does `scope` subsume `allOf:`, or stay a separate declaration?**~~ **Resolved 2026-09-24 — see design-history.md, "`scope` subsumes `allOf:` — same mechanism, `scope` just doesn't wait."** They're the same mechanism: both declare a set of edges that must all be present; `allOf:` waits for missing instances to arrive, `scope` fails immediately as a scope-mismatch failure edge, and `scope` alone carries optional field-level narrowing. `allOf: [A, B]` is sugar for `scope: [read:A, read:B]` with waiting turned on and no narrowing — not a second thing to reconcile against `scope`. (Earlier text, for the record: `Fn` receiving only the specific field(s) a node's `scope` names, never the whole edge, was already settled — a durable-functions auth middleware from an earlier project scoped required env vars this precisely, though it notably didn't apply the same narrowing to the authenticated-user object it passed through, part of what prompted designing this more tightly here.)

- **Should the generator (`generate.ts`, docs/superpowers/specs/2026-09-10-generator-and-fuzz-harness.md) generate `null` for nullable fields, and explore cross-field combinations?** Neither was named in that spec, surfaced instead by the final whole-branch review that implemented it. `null` is arguably the canonical boundary value for a `nullable: true` field — "the case a hand-written example set is least likely to include" (the spec's own rationale for boundary bias generally) — but adding it wasn't part of the approved design. Separately: every field in one generated payload currently shares a single `caseIndex`, so per-field boundary coverage is thorough but cross-field *combinations* are never explored (a bool and a 2-value enum on the same edge only ever see 2 of their 4 possible combinations, no matter how large `count` is) — `generateManyValue`'s own `caseIndex + i` fix (design-history.md, "The generator mechanism, built") is the visible precedent for a general remedy, not yet generalized beyond collections. Neither is a defect in what was built; both are candidate scope for a follow-up spec.

- **Which parts of a node declaration are contract, and which are commentary?** Surfaced putting property assertions in the contract hash (`hash.ts`'s `fingerprintNode`, docs/superpowers/specs/2026-09-23-property-assertions.md) — precisely to avoid an implementation sitting accepted against a strengthened invariant it was never checked against, the same reasoning `closure` was already included for. That choice made two existing omissions look like an inconsistency rather than an oversight. **One of the two is now closed:** `scope` is fingerprinted. It is *behavioural* — it feeds `narrowIdentity`, so it decides what data `Fn` actually receives at runtime. Change `read:Identity:sub` to `read:Identity:iss` and, unhashed, the previously-accepted implementation resolves unchanged and reads `env.identity.sub` as `undefined`, silently, with `acceptImplementation` declining to re-check it because the hash says nothing changed. Replay made the same hole worse: `replayInvocation`'s drift refusal is only as good as `fingerprintNode`'s coverage, so a declaration whose `scope` had widened since the recorded invocation passed the drift check untouched, resolved the very same pinned implementation, and replayed "successfully" with the newly-declared field simply absent from the replayed `identity`. The stated reason for deferring — "changing what's in the hash shifts every existing accepted hash" — turned out to be vacuous on inspection: no `implementations/` tree exists in this repo and no `<contract-hash>.ts` file lives anywhere outside a test's temp directory, so there were no accepted hashes to shift and the fix cost nothing. Scope is sorted and de-duplicated before hashing (order carries no meaning; a repeated scope is redundant but unambiguous), and an empty array hashes identically to no `scope` at all.

  **Still open: `examples`.** It stays out of the hash, deliberately, per `NodeFingerprint`'s own doc comment ("examples gate acceptance, they don't define the hash being accepted against"). The asymmetry with `scope` is the point — `examples` is a *verification* artifact, not behaviour — but the consequence is still real: adding an example to a node doesn't invalidate its accepted implementation, so an implementation can sit marked accepted while an example it was never run against sits right there in its contract. Leaving it unhashed weakens a gate rather than corrupting a result, which is why it didn't ride along with `scope`; what's undecided is whether that weakened gate is acceptable long-term, or whether acceptance should instead re-run examples against an already-accepted implementation without re-deriving its hash — a third option that keeps the hash meaning "the contract" while closing the hole.

- **`Log` is doing two jobs under one interface.** Surfaced building invocation records (docs/superpowers/specs/2026-09-23-invocation-records-and-replay.md §2): `Log.append` both records what a node actually emitted — provenance-carrying, an `InstanceEnvelope` attached — and stages inputs so an `allOf`-input node's readiness check has something to find (`invoke.ts`, and several tests, appending a payload with no invocation behind it at all). That second use is why `envelope` had to become optional rather than required: a staged input has nothing to attach. Making the parameter optional kept every existing caller working, but it means one interface is quietly standing in for two different kinds of entry. Not decided: whether staging deserves a mechanism of its own, separate from the Log, or whether a "staged" instance — envelope absent, by construction rather than by omission — is a legitimate kind of log entry in its own right. **Related, deliberately recorded alongside this rather than as its own item:** `runtime.ts`'s `tryFire` rebuilds an `allOf` node's input bag with its own `log.latest` loop, one call per declared edge, duplicating the read `membrane()`'s own `allOf` invoke already performs internally to resolve readiness (`membrane.ts`, `Log.latest`'s doc comment names the hazard this depends on — synchronous, same-tick reads with nothing appending to the Log in the gap). The real fix is for `membrane()` to return the resolved input bag alongside `result`/`envelope`, so the trace entry's `input` comes from that single read instead of a second, independently-performed one that could in principle drift from it. Deliberately deferred rather than done here: the hazard is dormant today (nothing makes `Log` async yet), and returning the resolved input would change `membrane()`'s return shape, which three tasks' worth of callers (`invoke.ts`, `runtime.ts`, and their tests) already consume. Recorded together with the "two jobs" question above because both become live the instant `InMemoryLog` is replaced by a real store — that's one decision (what `Log`/`membrane()`'s contract should actually be once reads and writes aren't free and synchronous), not two independent ones.

- **Should `membrane()` build the envelope before asserting input, so every attempted invocation is observable?** Surfaced deciding the envelope's optionality (docs/superpowers/specs/2026-09-23-invocation-records-and-replay.md §4). The envelope is built *after* the input assert, so a rejected input returns `Failed<In>` before any envelope exists — which is why the returned envelope is optional, with the rule "present iff `Fn` actually ran." That rule is clean and gives the trace a precise meaning: it records *invocations*, never attempts. The cost is observability, and it is larger than it first appears. A rejected input produces **no trace entry at all**, and its `Failed_*` log instance carries **no provenance** (`instanceEnvelope` returns `undefined` without an envelope) — leaving it shaped exactly like a *staged* input, which `Log.append`'s own doc comment says never happens for a real emitted instance. So two failures that look identical in the log (`{input, reason}` under the same synthesized edge) have opposite provenance depending on whether `Fn` ran: a thrown `Fn` gets a trace entry and a provenance-carrying instance, a rejected input gets neither. The only thing distinguishing them is the *absence* of provenance — a real signal, but an accidental one rather than a designed one. Replaying a run therefore reproduces its invocations and silently skips its rejections. Not decided: whether to build the envelope first (making it non-optional and every attempt observable, at the cost of changing error precedence — a bad `scope` declaration would surface ahead of a bad input, breaking existing tests — and running `hashNode` for inputs about to be rejected anyway), or to keep the current ordering and distinguish rejections some cheaper way, e.g. a marker on the `Failed_*` instance saying "rejected before invocation" that closes the looks-like-a-staged-input confusion without touching ordering. Current read is that observability probably does want the first option eventually; this pass was implemented correctly under the second, and the choice deserves its own decision rather than being folded into a branch about replay.

- **Declarations acceptance gate — required human sign-off on `declarations/`, exact loosening mechanism undecided.** `design-history.md` ("Acceptance gating, generalized one layer up") generalizes §10's existing accept-before-persist mechanism from implementations to declarations: a change to `.edge`/`.node`/`.topology` isn't accepted until a human signs off, independent of who drafted it — buildable today as required review on `declarations/**`, CODEOWNERS-shaped. Decided to ship this as a required gate rather than optional from the start (a constraint that's optional from day one never gets pressure-tested). Not designed: the loosening mechanism itself — who's allowed to be the accepting reviewer once a project has earned enough trust to relax it, whether that's a `.node`-file-shaped permission (§7's PDP shape) or a repo-level setting entirely outside weir's own contract, and whether the gate applies uniformly to all of `declarations/` or per-file/per-directory/per-edge individually.
