# The generator samples string length uniformly, so a generous `maxLength` makes acceptance enormous

Status: resolved (2026-10-01 — boundary lengths once each, ordinary lengths
otherwise; 108 MB to 4 MB).
Last grounded: 2026-10-01.

## The measurement

`weir accept` defaults to seed 42 and **100 generated cases** (`fuzz.ts`). For
`parcelCentroid`, whose input carries `boundaryJson` declared
`utf8, minLength: 2, maxLength: 2000000`:

```
boundaryJson length over 100 generated cases (declared maxLength 2000000)
  min 2  median 1,157,240  max 2,000,000
  total chars: 107,972,852
  JSON.parse succeeds on 0/100
```

**108 million characters** of random text, to reach a verdict the first case
already determined. The other two nodes with an opaque field are the same order:
`normalizeParcel` 101 MB, `resolveIdentity` 101 MB.

## Why it is a design question and not just slow

Three separate costs, and the third is the one that matters:

1. **Time and memory**, which is the obvious one and the least interesting.
2. **The fixture cannot be shipped.** The scaffold wants to hand an implementer the
   inputs the gate will use
   ([the deterministic scaffold](../superpowers/specs/2026-10-01-the-deterministic-scaffold.md)),
   so they learn *before* submitting that a field arrives as noise. 108 MB cannot
   be written into a workspace, so the scaffold ships a **report** instead — the
   shape, a warning, and four truncated samples. That is a worse artifact than the
   real inputs, and the only reason it is a report is this. (Still true after the
   fix below, though for a different reason: 4 MB rather than 108 MB, and almost
   all of it the two deliberate boundary cases.)
3. **Uniform length buys nothing.** The interesting lengths for a string field are
   `minLength`, `minLength + 1`, `maxLength - 1`, `maxLength`, and something short
   and ordinary. `generateNumericValue` already knows this — it emits boundary
   cases first and samples only afterwards. `generateStringValue` samples the
   *length* uniformly, so 95 of 100 cases are a megabyte of noise that tests
   exactly what a 20-character string would have tested.

## RESOLVED the same day

`generateStringValue` now emits `minLength`, `minLength + 1`, `maxLength - 1` and
`maxLength` **once each** — deduplicated and clamped — and draws every remaining
case from `[minLength, min(maxLength, minLength + 64)]`. The span matches the
`maxLength` a field gets when it declares none, so a field with no declared bound
behaves exactly as it did before the split existed.

Measured on the same corpus, at the same seed and count:

| node | before | after |
|---|---|---|
| `parcelCentroid` | 108,024,291 B | 4,033,864 B |
| `normalizeParcel` | 100,793,365 B | 4,010,255 B |
| `resolveIdentity` | 101,048,163 B | 4,059,823 B |
| `routeCounty` | 5,340 B | 5,286 B |

`boundaryJson` lengths went from `min 2 / median 1,157,240 / max 2,000,000` to
`min 2 / median 41 / max 2,000,000`. **27× less work, with both ends of the declared
bound still reached**, because a declaration promising to carry 2 MB should have
something carry 2 MB. The 4 MB that remains is almost entirely those two deliberate
cases.

This also settles the first sub-question below: `maxLength` is generated **once**
per batch rather than in the tail of a uniform distribution.

### What it gives up, knowingly

The range of lengths *between* the boundaries and the ordinary span is no longer
sampled. A bug reachable only by a 600,000-character string, which neither 2,000,000
nor 66 provokes, is not reachable from here. That is the trade, and it was taken
rather than discovered.

### What the build found

A test of mine passed by luck. The boundary assertion used a field declared
`minLength: 2, maxLength: 4` and still passed under a break that removed two of the
four boundary lengths — because with a 3-wide range the *ordinary* random draw
reaches the missing boundary by chance. Rewritten against a field whose upper
boundaries (99, 100) sit above the ordinary span, so only the boundary path can
produce them. Both breaks now redden it.

That is the fifth test this day whose own break-proof showed it measuring less than
its name claimed.

## What stays open under it

- **Whether this fixes a cause or a symptom.** Every field this bit holds
  serialized data in a `utf8`, which is friction #1. If the geometry were declared
  structurally, no field would carry a 2,000,000 bound and the question would not
  arise. The generator is better either way, but it is not the fix for the thing
  underneath.
- **Whether the gate should budget total generated bytes**, the way the host
  budgets a run. A different mechanism from better sampling, and it interacts
  badly with reproducibility: a cap that truncates a sequence means the seed no
  longer determines the cases. Not needed now that a batch is 4 MB rather than
  108 MB, which is why it was not built.
- **Whether the scaffold can now ship the real inputs** rather than a report
  ([the deterministic scaffold](../superpowers/specs/2026-10-01-the-deterministic-scaffold.md)).
  4 MB is three orders of magnitude better and still too much random noise to write
  into a git-tracked workspace, and almost all of it is the two deliberate boundary
  cases. Shipping the ordinary cases and *describing* the boundary ones would fit,
  at the cost of a fixture that is no longer exactly what the gate runs — which is
  the property that made the fixture worth having.
