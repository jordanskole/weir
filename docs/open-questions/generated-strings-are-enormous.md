# The generator samples string length uniformly, so a generous `maxLength` makes acceptance enormous

Status: open.
Last grounded: 2026-10-01 — measured on blue-ribbon's `parcelCentroid` at the
gate's real settings.

## The measurement

`weir accept` defaults to seed 42 and **100 generated cases** (`fuzz.ts`). For
`parcelCentroid`, whose input carries `boundaryJson` declared
`utf8, minLength: 2, maxLength: 2000000`:

```
boundaryJson length over 100 generated cases (declared maxLength 2000000)
  min 2  median 1,157,240  max 2,000,000
  total chars: 107,972,852
  JSON.parse succeeds on 0/100
```

**108 million characters** of random text, to reach a verdict the first case
already determined. The other two nodes with an opaque field are the same order:
`normalizeParcel` 101 MB, `resolveIdentity` 101 MB.

## Why it is a design question and not just slow

Three separate costs, and the third is the one that matters:

1. **Time and memory**, which is the obvious one and the least interesting.
2. **The fixture cannot be shipped.** The scaffold wants to hand an implementer the
   inputs the gate will use
   ([the deterministic scaffold](../superpowers/specs/2026-10-01-the-deterministic-scaffold.md)),
   so they learn *before* submitting that a field arrives as noise. 108 MB cannot
   be written into a workspace, so the scaffold ships a **report** instead — the
   shape, a warning, and four truncated samples. That is a worse artifact than the
   real inputs, and the only reason it is a report is this.
3. **Uniform length buys nothing.** The interesting lengths for a string field are
   `minLength`, `minLength + 1`, `maxLength - 1`, `maxLength`, and something short
   and ordinary. `generateNumericValue` already knows this — it emits boundary
   cases first and samples only afterwards. `generateStringValue` samples the
   *length* uniformly, so 95 of 100 cases are a megabyte of noise that tests
   exactly what a 20-character string would have tested.

## The shape of a fix

Mirror what the numeric generator already does: boundary lengths first, then short
samples, with the full `maxLength` appearing **once** rather than in the tail of a
uniform distribution. Same coverage, a thousandth of the bytes.

Undecided:

- **Whether `maxLength` should be generated at all, every run.** Once per run is
  defensible; 50 times is not. But a field whose bound is 2,000,000 arguably wants
  that bound exercised, since a real 2 MB payload is what the declaration promises
  to carry.
- **Whether this interacts with the opaque-field problem or merely co-occurs with
  it.** Every field this bites is a field holding serialized data as `utf8`, which
  is friction #1. If the geometry were declared structurally, no field would carry
  a 2 MB bound and this question might not arise — so fixing the generator could be
  treating a symptom.
- **Whether the gate should cap total generated bytes** as a budget, the way the
  host budgets a run. That is a different mechanism from better sampling and would
  interact with reproducibility: a cap that truncates a sequence makes the seed no
  longer determine the cases.
