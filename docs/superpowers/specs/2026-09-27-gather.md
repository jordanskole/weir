# `gather`: the dual of spread

Status: implemented.

## Motivation

`spread` gave weir data-driven fan-out: one alert becomes N entities, each taking its own treatment with its own lineage. The dual has no expression at all. Raised 2026-09-27 by the outside reader who wrote the original `soc-triage` sketch, reading the committed example:

> One alert → N entities → independent work per entity → rejoin each entity's branches. It does **not** do: N entity assessments → one alert assessment. That's the scatter/gather operation a real SOC triage workflow immediately wants.

`examples/soc-triage` ends with N `Assessment` instances and nothing that can say anything about the alert as a whole. That is not a missing convenience; it is half of an operation.

Named before being built (design-history.md, "`gather` is `sequence`"): gather is `sequence : t (f a) → f (t a)`, and spread + per-element subgraph + gather is `traverse`. Two consequences of that naming are load-bearing below — the failure policy (§4) and the empty case (§5) — and both would otherwise have been decided by taste.

## 1. What makes it hard, and what makes it tractable

Gather is a join, but not the one weir has. An `allOf` node's cardinality is **statically known**: the declaration lists the edges, so "am I complete" is answerable from the contract. A gather's cardinality is **decided at runtime** by the spread that produced the elements, so completeness cannot come from the declaration.

The first framing of this (open-questions.md) concluded it needed "a lineage-scoped barrier the pulse loop has no notion of", which is true and made it sound much worse than it is.

**The collection token records the count.** `spread` logs the collection it was given (`Many_Entity`) alongside the element instances it materialized — kept so a vectorized consumer stays reachable (2026-09-26-spread-materializes-elements.md §1). Every descendant reaches it by ordinary lineage:

```
Assessment ← EntityEvidence ← IdentityContext ← Entity ← Many_Entity
```

So the barrier has a **known target**: fire when N instances of the gathered edge descend from this collection, where N is that collection's size. No global quiescence, no new notion of doneness — a count, and a lineage walk that already exists.

That the collection is available at all is a consequence of a decision taken for an unrelated reason. Worth noting as evidence for keeping it rather than treating it as dead weight.

## 2. Declaration

A new input kind, alongside `single` and `allOf`:

```yaml
# declarations/summarizeAlert.node
label: Summarize Alert
input:
  gather: Assessment
output: AlertAssessment
```

`gather: X` says: *collect every `X` descended from one spread, and fire once with the collection.* The payload is a keyed collection, the same shape a `many` output produces — keyed by the gathered edge's own `index`, per design-history.md's "`many` is a collection, keyed by index, not an array".

**Which spread it gathers from is not declared, and must not be.** It is the collection ancestor shared by the candidates — the same nearest-common-ancestor question `joinRows` already answers, asked of a collection token instead of an ordinary instance. Declaring it would make a node's contract depend on the topology above it, which is the property `soc-triage` demonstrates weir does *not* have: `investigateIdentity` says `Entity → IdentityContext` and knows nothing about being one of N.

## 3. Readiness

For a node declaring `gather: X`, in one pulse:

1. Take the unconsumed `X` candidates on declared arcs — `eligibleForEdge`, unchanged.
2. Group them by the nearest collection ancestor in their lineage: the highest-`seq` ancestor logged under a `Many_*` edge name.
3. A group is **complete** when its size equals that collection's entry count.
4. Fire once per complete group, consuming the whole group.

An incomplete group yields no candidate and is retried next pulse, which is how every readiness rule here already behaves — the same reason an `allOf` group that never completes reaches quiescence rather than spinning.

## 4. Failure: all-or-nothing, because that is what `sequence` means

If one element's subgraph produces `Failed<In>` instead of the gathered edge, the count never reaches N and the group never completes. Left there, the gather hangs until the budget stops the run — a silent stall, which is this repo's worst failure mode.

`sequence`'s signature settles it: `t (f a) → f (t a)` means a single failure makes the whole result a failure. **Resolved: a gather whose group can no longer complete fails as a whole**, emitting `Failed<In>` so the topology may route it like any other failure.

**Not under "the usual synthesized edge", which this section originally said and which is wrong.** Corrected during the build. `Failed_X` is `{ input: X, reason }` — one instance of `X`. A gather's `Failed<In>` carries the *collection* it was holding when the group died, and logging that under `Failed_X` would put a collection in a field declared to hold one entity: a payload nothing would catch, since `Log.append` takes an edge *name* rather than a definition. A gather of `X` and an ordinary node consuming `X` fail differently, so they route differently — `Failed_Many_X`, synthesized per gathered edge the way `Failed_A_B` is synthesized per declared `allOf` combo.

The new edge is expressible for a reason worth naming: a bare keyed collection cannot be an edge payload (which is why `Many_X` is a reserved log name rather than a declared edge), but a *field* may be `many` — so `{ input: many X, reason }` is an ordinary edge. The constraint that forced the reserved name works in weir's favour one layer down.

"Can no longer complete" is decidable without waiting: a group is dead when, for some element of the collection, a `Failed_*` instance descends from it. That is the same lineage walk step (2) already performs, asked of the failure edges.

**Corrected 2026-09-27: that rule closes one of the two ways to hang, and this section claimed both.** An element whose subgraph produces a `Failed_*` is caught. An element whose subgraph simply **ends** — a `oneOf` routing it to a branch nothing consumes, which is an ordinary "not applicable" decision rather than a failure — produces no failure to find, so the count never reaches N, no group ever dies, and the gather hangs to quiescence in silence. Exactly the outcome the paragraph above says it prevents.

It is not fixable from inside gather. There is no lineage evidence that an element is *finished* rather than *slow*; "nothing more is coming" is a property of the whole run reaching quiescence, which a readiness rule evaluated mid-pulse cannot see. The safeguard belongs one level up, where quiescence is observable: [quiescence is not success](2026-09-27-quiescence-is-not-success.md). Found by a reader given only the docs, proposing a general end-of-run check and not knowing it landed on a hole in this section.

Recorded rather than deferred because the alternative — gather what succeeded — is a real option that some workflows want, and choosing it should be a declaration the author makes, not a default they inherit. Not built here.

## 5. The empty collection

`traverse` over an empty collection yields an empty collection. A spread of zero elements must therefore let its gather fire **immediately, with an empty collection** — never hang waiting for the first of zero things.

This is the case most likely to be missed, and it is not hypothetical: `extractEntities` returning no entities is an ordinary outcome for an alert that names nothing recognizable. Named here so the test exists.

## 6. What this does not need

**`input: many X`.** Gather produces a collection token and fires *its own* node with it, so the consumer is the gather node itself. The vectorized consumer stays a separate, still-unbuilt thing: it consumes a collection someone *already produced*, where gather *builds* one. Sequencing them the other way round — vectorized input first — would not have helped.

## Testing

Break-proofs required for each, and recorded in each test's own comment along with what the break-proof showed. `tsconfig.json` excludes `src/**/*.test.ts`, so test files are never typechecked.

1. A `gather: X` node fires **once** with a collection of every `X` descended from one spread, keyed by each element's own index. *Built* (`gather.test.ts`). Its break-proof is the keying and the causation, **not** completeness: both elements reach the gathered edge in the same pulse there, so "wait for the group" and "fire on whatever is there" are indistinguishable. The comment first claimed completeness anyway — the vacuous-test pattern, written into the test meant to avoid it.
2. It does **not** fire while the group is incomplete, and does fire on the pulse after the last member arrives. Assert both: a rule that fires early would pass a final-state check. *Built*, with a deliberately asymmetric arm — one element takes an extra hop — which is what makes it non-vacuous, and is there because a symmetric fixture is exactly how `manuscript-review`'s join test once passed with the join disabled.
3. Two spreads in one run gather separately. *Built*, as a nested spread (`Seed → many Batch → many Item`), which is the only fixture that produces two barriers in one run. It is the one test that proves grouping is by the **nearest** collection ancestor rather than any.
4. An empty collection gathers immediately to an empty collection (§5). *Built*, and it catches two distinct breaks nothing else does: requiring a non-empty group, and consuming only the members rather than the barrier token (an empty group has no members, so without consuming the token it re-fires every pulse to `maxPulses`).
5. A group with a failed element fails as a whole, routing to `Failed_Many_X`, rather than hanging until the budget (§4). *Built*, plus its precedence sibling: a group that **completed** fires as a success even though a side branch under the same barrier had already failed. That sibling needs the asymmetric arm too — with the side branch on the fast path, its failure lands in the same pulse the group completes, is invisible in that pulse's snapshot, and the test passes under any precedence rule.
6. `examples/soc-triage` gains `summarizeAlert`, and the run produces exactly one `AlertAssessment` naming both entities. *Built*. It is the only test that exercises the `gather:` parse path, Rule C, and the real synthesized `Failed_Many_Assessment` end to end — `gather.test.ts` builds its `Program`s by hand, so the two would otherwise drift. It catches neither readiness rule, for the reason #1 gives, and says so.

Three more the build added, which the spec had not anticipated:

7. **Rule C**: a gather with no spread anywhere upstream is rejected at elaboration. `assertWiringTypes` grew a third rule for it. Rule B does not catch it — something *does* produce `X`, so the node looks ready — and without it the program elaborates clean, `weir check` reports ✓, and the run reaches quiescence having silently never fired the gather. That is the failure mode this repo rates worst, so the one thing about a gather decidable from the topology is decided there.
8. **`input: gather` requires an index** on the gathered edge, the same requirement `output: many` carries, checked at elaboration rather than left to the membrane.
9. **The membrane checks the collection's keys**, not only its entries — each entry must sit under the key its own `index` names, as `assertManyOutput` and `assertPayload`'s `many`-field branch both already check. The runtime keys it correctly by construction, so the only caller this catches is a direct one (`invokeWithInput`, a test) — which is exactly the caller with no other check on it.

### The one test in the original list that could not be built

**A property relating the gather's output to every element** was listed, on the reasoning that a fan-in property naming a single input is the false green fixed in `2d9ba58`. It is **not expressible**: `property.ts` resolves dotted paths over fixed keys and has no quantifier, and a gathered collection's keys are runtime data. There is no honest weaker version — a property over `input` as a whole compares against the collection object — so none was written, and the gap is recorded in `open-questions.md` rather than papered over with a property that passes because it checks nothing.

What does cover the gather node instead, stated exactly: its **examples** (concrete keys are known in an example, and `summarizeAlert` declares both the two-entity case and the empty one) and its **generated cases** (`generateInputCases` varies a gather's collection size with the case index so the empty collection is among them — break-proofed by fixing the size at one, which reddens the `realOutputs` count). What the generated cases cannot do is *reject* an implementation that fails on the empty collection: a generated case coming back `Failed<In>` is a legitimate outcome, so throwing on the empty collection is indistinguishable from declining it. The declared example is what pins that behaviour.

## Explicitly out of scope

- **`input: many X`**, the vectorized consumer (§6).
- **Gather-what-succeeded** as a declarable policy (§4).
- **Nested gathers.** A gather of a gather is `join`'s territory — flattening `Many (Many X)` — and is a different operation with different laws (design-history.md, "`gather` is `sequence`").
- **Cross-correlation gathering.** Nothing joins across runs, by design.
