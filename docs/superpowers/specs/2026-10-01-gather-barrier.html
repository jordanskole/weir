The barrier and the collection are two different things

A spread fans out over parcels; some succeed and some fail. Two single-input gather nodes close on one shared barrier — so the branch lives in the topology, not inside a node. The open question is only what to call the keyword that widens what closes it.

Four names for one keyword

Same topology in every case. Only summarizeCorridor's input block changes — and whatever it is called, it declares what closes the barrier, never what the node receives.

partition:

input:
  partition:
    - Card
    - Failed_Card
  take: Card
# own input kind
  • Names the operation
  • Needs a second key (take:) to say which edge this node gets
  • Two keys where one would do

Was my favourite until the node stopped receiving both edges. Now it names something the node no longer does.

accepting:

input:
  gather: Card
  accepting:
    - Failed_Card
# one gathered edge,
# widened barrier
  • One gathered edge stays obvious
  • Zero churn on existing gathers
  • Reads as "tolerating", which is odd for a legitimate alternative

Survives the correction intact, because it always described the barrier rather than the payload. Runner-up.

settled:

input:
  gather: Card
  settled:
    - Failed_Card
# all vs allSettled
  • Precise analogy: all → allSettled
  • One word carries the whole semantics
  • Borrowed from one host language; OCaml comes after v1

Chosen. The concept is not JavaScript's — only the spelling is. “This element has settled” is true of a failure and of a legitimate absence alike.

or:

input:
  gather: Card
  or:
    - Failed_Card
# per-element
# alternation
  • Shortest; alternation is the semantics
  • Reads the same for failures and alternatives
  • or is already a property operator and echoes oneOf

Three meanings for one word in one declaration language is one too many.
