# Design history

This is a record of how weir's design arrived at what the readme describes. It's reconstructed from a rubber-duck conversation (2026-08-17 to 2026-08-18) and kept so decisions are traceable to the problem that forced them, not just stated as conclusions.

## The seed

Starting frustration: foundational principles — Rich Hickey's "Simple Made Easy," SOLID, data-centric/schema-first design — don't show up naturally in code without constant discipline. Working in PHP made this sharper: classes tend to violate single responsibility just by existing as classes, and `this` is inherently a smell (hidden, mutable, ambient state).

The seed idea: what if the framework is just **edges** (pure data — the shape of what crosses the wire) and **nodes** (pure transformers — input edge to output edge)? Side effects live in middleware. Nothing polls; everything is evented.

This is flow-based programming territory — Morrison's FBP, Erlang/OTP, core.async + transducers, Kafka Streams, Node-RED all land near here, and each hit the same walls this history works through.

## Splitting edge into schema vs. wiring

"Edge = shape of the data" and "edge = the wire between two nodes" turned out to be two different concepts fused together. A schema is a value — inert, comparable, versionable. A connection is topology — which output feeds which input, with cardinality and routing. Fusing them meant the same schema couldn't be wired differently between two node pairs, and topology couldn't be validated or diffed as its own thing.

Resolution: schemas are data; edges (as wiring) are `(from_node, output_port, to_node, input_port, schema_ref)`. Topology becomes data you can validate, diff, and render.

## Prior art: bankql already proves the edge half

Partway through, it became clear that a sibling project — [bankql](../../bankql) — is already running the "edges" half of this design in production, just without the name. Verified against the actual source (`packages/schema/src/`):

- `defineField` / `defineDataset` (`define.ts`) are identity functions that exist purely to pin TypeScript inference on a rich `FieldDef` / `DatasetDef` shape (`types.ts`) — label, description, measure, format, unit, enumValues, a typed `relation` to another dataset, and a `sourceKey` mapping back to the raw source column. That `DatasetDef` is, functionally, an edge definition.
- One `DatasetDef` already drives multiple downstream artifacts from a single source of truth (`index.ts`): DuckDB `CREATE TABLE` DDL (`duckdb.ts`), an LLM-facing description/system prompt (`llm.ts`), agent tool specs (`agent/queryDataTool.ts`), and the foreign-key graph via each field's `relation` (`relations.ts`). That's the "edges are the tables" claim from this design, already shipped rather than proposed.
- `hashDataset()` (`hash.ts`) fingerprints only the *structural* fields of a dataset — `type`, `measure`, `format`, `enumValues`, `relation` — deliberately excluding `description`, `unit`, `sourceKey`, `blobPath`, `isDeprecated`. That's exactly the identity-bearing-vs-cosmetic split an edge's `schema_ref` needs, and it comes with a rule worth transferring directly: if a description change busts a cache, the fingerprint is wrong — fix the fingerprint, don't work around it.

The transferable conclusion: every edge instance in weir's log should carry the schema hash it was written under, the same way bankql's `assertDatasetHash` catches drift at startup/test time. Replay compares the recorded hash against the current definition and either migrates through a declared rule or refuses — the schema-evolution problem doesn't need to be invented from scratch, bankql already has a working answer to steal.

## Middleware was where purity leaked

If a node is `input → output` but middleware does the actual I/O, the node was never pure — the impurity just moved behind a decorator, and the testability purity was supposed to buy got lost.

Resolution: **effects are data.** A node returns a description of what it wants (`{fetch, url}`, `{write, table, row}`); the runtime interprets it and feeds the result back in as another edge.

## The envelope

Persistence and cross-cutting concerns (tracing, dedupe, retry policy) still needed somewhere to live without becoming middleware. The fix: every edge instance is `{envelope, payload}` — envelope carries `id`, `correlation_id`, `causation_id`, `timestamp`, step index. The payload is what the schema describes.

This is CloudEvents / Kafka headers / event-sourcing's standard shape. Cross-cutting concerns become **readers of the envelope**, not wrappers around the node — nothing decorates anything.

Open call, resolved as opt-in: does a node's `Fn` see the envelope? Default no — `(payload) => ...` stays context-free. A node that needs identity (routers, dedupers) opts in with an explicit second argument, `(payload, env)`, so context-dependence is visible in the signature rather than implicit.

## Nominal edges: a wrong turn, corrected within the hour

The `birthday: Person -> Person` example exposed a real problem: if routing follows type identity and there's only one `Person` type, `birthday`'s output is its own input. It feeds itself; everyone ages forever. Add `capitalize: Person -> Person` and now there's a two-cycle with undefined ordering on top of the self-loop.

**First proposed fix (rejected): make edges nominal.** Split shape from identity — `type Person {...}`, then distinct named edges `edge PersonReceived : Person` and `edge PersonAged : Person`, with `node birthday: PersonReceived -> PersonAged`. No self-loop, wiring is intentional, and `PersonReceived`/`PersonValidated` stay distinct even when byte-identical, avoiding the accidental-fan-in failure mode of content-based pub-sub (every node emitting `Order` implicitly feeding every node consuming `Order`).

**Why it was rejected almost immediately:** the premise — "routing follows type identity" — was never actually true. Wiring in this design is *always* declared explicitly, node by node; nothing is auto-derived from matching shapes. Once that's true, the self-loop was never real: `birthday`'s declaration doesn't cause it to feed itself, it just describes its interface. And nominal edges would have broken the thing that motivated the whole design in the first place — `birthday|birthday|birthday` (increment age three times) only composes *because* the ends match structurally. Nominal-by-default kills that example.

**The actual resolution: structural by default, wiring always explicit.** Edge compatibility is by shape. Nominal naming (`PersonReceived` vs. `PersonValidated`) survives only as an opt-in tool for **refinement** — reached for deliberately when a specific decision needs to be visible in the topology (see "Fan-out is three different things" and "Failure as an edge" below), not as a blanket rule for every edge in the system.

**The consequence this uncovered:** `birthday|birthday|birthday` differing from a single `birthday` is the entire point of composing nodes — measuring a node against idempotence was the wrong instinct. But it breaks naive log replay: three invocations of the same node, same name, same shape — if the log records node name plus payload, replay can't distinguish position two from position three. Fixed by giving the log **positional identity**: the [envelope](#the-envelope)'s per-invocation id/step index, not the edge type, is what disambiguates repeated invocations. This is also where the envelope's id was pinned down as being allowed to just be a timestamp/UUIDv7 — created per invocation, describing that run, never part of the data itself.

## Fan-out is three different things

Node-RED's failure mode was conflating three distinct behaviors under "multiple outputs":

- `one of {A, B}` — exactly one fires, chosen by value. Branching, a coproduct.
- `all of {A, B}` — every one fires, distinct edges. True fission, a product.
- `many A` — N instances of the *same* edge. Cardinality, a list functor.

`validate: PersonReceived -> one of {PersonValid, PersonInvalid}` and `place_order: OrderPlaced -> all of {InvoiceRequested, InventoryReserved}` are wildly different control flow and need to be declared as such, not both just "outputs."

## Subgraphs are nodes

A subgraph with exactly one input edge and one output edge is indistinguishable from a node — same signature, same contract. So graphs nest, and "node" and "graph" are the same kind of thing at every level (the box-inside-a-box picture from string diagrams). The system is self-similar rather than one sprawling flat network.

Deliberately declined: naming the nesting levels ("galaxy," etc.). Naming them would break the property that makes them useful — a node has to stay transparently swappable for a subgraph, the way a directory full of directories is still just a directory (Composite pattern: leaf and composite share one interface so callers can't tell them apart).

The one distinction that does carry information points down, not up: does this bottom out in host code, or in more graph? That's **leaf vs. composite** — one word for the general thing (node), one qualifier for the floor (primitive).

This also creates a log granularity decision: a composite node's run produces internal edge instances — record them (transparent: full causal trace, large logs) or don't (opaque: smaller logs, can't replay the inside).

## Failure as an edge

If a node's `Fn` throws, that can be bolted on the side (try/catch, retry policy, dead-letter queue as separate mechanisms) — or every node's real output signature can be `one of {…successes, Failed}`, making failure just another wire that has to be terminated somewhere.

Resolution: the second. A retry becomes a node that consumes `Failed` and emits the original edge; a dead letter is a node with no output; the type checker flags unhandled failure paths. It also keeps the log honest — a failure is an edge instance like any other, and replay sees it. Cost: every node gains an output edge and topologies get busier. Judged worth it, and flagged as nearly impossible to retrofit later — this had to be decided early.

## Persistence and execution model

- The log of edge instances *is* the persistence layer.
- State is a fold over that log.
- Replay requires the fold to be deterministic.
- The framework is "composition, not a program": you elaborate the topology, then execute it — a query-planner-like split between declaration and execution.

## Generics: elaboration monomorphizes

Flagged as the one item that couldn't be deferred: `retry: T → T`, `log: T → T`, `batch: T → many T` need a way to be written once but still emit concrete, fully-typed edges into the netlist — every edge instance in the log needs a named concrete type, so a live type variable can't survive to runtime. Protobuf has spent fifteen years not solving this.

Resolution: **elaboration monomorphizes.** `log<Parrot>` is written once, polymorphically, but expands at elaboration time into a concrete `log_Parrot: Parrot → Parrot` node in the netlist. The type variable lives in phase one (authoring) and is gone before anything executes — same move Rust makes with generics, and Verilog with generate blocks. Polymorphic authoring, concrete artifact.

This makes a **node declaration** and a **node** different things: `feed: Animal<T> → Animal<T>` is a template; the netlist contains `feed_Parrot: Animal<Parrot> → Animal<Parrot>`. Templates live in source, instances live in the topology, elaboration is the boundary. If a type variable can ever appear in the *emitted* netlist, polymorphism has leaked into the runtime and a unifier is needed after all — worth being strict about in the serialization format.

Two costs this creates, taken deliberately:
- **Netlist size** — `log` across forty edge types is forty nodes. Fine for analysis, but the topology you query is bigger than the topology you wrote.
- **Authoring ergonomics** — if the elaborator isn't pleasant to use, the forty declarations get hand-written instead, and the elaborator goes from "nice separation of concerns" to load-bearing.

Where the type parameter lives also moved: not on the node, but instantiated into a concrete edge before anything runs (e.g. `Animal<Parrot>` is a real named edge in the netlist) — the same opt-in-naming move as refinement edges above (`PersonReceived` vs. `PersonAged`), just applied to generic instantiation instead of a branching decision: give the concrete thing its own identity rather than letting it collapse into its structural shape. Variance was decided deliberately as **invariant**: `Animal<Parrot>` is not assignable where `Animal<Whale>` or `Animal<Animal>` is expected. Each instantiation is its own edge, full stop — covariance is where generics grow soundness holes and the type checker stops being a weekend project. Can be relaxed later; can't be tightened later. Bounded polymorphism (`T extends {legs: uint8}`) is fine and brings structural matching back in at the bound — checking whether a type satisfies the bound is structural, same as everywhere else — without making distinct instantiations assignable to each other.

## Permission gates, distinct from type gates

Two different checks turned out to be needed at a node boundary, and worth keeping distinct rather than merging:

- **Type gate** — you can't call `charge_card` without holding an `AuthorizedPayment`. Structural, no runtime check, about data provenance. (See "The weir in dynamic topologies" below.)
- **Permission gate** — you can't *traverse* `charge_card` unless the calling principal holds the grant. Runtime, checked against the envelope, about actor authority.

This works precisely because the node's `Fn` can't see the envelope: the runtime checks the permission at the node boundary, and the function stays pure and identity-blind. The check happens at the weir, not inside the fish.

**Exit permissions** are the more interesting half — information-flow control over who may *receive* an edge, not just who may traverse a node. A node that widens `Transaction` to `PublicTransaction` is a declassifier, and exit permissions are where that gets declared. This matters more here than in most systems because the log holds everything — every edge instance ever produced, including the pre-declassification ones — so read authorization on the log is a real, self-inflicted problem, and exit permissions are the natural place to answer it.

Discipline to hold: a node declares *which permission is required* (a name) and delegates the actual check to a PDP (policy decision point) — same move as delegating to Cerbos elsewhere in this design. The moment a node declaration contains permission logic itself, the purity that made this tractable is gone.

## Encryption keys: scope to reader, not writer

A related question — should each node get its own key — was rejected: keying by producer answers the wrong question. If node A encrypts with `key_A`, every downstream consumer of A's output needs `key_A`, so keys propagate along the edges until everyone holds everything — N keys, zero isolation.

Keys should scope to **who may read**, composed along three axes:
- **Per data subject** — the erasure answer. Dropping one person's key makes their fields inert everywhere in the log at once, without rewriting an append-only store.
- **Per zone** — client holds the vault, server structurally cannot decrypt (already the shape of a prior design elsewhere; the zone annotation just makes it explicit).
- **Per classification** — PII vs. financial vs. public, so a compromise is bounded to one class.

Composed as a derived key per `(subject, classification)`, wrapped by a zone key — standard envelope encryption. Worth knowing before the log format is designed, since retrofitting field-instance-granularity encryption is awkward.

For v1, explicitly: **don't build any of this.** Label fields, generate the redact/rehydrate pair from the labels, and put key resolution behind an interface with a hardcoded implementation — the same discipline as delegating authorization to Cerbos. The framework declares which key class a field needs; something else answers where the key comes from. Key management is a KMS-shaped problem that will eat the project if tackled prematurely.

## The pivot: this is a substrate for agent-written code

The framing that reframed several "costly" decisions as the actual point: the human doesn't write node bodies. The human defines edges, defines nodes (as typed contracts), and composes the graph. An agent writes the implementation inside each node. That changes what the design is optimizing for:

- **Total contracts** stop being a burden and become the entire prompt — input edge, output edge, nothing else, no ambiguity for the agent to resolve wrong.
- **Purity** means generated code is verifiable locally, without mocking a world.
- **Effects-as-data** means an agent structurally cannot reach outside its declared type — the blast radius of a bad node is bounded by its type, not by what the code happens to do.
- **No `this`** means no hidden state an agent couldn't see — which is where most agent-generated bugs actually originate.
- **The log** turns every historical run into a regression suite: regenerate a node, replay, diff.
- A further, previously unnamed property: **the implementation becomes disposable.** If a node is pure and fully specified by its types, its body is derived, not authored. The durable artifact is the topology plus edge definitions; the code is a build output you can throw away and regenerate.

The corollary: review, not generation, is the actual bottleneck for agent-written code. Reading a 400-line service to judge correctness doesn't scale; reading a pure function with a fully specified type, checked against recorded inputs, does. The design cuts the work at the seam where agents are strong (small, plausible, locally-typed functions) and keeps the part where they're weak (deciding what should exist — the topology).

Also noted directly: the mapping to tool-calling is real without having been designed for it — nodes are tools, edges are their schemas, a node's prose description is the tool description.

## The weir, formalized: cut vertices are computable

The salmon-run intuition behind the project's name already had names in adjacent fields, and naming it precisely is what made it mechanical rather than aspirational. Architecture calls it the **narrow waist** (IP is the narrow waist of the internet — validate once at the pinch, everything above and below inherits the guarantee). Security calls it **complete mediation** — a checkpoint only works if there's no path around it. But the graph-theoretic name is the one that matters, because it's *computable*: a **cut vertex** (articulation point) is a node whose removal disconnects the graph — every path from A to B is forced through it.

Because the topology is data (the elaboration decision above), cut vertices aren't a property you argue for in review — they're a query. Run the cut-vertex algorithm over the netlist and get back the complete list of pinch points, plus, just as usefully, the list of places flow *bypasses* one — "this invariant is supposed to be enforced at node V, and here are the three paths that reach the downstream region without touching V." That bypass-detection is the complete-mediation check, computed instead of read off a diagram by a reviewer.

This also folds topology validation into a mechanism that already existed rather than requiring a new one: because a subgraph with one input and one output edge *is* a node (see "Subgraphs are nodes" above), a property test at a subgraph's boundary is already a topology test. Validating a whole topology isn't a new capability — it's the same node-level property-test mechanism, one level up.

## System functions: topology and log as queryable data

`plan(from: Edge, to: Edge) -> [Topology]` — a function to find routes between two edges — turned out to be a **planner**, and the SQL analogy runs deeper than intended: it's type-directed search (the same shape as Hoogle searching Haskell by signature, or a query optimizer enumerating legal plans and ranking by cost). And because the planner is itself a node, it lives inside the graph the same way `information_schema` lives inside the database it describes, rather than as an external tool bolted on.

The ranking metadata falls out of decisions already made, for free:
- **Lossy or not** — does a candidate path contain a converging triangle (erasure)? The triangle vocabulary from "Refinement is how decisions survive" becomes planner output.
- **Pure or effectful** — does the path emit effect descriptions an agent should know about before choosing it (e.g. "this route charges a card")?
- **Depth, fan-out, zone/process-boundary crossings.**
- **Observed success/failure rate, read straight from the log.** This is the real prize: a SQL query planner ranks using table statistics from `ANALYZE`; this planner ranks candidate topologies using *actual recorded outcomes* from real runs, because every execution already writes typed, causal edge instances to the log. Nobody else can do this ranking, because nobody else has a typed causal record of every execution to rank from.

This generalizes to a whole `sys` namespace — system tables/functions analogous to `information_schema`: what edges exist, what refines what, what's unreachable or orphaned, which nodes are cut vertices, which paths bypass a given node, and the planner itself. Ontology and topology reviews (see "Verification" risk ordering) get partial mechanical support from this namespace — cut-vertex analysis and reachability/orphan detection run automatically over the netlist at elaboration time — where node-level correctness still relies on tests and review of the types.

## The weir in dynamic topologies

A late distinction, connecting the framework name back to its purpose: everything above assumes a topology fixed at elaboration time. But applications built by/for agents increasingly look like **elastic, dynamic topologies** — an agent choosing the next node at runtime rather than a human fixing the graph in advance. That's a different mode: static graph analysis (cut vertices, reachability, complete mediation) doesn't exist for a topology that isn't fixed until runtime.

The resolution was not to treat the weir as DX-only (a nice-to-have for the human author) that stops mattering once routing goes dynamic. It matters *more*: the chokepoint relocates from the graph to the type. `charge_card: AuthorizedPayment → Receipt` means an agent cannot call `charge_card` without holding an `AuthorizedPayment` — and only `authorize` mints one. You lose static proof of the chokepoint, but keep automatic runtime enforcement, because the enforcement lives in the refinement types rather than in someone remembering to check a policy.

Precedent: a query planner picks a different plan every execution, cost-based, and nobody worries — relational algebra guarantees the *result* is correct regardless of which plan the optimizer picks. The target for agent-routed weir topologies is the same property: any route the agent takes is correct by construction, because an incorrect route is structurally impossible to construct, not just discouraged.

This means the decisions made early for reasons that read as pure DX — nominal refinement on branching nodes, total contracts, no row polymorphism — turn out to matter more, not less, once the topology is chosen by a model at runtime instead of declared by a human ahead of time.

## Relation/Cardinality: ontology, not a wiring bypass

Raised while reading `types.ts` during node-declarations work: `FieldDef.relation` (`{edge, field, cardinality}`, ported wholesale from bankql — see "Prior art" above) looked at first glance like it might let one edge join to another directly, bypassing nodes — which would break "wiring is always declared explicitly, node by node" (see "Nominal edges" above).

It doesn't. `relation`/`Cardinality` (`1:1`, `1:many`, `many:1`, `many:many`) is ontology metadata — a domain fact, the same role a foreign key plays in a relational schema — not a routing mechanism. No edge instance ever reaches another edge's data without a node in between; a `Relation` only tells whoever (or whatever agent) is authoring a node's body what shape of lookup it's implementing. A node enriching `Order` with its `Customer` implements the `many:1` side and should declare `single Customer` output; a node fetching a customer's orders implements the `1:many` side and should declare `many Order`. `many:many` almost always wants a junction edge rather than collapsing into one node.

So `Relation.cardinality` and `OutputSpec`'s `single`/`oneOf`/`allOf`/`many` (see "Fan-out is three different things" above) are the same vocabulary at two different layers: `Relation` is a fact about the domain; `OutputSpec` is what a specific node declares it produces when it chooses to enact that fact. Nothing currently checks the two agree — that's a legitimate future validation, not yet built.

## Considered and rejected: ambient shared state (ADF, state machines)

Raised while looking for prior art on the open questions around accumulators, wait/sleep, and join keying (see `open-questions.md`): could a node just read and write some shared state pool instead of being strictly `In → OutputSpec`? Three real systems were checked against this instead of speculating.

**Azure Durable Functions** (the `apps/durable-functions` tree of an earlier project of mine) answers all three questions concretely, without ambient state. Its accumulator (the `collector` XState machine, `packages/schemas/src/automations/machines/collector.ts`) holds state as a persisted, versioned snapshot advanced one event at a time, deduped by an id — the same role weir's envelope `id` plays. Its wait is a durable timer (`createTimer(deadline)`, a duration) or, unused in this codebase but present in the platform, `waitForExternalEvent(name)` — a real `waitUntil(signal)` that suspends indefinitely at zero cost until something calls `raiseEvent(instanceId, name, data)`, and composes with `Task.WhenAny`/`Task.WhenAll` over several named events for timeout-races and joins. None of this needs a shared pool: state is scoped to one orchestration instance, and "join" is naming several events and waiting on some/all of them by name — much closer to `OutputSpec`'s `oneOf`/`allOf` than to a shared variable.

**LangGraph** is the one system that actually does this the ambient way, and it's worth naming exactly why that was rejected rather than just "different." LangGraph has no typed edge between nodes at all — one shared `state` object every node reads and partially writes, with conflicting concurrent writes resolved by a **reducer** attached to each field (e.g. `Annotated[list, operator.add]`). That's LangGraph's single answer to both accumulation and joining — a merge function on a shared channel, not correlation by id. The cost is exactly what showed up when this was checked against weir's decisions: no type gate per node, since any node can read any state field regardless of whether it's wired to whoever wrote it. That's structurally the same shape as **Azure Data Factory**'s pipeline-scoped variables (state set by one activity, mutable and readable by any other activity in the pipeline, lifetime-scoped to the whole run rather than to an edge) — both are the "ambient, mutable state" the readme's opening line (`no classes, no this, no ambient state`) was written against, just relocated from an object instance to a pipeline/graph run.

**State machines carry more primitives than their node/edge diagram admits**, which is a separate reason to keep `NodeDef` as-is for now. XState and LangGraph both draw as boxes-and-arrows, but the real vocabulary is six-plus parts — states, events, transitions, guards, actions, context (LangGraph adds channels/reducers/checkpointer on top). my earlier project's `reactorMachineTemplate` demonstrates the cost directly: the *template* (`setup()` — guards + actions, static) and the *topology* (`createMachineConfig()` — states + transitions, built from user config) had to be authored as two separate pieces that get assembled at runtime, because a state machine's full vocabulary doesn't fit into one declaration. weir's two-part vocabulary (edge = schema, node = pure fn) is a deliberate simplification against that, and closer to the mental model most people already have from IFTTT/Zapier/n8n-style "nodes passing data" than to a state machine's.

**Resolution:** keep `NodeDef` exactly as it is — single `In extends EdgeDef`, no shared/ambient state channel. The three open questions (accumulators, wait, join keying) stay open, but "give nodes a shared state pool" is now a rejected direction rather than an unexplored one, and multi-input/many-to-one nodes (if/when they're added) should still resolve via named, typed edges — closer to Durable Functions' named-event joins than to a reducer over ambient state.

## The netlist is an IR; start with the AST

A late naming pass over vocabulary that was already there without being said out loud: the design keeps reaching for compiler terms because it *is* one. "Generics: elaboration monomorphizes" above describes monomorphization by name. "Netlist" is EDA/HDL vocabulary — a flat, typed listing of component instances and their wiring, the thing a hardware description language compiles *down to*. `plan(from, to) → [Topology]` "turned out to be a planner" — type-directed search over an IR, ranked by cost, same shape as a query optimizer. Cut-vertex/reachability analysis "computed instead of read off a diagram" is dataflow analysis over that IR, the same category of pass as liveness or reaching-definitions, aimed at weir's own invariant (complete mediation) instead of register allocation. Dynamic mode's "netlist becomes the legal-move generator rather than the plan" (`design.md:208`) is an interpreter walking IR at runtime where static mode has a compiler resolving it ahead of time — AOT vs. JIT, mapped onto agent-routed vs. human-fixed topologies.

Naming it sharpens a question raised independently and then recognized as the same one: a normal compiler pipeline takes rich, ambiguous source — comments, naming, control-flow shaped for a human reader, the "why" — and *discards* it on the way to an AST/IR, keeping only what execution needs. That's real fidelity loss; decompiling back is lossy forever for exactly this reason. weir doesn't have that step. The AST-shaped thing — edges plus topology — *is* the source; node bodies are generated outward from it, not compiled inward into it. This is "The pivot" section's claim restated: *"the durable artifact is the topology plus edge definitions; the code is a build output you can throw away and regenerate"* (above). Nothing is lost going in because nothing narrative was there to lose — the "why" that would normally live in prose comments lives instead in the edge's own typed vocabulary (`measure`, `format`, `relation`, refinement naming like `PersonReceived` vs. `PersonAged`) and, per the still-open "Prose blocks on node declarations" question (`open-questions.md`), optionally in a description attached *to* the AST-level node rather than compiled *from* prose into one.

The practical corollary: weir isn't a new idea bolted onto flow-based programming, it's the well-understood source → AST → IR → execution pipeline with the authored/derived roles swapped — durable artifact and disposable artifact trade places, but the pipeline shape (and the tooling that shape unlocks: validation before "compiling," diffable topology, deterministic replay as a VM trace) is the same one compilers have used for decades. That's most of why this direction has felt more solid under scrutiny than the ambient-state alternatives in the entry above: it isn't being invented from scratch, it's reusing a shape with fifty years of prior art behind exactly the properties (static analysis, replay, monomorphization) weir keeps needing.

## Identity is the actor; edges are the resource; the node boundary is a membrane

Raised while narrowing `Envelope.identity` away from `identity?: string` (`types.ts`): what should fill in for "who/what this invocation runs as," and does it ever legitimately not exist?

**It never doesn't exist.** Tried to find a counterexample — an unauthenticated request, a cron firing, a pure computation with no side effects — and none of them hold up. ABAC/PDP systems (Cerbos and others) deliberately model "anonymous" as a real principal rather than the absence of one, because a policy check needs something to evaluate against; a cron still fires under some execution context; a pure node still inherits the identity of whatever caused it, the same way `correlationId` propagates. `identity` is better read as **"on behalf of"** than "who's logged in" — a system-triggered event still runs on behalf of the system, accountable the same way a human actor would be. my earlier project's `BaseActivity` (`packages/schemas/src/activities/base.ts`) confirms this is how a real production system already modeled it: `actorType`/`actorId` are required on *every* activity, no exceptions, and `ActorType` (`enums.ts`) includes `System` as a first-class value — there's no "no actor" case in the schema, only different kinds of actor. Resolution: `identity: Identity`, required, not optional — matches `causationId`'s reasoning above (a meaningfully-always-present fact belongs in the type as required, not as something that might be missing) but lands on the opposite nullability, because unlike causation, there's no root case where "on behalf of" is truly nothing.

**This completes a triad `design.md`'s permission-gates section already implied without naming it.** *"The node declares which permission is required and delegates the decision to a PDP"* is a Cerbos-shaped `check(principal, resource, action)` call: `identity` is the **principal**, the edge instance crossing the wire is the **resource**, and the node being invoked (`charge_card`) is the **action**. Keeping `Identity` narrowly "just the actor" — not also carrying tenant/institution scope — is what keeps that PDP call clean; scope-like attributes (my earlier project's `rssdId` on every activity, alongside `AutomationScope`'s `self`/`institution`) belong as attributes on the *resource* side (a field or `relation` on the edge), the same way Cerbos keeps principal attributes and resource attributes in separate bags rather than one merged identity blob. Non-nullable `identity` also keeps the PDP check total rather than needing a null-branch, which matters given "no conditionals in the declaration, ever" is already a hard rule for permission gates.

**Naming continuity, worth keeping on record:** the original rubber-duck conversation used **membrane** for this exact mechanism — the node's in/out boundary, where both the type gate and the permission gate actually run. "Weir" names the macro architecture (the narrow crossing, system-wide); "cut vertex" and "complete mediation" name the graph-theoretic and security properties; "membrane" is the term for the boundary *doing* the checking at one specific node. Three names, three angles, one mechanism — consistent with how the rest of this history tends to accumulate vocabulary rather than replace it.

`Identity`'s actual shape is still a placeholder (`Record<string, never>`, `Unit`'s idiom — not `{}`, which types as "any non-nullish value" and would narrow nothing) — designing the real actor model is future work, not resolved here.

## Composition parser deferred; authoring format designed instead

Started as "is a composition parser (`getting-started.md` step 3) next." Turned into a longer brainstorm that ended up reframing the step rather than building it.

**The parser isn't needed yet.** Composition syntax's documented job (`design.md` §6) is node-level examples — `given → expect` — not general topology authoring; step zero already settled topology-as-data (`netlist.json`). And examples are already fully representable without any parsing: `Example<In,O>` (`types.ts`) is exactly `{ given, expect }`, already written by hand in `node.test.ts`, 26 tests passing. Nothing currently depends on parsing pipe strings — composition syntax stays a prose convention for docs and design conversations, real and decided but not blocking, the same category as encryption/PDP in `getting-started.md`'s deferred list. Fan-out syntax candidates were explored first (bracket-per-kind, OCaml `match`, keyword-call syntax mirroring `oneOf()`/`allOf()`/`many()`) before this reframe made the question moot for now — worth revisiting if something eventually needs to parse free-typed examples (an agent prompt surface, a checked-docs tool).

**What actually turned out to be missing: a real authoring format for edges, nodes, and topologies**, as files rather than TS object literals or hand-maintained JSON. Landed on real YAML (not a custom grammar — explicitly rejected inventing a dialect, the way GitHub Actions/Azure Pipelines YAML stay real YAML with schema-driven tooling layered on by filename convention, not new syntax) across three file kinds, `.edge`/`.node`/`.topology`. Two of the three are pure data with no design gap (`.edge`, `.topology`); `.node` isn't, because `Fn` is executable code and a data format can't hold it — nor should it, per "the implementation becomes disposable" (the pivot section, above).

**The `.node` seam mirrors the registry/handler split I built on an earlier project precisely**, not just by analogy: `actionRegistry` (declarative, `packages/schemas`) stays separate from its handler files (`apps/durable-functions`), paired by naming convention and kept in sync by codegen (`codegen-actions.ts` scaffolds the handler stub from the registry entry) rather than by memory. `.node.yaml` plays the registry's role — contract only, no body — and weir's elaborator (§4) is the natural place for the equivalent scaffolding, since it already does the same kind of work resolving closures and monomorphizing generics.

**Versioning came from a real operational worry, not tidiness**: mutable `Fn` implementations break replay determinism, and redeploying a node's code out from under a long-running or replayed invocation is exactly the failure mode my earlier project's reactor orchestrators already had to solve — *"running instances are frozen to v1's data"* even after v2 ships (`activity-subscriber.md`, "Version Pinning"). Resolution: each node gets a directory of append-only implementation files rather than one mutable file; regeneration triggers off the same schema-hash mismatch check already used for edges (§5) and my earlier project's Arrow cache, applied one layer down; and an invocation now needs to record which implementation version it actually ran under, alongside `causation_id`/`schema_hash` in the envelope, so replay is exact regardless of what's since been regenerated. Written into `design.md` as a new §10, "Authoring format," since this is now decided architecture, not just how the decision happened.

**The version identifier is the contract hash, full stop — a walked-back detour.** First instinct: name each implementation file by its contract's schema hash — content-addressed, reproducible. Second-guessed that over a retry scenario (a rejected attempt redone against the same unchanged contract would collide on a bare hash) and landed briefly on a combined `<contract-hash>-<timestamp>` identifier to give retries distinct filenames. That was solving a problem that shouldn't exist: a *draft attempt* isn't a version and was never meant to be written into the append-only directory at all — only an implementation that's actually passed its examples gets persisted, one per contract state. Under that framing, "regenerate against an unchanged contract, get a different accept/reject outcome" isn't a storage case to design around, it's the examples underdetermining the function (§6, "a single example underdetermines the function") — a defect to fix in the contract, not a versioning scenario to accommodate. Filename reverts to `<contract-hash>.ts`; a timestamp, if wanted, is file metadata, not identity.

**Left open:** the version-pin field's exact name/shape on the envelope. (The `oneOf`/`allOf`/`many` YAML shape inside `output:` and JSON Schema generation, also left open here, are resolved below — "`.field`/`.edge` get real YAML, real validation, and a decided `.node` output shape.")

## The package boundary is real, and `.node.yaml` never references `fn`

Picked back up: whether `.node.yaml` and its implementation directory need a structural package boundary, or can just live side by side. Answer: real boundary, same schemas/runtime precedent from my earlier project already cited — and taken one step further than either side had noticed. That project's `actionRegistry` doesn't store a handler file path at all; the mapping from action type to `df.activity.action-{kebab-type}.ts` is pure naming convention, enforced by codegen, never data. Applying that fully: `.node.yaml`'s schema carries no `fn` field. The contract doesn't reference its implementation, doesn't know whether one exists. The elaborator resolves `{node-name}/{contract-hash}.ts` by name alone. This isn't just consistent with the package boundary, it's what makes the boundary cheap to build — a stored path would have to survive being resolved across packages (the classic relative-path-breaks-across-boundaries problem); a bare name resolved by convention doesn't care where either side physically lives.

Also corrected here: the versioned-implementation-directory idea itself (`Birthday/` as a directory, not a file, holding timestamped-then-content-addressed files) was misattributed in conversation as something proposed *to* the person building this, when it was proposed *by* them — worth being precise about in a document meant to trace decisions to who actually made them, not just that they got made.

## Property tests are generation, not mocking

Raised directly out of the retry/underdetermination conversation above: what if edges had generators — property tests running against N generated instances instead of hand-typed cases, the way `fast-check`/QuickCheck-style libraries work? Not a new idea, just a missing mechanism: `design.md` §6 already named this — *"Edge definitions double as generator specs... property tests are close to free here"* — without ever specifying how it runs. This concretizes it rather than invents it, and it's proven prior art, not speculative: property-based testing libraries already derive a per-field generator from a type shape and compose them into a whole-record generator, a near-literal transliteration of `FieldDef`'s existing `type`/`enumValues` fields — the same "mechanically derivable from the same types" move as the JSON Schema tooling, a different downstream artifact off the same source. No library named here, deliberately — same "spike, not a host-language commitment" caveat as everything else in `spikes/ts-prototype/`.

**The sharper realization: examples and mocks are not the same thing, and it's not incidental.** Floated dropping hand-written examples in favor of generated-only, walked back immediately — examples help authoring/thinking, and it wasn't clear *why* they're not redundant with generation until the mocking question got asked directly. Mocks exist to fake out **impure dependencies** — a database, an HTTP client — so a test can isolate code that can't avoid touching them. Weir nodes have no such dependencies to fake: "effects are data" (§5) means a node never calls anything impure directly, it just returns a value describing what it wants done. This isn't a new conclusion either — "the pivot" section already said it: *"Purity means generated code is verifiable locally, without mocking a world."* An `Example` is a real invocation of the real pure function against a chosen input, not a substitute for anything absent. So examples and generated cases were never competing ways to do the same job — examples are hand-picked for legibility (what a reviewer reads to see intent), generated cases are unbiased breadth a human wouldn't think to write by hand. Both stay; acceptance (§10, updated) now requires passing both, which also strengthens the earlier underdetermination point directly — broad generated coverage is what would surface a flip-floppy contract *before* acceptance, rather than via a flaky retry after.

## `Failed` gets a shape, and the catch stops being hand-written

"Failure as an edge" (above) resolved *that* failure is a real, wired edge rather than a bolted-on try/catch, and flagged the concrete shape as "nearly impossible to retrofit later." It sat unshaped since — no fields, nowhere in `types.ts`. Picked back up from a proposal to soften it into a nullable `envelope.error`, closer in spirit to Rust and "even more implicit."

Worth being precise about why that particular softening doesn't hold, since the instincts behind it (Rust, implicit) actually point the other way. Rust's `Result<T,E>` is not nullable or implicit — it's a checked sum type the compiler forces callers to handle, the same shape `Failed` already is. A nullable envelope field is the option "Failure as an edge" already considered and rejected (*"bolted on the side"*), and for the same reason the earlier null-vs-undefined work landed on `causationId: string | null` over an optional field: a nullable field doesn't force anything, and the entire point of choosing `Failed` as a real edge was *"the type checker flags unhandled failure paths"* — a property only a wired branch gives you.

What survives from the proposal, reconciled: `Failed<In>` stays a real edge, now shaped — `{ input: PayloadOf<In>, reason? }`, parameterized by the failing node's own input so a retry node has something to re-emit, not just a signal. What's genuinely new is authoring ergonomics, not the type: the runtime wraps every `Fn` invocation by default, an uncaught exception becomes `Failed<In>` automatically — no hand-written `try`/`catch` per node. An author can still construct and return `Failed<In>` explicitly for a specific `reason`, but isn't obligated to. Same opt-in shape `env` already has on `Fn` — implicit by default, more control available if reached for, not a competing mechanism.

## Constraint creep considered and declined: step/multipleOf, and format-as-validator

Following the `FieldDef` validation-layers pass above (`min`/`max`/`minLength`/`maxLength`/`pattern`, checked in `defineField`), two further Zod/HTML-form-shaped additions came up and were both declined, for the same underlying reason: each pulls `FieldDef` further from describing what the data *is* and toward prescribing behavior or presentation that belongs somewhere else.

**`step`/`multipleOf` for numeric granularity** (HTML's `step` attribute, Zod's `.multipleOf()`) — the case that motivated it: an `f32`/`f64` amount field that should only ever land on cent boundaries. Declined because the thing being patched isn't a missing constraint, it's a wrong type. A float required to always be a multiple of `0.01` is a fixed-point/decimal value wearing a float's clothes; a `step` constraint bolted onto `f32` treats the symptom (values that don't line up) rather than the cause (the type can represent values that shouldn't exist at all). If money needs exact cent precision, that's a scalar-type gap — a real fixed-point/decimal type — not a validation-layer gap.

**Making `format` a validator instead of a display hint** — floated reusing the existing `format` field (`id`/`enum`/`text`/`date`/`datetime`/`count`/`percentage`) so `format: "date"` would start implying a real ISO-8601 check, closing the gap where it's currently cosmetic only. Declined because `format` and `pattern` would then be doing the same job through two different mechanisms — one implicit (a hidden regex behind a display label), one explicit (the actual regex, already sitting right there on the same field). A field's real shape should be visible in its own definition, not inferred from what a display hint happens to imply. If a value needs shape-validation, `pattern` already says so directly; overloading `format` to also mean that just hides the same fact behind a second name.

Both come back to one rule: reach for a new field or a new type when a constraint is genuinely new, rather than loading a second meaning onto a field that already means something else (a display hint, or a numeric type chosen for unrelated reasons).

## Compound fields embed literally — Mongo-like, not SQL-like

Came up while extending `EdgeDef` so a field can hold another edge's shape directly (`PersonWithAddress { name, address: Address }`), needed for the earlier "different shapes per variant" thread once it was narrowed down to "can a field be richer than a scalar." `Payload<F>` grew a recursive case (`F[K] extends AnyEdgeDef ? PayloadOf<F[K]> : never`) so a compound field's runtime shape is computed the same way as the top level.

Two notational questions got asked and both resolved the same direction, worth recording so they don't get re-asked. **Should a compound field be spread instead of nested** — `address: ...Address` compiling to the fields landing flat on the parent? No: spread only ever flattens into the *enclosing* object (`{ ...Address, name }`), it can't bind to a specific key — `{ address: ...Address }` isn't coherent syntax in the language this is modeled on. That's not a gap, it's confirmation that spread (§2, already decided — reuse a shape by copying its fields in flat, erased at authoring time, no runtime relationship) and a compound field (a field whose value *is* a nested instance, still present at runtime) are two different, complementary mechanisms, not competing notations for one idea.

**Should a compound field compile to a reference instead of embedding** — `address: Address` becoming `address: Address.id` (Prisma-schema-shaped: a foreign key, resolved by a join) rather than the literal nested object. Declined. Two reasons, one immediate and one forward-looking:

- It would duplicate `FieldDef.relation`, already decided to be exactly this — a foreign-key-style domain fact between two *independently instantiated* edges, resolved by a node ("Relation/Cardinality: ontology, not a wiring bypass," above). A compound field isn't pointing at a separate instance somewhere else in the graph; it's owned, created and destroyed with the parent, never independently addressable. Collapsing the two into one FK-shaped mechanism would lose that distinction.
- Storage optionality, checked directly rather than assumed: Avro (records-within-records), Parquet (nested schema via repetition/definition levels), and DuckDB (`STRUCT`) all have first-class nested/struct support — a compound field maps straight onto a nested column, no join required. Committing to `address: Address.id` now would have pre-committed to a normalized/joined storage shape before any storage engine was chosen; embedding is the choice that keeps the eventual portable-artifact story (§5, "the log... is the source of truth," tables as materialized views) open rather than narrowing it.

Net: `relation` and compound fields are now two deliberately distinct, complementary idioms for the same general "one edge relates to another" question — `relation` is the SQL-like half (normalized, joined, resolved by a node), compound fields are the Mongo-like half (denormalized, embedded, resolved for free by just being the same payload). Both stay; reaching for the wrong one is now a legible mistake rather than an ambiguous choice.

## `.field`/`.edge` get real YAML, real validation, and a decided `.node` output shape

Picked up directly from §10's "deferred, not designed away" on schema-driven editor support, and from the "Left open" note above naming the `oneOf`/`allOf`/`many` YAML shape and JSON Schema generation as unresolved. Both are resolved now, plus a third thing neither had named yet: an actual loader.

**The elaborator's edge/field half is real** (`spikes/ts-prototype/src/elaborate.ts`), not just illustrative like `netlist.json`. `.field`/`.edge` YAML loads into validated `FieldDef`/`EdgeDef` objects through the exact same `defineField`/`defineEdge` every hand-written TS object goes through — no separate YAML-specific validation path to drift out of sync. Bare-name references (`email: email`, `address: Address`) resolve by glob-by-extension, the same convention §10 already committed to for `.node`'s implementation file, extended one layer down: whichever of a `.field`/`.edge` file with that name exists, wins. A file's declared `name:` must match its filename — the filename is the only handle another file has to reference it by, so a mismatch is a load error, not a silent orphan.

**JSON Schema is generated mechanically from the same validation** (`spikes/ts-prototype/src/schema.ts`), not hand-maintained — `fieldSchema()`/`edgeSchema()`/`nodeSchema()` read straight off `defineField`'s own `INTEGER_RANGES` table and type-appropriateness rules, so a numeric field's `min`/`max` bounds in the editor are the identical numbers the runtime check enforces, not a second copy that can drift. Wired into VS Code via `redhat.vscode-yaml`'s `yaml.schemas` workspace setting (`.vscode/settings.json`) — no custom extension code. What it can't do, on purpose: cross-field relationships standard JSON Schema has no clean way to express (`min <= max`), and (for `.node`) cross-*file* shape-matching (does `given: { age: 41 }` actually match what `Person` declares) — that second one is squarely §6's territory (generation against the real edge shape), not an editor-tooling gap to be closed with more schema cleverness.

**`.node`'s `output:` shape, the specific open item, resolved by extending precedent that already existed rather than inventing one**: `netlist.json`'s `expect_Person_age_42` had already sketched `output: { oneOf: ["Pass", "Fail"] }` in passing. Generalized: a bare edge-name string is sugar for `single`; `{ oneOf: [...] }`/`{ allOf: [...] }`/`{ many: name }` cover the other three `OutputSpec` kinds, the presence of the key itself acting as the discriminant rather than a separate `kind:` field. `examples[].expect` follows the same shape `Tagged<E>` already has in `types.ts` — `{ edge: "Pass", payload: {...} }` for `oneOf`/`allOf`, a bare payload for `single`/`many`. `closure` stays exactly one of `expected:` or `literal:`, never both, mirroring `ExpectClosure | LiteralClosure`'s union in the TS types. A `.node` file's schema has no `fn` property at all, same as the TS type — enforced now, not just documented.

## A real `datetime` scalar type

Hit hand-authoring a to-do example's `created_at`, first-hand evidence the "fun and easy to author" goal actually surfaces gaps `.field`/`.edge` alone wouldn't have. Same shape of question as the earlier `step`/`multipleOf` anti-pattern: `Format` already has a `"datetime"` value, but it's cosmetic only (the format-as-validator entry above declined making `format` mean anything at runtime) — reaching for it here would silently validate nothing. Resolved the same way that entry pointed at: a real scalar-type gap gets a real scalar type, not a display-hint workaround.

**Representation: ISO-8601 string, not a numeric epoch**, even though Avro/Parquet/DuckDB's native timestamp types are all integer-backed under the hood — the same storage engines cited in the compound-fields entry above. The difference here is which layer is being optimized for: compound-fields-as-embedding was a storage-shape decision; this is an authoring-ergonomics one. `created_at: "2026-08-21T09:30:00Z"` is legible to hand-type and read back; `created_at: 1798270200000` isn't, and nothing forces the eventual storage layer to keep the string representation — Avro's own logical-type pattern (a semantic label over a physical type, with a defined conversion) is precedent for exactly this kind of split. ISO-8601's fixed-width, zero-padded, UTC-suffixed format also sorts correctly as a plain string, so `min`/`max` bounds aren't given up by choosing the readable representation.

**One type, not two.** `Format` already distinguishes `date`/`datetime`; a date-only scalar (for a `due_date`) is a real near-future need, not a hypothetical one — but `created_at` is what actually came up, and it's a `datetime`. Added just that one, deferring `date` until it's an actual field someone's typing, not a preemptive pair. `ScalarTsType<"datetime">` maps to `string`, same as `utf8` — a distinct scalar, not a distinct TS representation; `validations` reuses `utf8`'s `pattern`/`minLength`/`maxLength` shape rather than inventing a new one, since both are just constrained strings from the type system's point of view.

## `many` moves from node outputs onto fields

Surfaced hand-authoring a to-do list example: `List { tasks: Task[] }`, reaching for TS array-bracket syntax for "this field holds many Tasks." That syntax doesn't correspond to anything — a compound field is a bare-string reference with no `type:` key at all (`address: Address`), and a scalar's `type:` is a closed `ScalarType` union that `Task[]` isn't a member of. What was actually missing: a field could hold *one* compound edge but never *many* of one.

**Reused `.node`'s `output:` idiom rather than inventing bracket syntax.** `{ oneOf: [...] }`/`{ allOf: [...] }`/`{ many: name }` already exist as `.node`'s answer to "more than one edge here," the key itself acting as the discriminant (`.field`/`.edge` get real YAML..., above). Applying the same `{ many: name }` shape to a field's value — `tasks: { many: Task }` — keeps one vocabulary for "many of an edge" across the whole system instead of two, and the resolution mechanics are identical to a plain compound field: a bare name, resolved by the same `.field`/`.edge` glob-by-extension convention, just wrapped in one more key.

**Mechanically**: a new `ManyEdgeDef<E extends AnyEdgeDef> { many: E }`, folded into `AnyEdgeDef`'s field-value union alongside `FieldDef`/itself (so a many-field can nest arbitrarily deep, same as compound fields already could). `Payload<F>` gained a third branch — `F[K] extends ManyEdgeDef<infer E> ? PayloadOf<E>[] : ...` — checked before the bare compound-edge case since a `{ many: E }` value would otherwise also happen to satisfy structural checks meant for `E` itself. `hash.ts`'s fingerprint tags a many-field's entry as `{ many: <recursive fingerprint> }`, distinct from a plain compound field's `{ edge: ... }`, so "one Task" and "many Task" can never hash identically. The elaborator rejects `many:` pointing at anything other than a bare edge-name reference — no inline shape, and no pointing at a field (`many` is for edges, the same way a compound field always was).

## `.field`/`.edge` stop declaring `name:` — the filename already is one

Found hand-authoring the same to-do example that surfaced `many`, and self-diagnosed directly: two files (`List.edge`, `Task.edge`) had a `name:` that didn't match their filename — a space in one, wrong case in the other — exactly the failure mode `elaborate()`'s filename-must-match-`name:` check existed to catch. The check worked. The response wasn't a better check.

**"If those things need to happen, they should be impossible."** A validated mismatch is still a mismatch that had to be caught; the actual fix is removing the second place the name could be written down. A standalone `.field`/`.edge` file's `name:` was only ever there because the file has no parent map to be a key in, the way an inline field's name comes free from its key in `fields:` — but the *filename* already carries that exact information, ambiently, for free. Requiring `name:` too meant asking a human to keep two copies of the same fact in sync by hand, then building a check to catch it when they didn't.

**Resolution: no `name:` key, anywhere, ever — not optional, a schema violation.** `elaborate()` derives a file's name from `basename(file, ext)` directly; `parseFieldFile`/`parseEdgeFile` now *reject* a `name` key if one's present, and `fieldSchema()`/`edgeSchema()`/`nodeSchema()` do the same via `additionalProperties: false` with `name` absent from `properties` — caught in the editor, not just at load time. `assertNameMatchesFilename` doesn't get replaced by a better version; it's deleted, because the state it existed to catch is no longer representable. Applied to `.node` too, for consistency, even though no `.node` loader exists yet — the same reasoning holds regardless of which file kind gets a real reader first.

Same move as `Failed<In>` being a real wired edge instead of a nullable field the type checker can't force anyone to handle (above): don't add a check for a mistake, remove the degree of freedom that made the mistake possible in the first place.

## `EdgeDef` gets a `label`, separate from `name`

Landed within minutes of the `name:` removal above, from hand-authoring `TaskList.edge` and wanting to write `Task list` somewhere — and immediately hitting "name" is not allowed. Not a regression; a real gap the removal exposed. `name` had quietly been doing two jobs — the machine identifier used for wiring/hashing/references, and, whenever an author bothered, something closer to a human-readable display string. Making `name` purely filename-derived kept the first job and dropped the second with nowhere to land.

`FieldDef` already drew this line correctly and had for the whole session: `label` (human-readable) and identity (a field's map key) were always two different things, never expected to match. `EdgeDef` never got the same split — resolved by giving it one: `label: string`, required (matching `FieldDef.label`/`description`'s required status, decided early this session), no relationship to `name` asserted or checked. `TaskList.edge` keeps its clean, reference-safe identifier; `label: Task list` is free text, spaces and all. `NodeDef` gets `label?: string` too, for consistency, but left optional — matching `NodeDef.description`'s existing optional status and the still-open "Prose blocks on node declarations" question (`open-questions.md`), the same restraint already applied when `.node`'s schema was built.

## Nullable fields, finally built — explicit `T | null`, picked up from early this session

Decided early in the validation-layers work, before the `.field`-file thread pulled focus and it never got built: "start rigid with null and expand from there" — explicit `T | null`, not an optional/absent key, matching the precedent `Envelope.causationId: string | null` already set. Came back around from hand-authoring a task's `due_at` and asking directly how to type it.

**Mechanically**: `FieldDef` gains a second type parameter, `N extends boolean`, carrying a `nullable?: N` property — `Payload<F>`'s scalar branch becomes `N extends true ? ScalarTsType<T> | null : ScalarTsType<T>`. One thing worth being precise about, since it's the third time this exact shape of bug has shown up this session (`AnyEdgeDef`, `ManyEdgeDef`, now this): `FieldDef`'s own default for `N` has to be the *wide* `boolean`, not `false` — a bare `FieldDef` reference (as used in `EdgeDef`'s `F` constraint) needs to stay structurally compatible with a field that actually has `nullable: true`, the same reason `AnyEdgeDef` had to exist as a separate wide alias rather than letting `EdgeDef` bare cover it. `defineField`'s own function-level default for `N` *is* `false`, correctly — that's the fallback for actual inference (an omitted `nullable` key), a different default for a different purpose than the interface's structural-compatibility default. Two defaults, two jobs, not a contradiction.

`nullable` is structural in the schema hash (`entry.nullable = true`, present only when set — a non-nullable field's hash is byte-identical to before this existed), and a plain `nullable: { type: "boolean" }` in the generated JSON Schema. (Whether it's required, and forbidden on `bool`, is decided in the next entry — landed within the same exchange.)

## `nullable` becomes required (except on `bool`, where it's forbidden)

Immediate follow-up, same conversation: `nullable` shipped optional (default non-nullable), then reconsidered — every field should have to make its nullability decision explicit, not fall into it by omission. Same instinct as `label`/`description` becoming required earlier this session, applied one property further.

**`bool` is the deliberate exception, not an oversight.** A nullable boolean is a tri-state hiding behind a two-state type — `true` / `false` / `null`-meaning-unset are three distinct states, and `null` there almost always means "I haven't modeled this correctly," not "this is genuinely absent." Rather than let that ambiguity into the type system, `bool` simply isn't allowed to declare `nullable` at all — forcing whoever's reaching for a nullable boolean to either pick a real default or model the missing state as its own thing.

**Mechanically**: `FieldDef` moves from a plain interface to a conditional type — `T extends "bool" ? FieldDefBase<T> : FieldDefBase<T> & { nullable: N }` — so `nullable` isn't just validated as present-or-absent, it's structurally absent from the `bool` branch's type entirely; TS's excess-property check catches `nullable` on a `bool` field the same way it already catches a stray `name` on an inline field. This is the same technique `Validation<T>` already used to shape `validations` per type — extending an established pattern, not inventing a new one. Two runtime backstops for the YAML path, which bypasses TS entirely: `defineField` throws if a non-`bool` field omits `nullable` or a `bool` field declares it; `fieldSchema()` gets a matching `allOf` conditional (`if type=bool then forbid nullable else require it`), so the editor catches it too.

One real cost, worth naming rather than hiding: `FieldDef` being a distributed conditional type means a bare `FieldDef` reference (e.g. `base.fields.id` in a test, typed only as the wide `EdgeDef` default) resolves to a union across every scalar type, and spreading a value of that wide union type while overriding a property can fail to type-check even when the concrete runtime value is fine — TS can't tell which union member's shape you meant. Discovered fixing test fixtures; the fix in every case was writing the field literal directly instead of spreading a wide-typed placeholder, not weakening the type. A real ergonomic tax for real precision, isolated to test-fixture authoring rather than anything hand-authored in `.field`/`.edge`.

## `.node` examples become required, and `given`/`expect` get tagged with the edge name

Surfaced hand-authoring `examples/todo-list/`'s `CompleteTodo.node`: `input: Todo, output: Todo` validated cleanly against `nodeSchema()` with no `examples` at all — and was immediately recognized as wrong. A same-shape-in-same-shape-out node conveys nothing beyond its type signature without an example; as written, `CompleteTodo` was structurally indistinguishable from a no-op, or from a node that changes `title` instead of `is_complete` — anything else `Todo → Todo`. §6 already named examples as one of three things a node declaration carries; this is that requirement actually being enforced rather than just stated.

**Terminology correction, on record so it doesn't drift:** "rhombus" was reached for mid-conversation to mean 1-in-1-out, with "straight pipe" and "triangle" proposed as clearer replacements. Checked against `design.md` §2's existing shape table before adopting anything: `Rhombus | width in = width out` is already the decided term for exactly this case (`node.test.ts` already calls `birthday: Person → Person` a rhombus) — "width in = width out" is about information preservation, not literal arity, and is a different axis entirely from "triangle" (a refining/eroding *decision*, one↔many). Existing vocabulary kept; nothing renamed.

**`given`/`expect` are tagged with the edge's name as the object key** — `given: { Todo: {...} }`, `expect: { Todo: {...} }` — rather than either a bare untagged payload or `Tagged<E>`'s `{ edge: "...", payload: {...} }` shape already used in `types.ts`/`netlist.json`'s trace. Deliberately diverges from that existing shape (netlist.json's own README already calls itself unratified) because the name-as-key form extends cleanly to `allOf`, where several edges fire at once — `expect: { A: {...}, B: {...} }` reads directly as "these things happened," where `Tagged<E>[]` would need an array of wrapper objects instead. For `oneOf`, "exactly one key present" is close to self-documenting. `closure.expected`/`closure.literal` adopt the same tagging, for one consistent convention across the file rather than examples being tagged while closure isn't.

**What `nodeSchema()` can and can't check here, and why — verified empirically, not assumed.** It's tempting to think the tag's *name* could be cross-checked against `input`/`output`'s own declared edge names, all sitting in the same file — no cross-file lookup needed, unlike matching `given`/`expect` against the *referenced* edge's actual field shape. Tried it directly with ajv's `$data` extension (`propertyNames: { enum: { $data: "1/output/oneOf" } }`) before relying on it: it silently accepted an invalid tag that should have failed. Not pursued further — a validator that's wrong is worse than no validator, and `$data` isn't standard JSON Schema regardless, so betting on it risks not even working the same way in `redhat.vscode-yaml`'s bundled version. Scoped `nodeSchema()` to what's honestly checkable without it: `examples` required and non-empty; `given` always exactly one tag; `expect`'s shape (one tag vs. several, object vs. array-of-objects) keyed off `output`'s own *structure* (`oneOf`/`allOf`/`many`/bare-string), which is a same-schema check, not a cross-reference. One real JSON Schema gotcha hit along the way: `required: [...]` is vacuously true against a non-object instance, so all four output-shape conditionals were matching simultaneously whenever `output` was a bare string, until each got an explicit `type: "object"` guard alongside `required`. Matching the *tag name* itself against a real declared edge stays `elaborate()`'s job, same conclusion as when `nodeSchema()` was first built — confirmed harder than hoped, not softened.

## The membrane: every node call is `membrane(fn(edges))`, never bare `fn`

Surfaced trying to design multi-input nodes for `AddTodoToList` (`examples/todo-list/`) and immediately snowballed into rethinking what an edge, a wire, and the envelope actually mean. The visual model — boxes and wires, à la Node-RED/n8n — was quietly implying that a wire *carries* data synchronously between two boxes, which doesn't hold up: an edge is a schema (§1), not a wire, and the wire itself represents control (sequencing/parallelism), not the payload moving through space. Getting that backwards is what made multi-input feel like it needed a literal two-lines-arrive-at-once join.

**First proposal, considered and adjusted:** carry an accumulating `state` map (keyed by edge type name) plus a `history` log directly on the envelope, so a node's `input` could mean "what must be present in state" rather than "what wire delivered a value." This is structurally close to LangGraph/Azure Data Factory's shared-state model, already considered and rejected once (this file, earlier) specifically because "any node can read any state field regardless of whether it's wired to whoever wrote it" — no type gate. The distinguishing question, worked through directly: is *this* state ambient in the same disqualifying sense?

**Resolved no, and resolved by not needing the field at all.** `design.md` §5 already committed to "node state is a fold over prior edges keyed by `correlation_id`" before this conversation started. A `state` map living on the envelope isn't a new mechanism — it's a cached, incremental *representation* of that same fold. Taken further: it doesn't need to be one shared map, or a persisted envelope field, at all. There is no single "graph-level state" — there are only independent per-edge-type logs, each carrying its own history, and a node's multi-input declaration (`every: [A, B]`) is a *readiness condition*, resolved by the membrane checking whether an `A`-shaped and a `B`-shaped edge both exist yet for the current `correlation_id`. No accumulator, no `.reduce` — presence in the log is the signal, same as `Promise.all` not caring what order its promises resolve in. `Envelope`'s persisted shape is unchanged; nothing was added to `types.ts`.

**This also dissolves "origin node" as a distinct kind of node.** If every invocation is uniformly `membrane(fn(edges))`, an origin node doesn't need a special input type (`Unit`, floated and rejected earlier this file) or a new `trigger:` primitive (floated in conversation, not built). It's an ordinary node; what makes it an origin is only where the membrane's `edges` argument comes from — an internal node's edges are read from prior nodes' logs, an origin node's edges are handed in directly by whatever triggered the graph (HTTP handler, cron tick, queue message). A graph with several origin-shaped inputs doesn't fire them independently: there is exactly one call to the graph's outer membrane per external event (concretely, one HTTP request), and every origin-shaped edge resolves from that single payload at once. This closes "Is a cron itself a node?" (`open-questions.md`) — no, it's a caller of the outer membrane, not a node in the graph — and "Time as a named origin edge" — `Std.Now` needs no special ambient-envelope mechanism, it's just another named edge a node can declare via `every:`, resolved the same as anything else.

**A diamond topology (`A -> B`, `A -> C`, `B -> C`) makes the transitivity concrete.** `C` declares `every: [A, B]`; it never needs to know that `B` itself required `A` to run. Reading `B`'s log entry already implies `A` was available when `B` ran, so the dependency composes without `C` redeclaring it — this is what closes "Join keying" (`open-questions.md`): there's no synchronous join to key, only independent, per-edge-type presence checks against one `correlation_id`.

**Mechanically, membrane also absorbs the runtime's existing exception-wrapping.** §3 already committed to the runtime wrapping every `Fn` invocation, turning an uncaught exception into `Failed<In>` automatically — the membrane is that wrapper, named, with assert (and, next entry, authorization) added ahead of the call rather than only failure-catching added after it. A membrane rejection (failed assert, unsatisfied scope) produces its own tagged edge the same way, never an exception escaping the boundary.

## Identity is a verified-once JWT; `scope` becomes a per-node declaration, and the grant registry is codegen

Direct follow-on to the membrane entry above: once every node call is `membrane(fn(edges), identity)`, what is `identity`, and is threading it through every inner membrane call itself a form of the ambient state just designed away?

**Resolved: it's a different shape of thing, not the same mistake.** What made a shared `state` map disqualifying was that it accumulates — multiple nodes write to it over the course of a thread, with no gate on who reads what. Identity doesn't accumulate: it's a JWT, verified exactly once by the graph's outer membrane on the way in, and every inner membrane call downstream sees the same value, unchanged — nothing ever writes to it. The property that actually matters isn't "is it available everywhere" (it is) but "does using it still require an explicit, declared gate" — and it does: a node's ability to *proceed* depends on `scope`, a new `.node` field it declares itself, checked by that node's own membrane call against the identity's claims before `Fn` runs. This is the same mechanism `design.md` §7 already named — "the node declares which permission is required and delegates the decision to a PDP" — given a concrete carrier (JWT scope claims) and a concrete enforcement point (the membrane), rather than a new concept.

**`scope` is optional, not required**, deliberately unlike `nullable` (this file, earlier): omitting `nullable` was silently dangerous (an unconsidered null crashing something downstream), where a node needing nothing beyond the thread's existing authentication is a common, unambiguous, entirely legitimate default — there's no footgun being papered over by leaving it out.

**The grant registry is generated, not hand-maintained.** Scanning every `.node`'s declared `scope` produces the canonical list of valid scopes mechanically — the same discipline `design.md` §10 already applies to JSON Schema generation (one source of truth, nothing hand-duplicated to drift out of sync), extended one layer up from data shape to permissions. A scope referenced by a `.node` file that no scan ever produced independently would be a typo, not a new grant; a scope nothing enforces isn't real. Not yet built: `elaborate.ts` currently globs and resolves only `.field`/`.edge` files (`elaborate()` returns `{ fields, edges }`); there is no `.node`-loading step yet for the registry (or anything else) to consume. `nodeSchema()` exists for VS Code's live validation of a single `.node` file in isolation, which is a different job than elaborating the whole set.

**What `fn` actually receives from identity is still open**, and worth closing the same way as everything above: does `Fn` get handed the raw JWT/identity value, or only the specific claims relevant to its own declared `scope`? Leaving the raw value reachable would reopen a smaller version of the same problem — a node inspecting a claim it never declared needing.

## Membrane moves out of "Primitives"; identity resolves to one system edge, everything else is `std.*`

Two related corrections to the membrane/identity design above, both raised pressure-testing the mechanism against real code and real terminology.

**"Primitive" was already a claimed word.** `design.md` §1 uses "primitive" for a narrower, specific thing — a node whose body is host code, as opposed to a composite whose body is a subgraph; an author's implementation choice. Membrane isn't that: never authored, never chosen, never referenced or opted into the way `Envelope` is. It's generated purely from a node's own contract, always present, never modified — closer in kind to "nothing polls" or "the log is the source of truth" (§5's other execution-model facts) than to something a `.node` file declares. Moved out of §1 into §5, defined next to the origin-node and multi-input paragraphs that already described its behavior in detail, rather than split across two sections.

**Code I've already shipped tested "what does `Fn` receive from identity" directly.** A `withAuth`-shaped middleware I wrote on an earlier project (described here without naming the project, same as elsewhere in this file) wraps every handler with two declared requirements — a required permission, a list of required env vars — and resolves them asymmetrically: env vars come back precisely typed to what was declared (a real generic deriving the injected shape from a `readonly string[]` tuple, `Record<RequiredVars[number], string>`), but the authenticated-user object is handed over whole, every field, regardless of which single permission was declared. Genuine evidence "purely spec-derived" is buildable and type-checked in practice, since I've run it — and also a concrete instance of the exact asymmetry this design has otherwise been avoiding (§7, "downstream nodes never see what they aren't entitled to"). Copying it wholesale would have reopened that gap for identity specifically.

**Resolved: `Identity` is the one true framework-provided system edge; nothing else is.** The outer membrane verifies a JWT once and populates `Identity` directly (`sub`, `iss`, granted scopes) — no node produces it, because verifying the token is the trust boundary itself. Everything richer that looked like it wanted the same treatment (a user profile, an account lookup) doesn't get it: it's an ordinary node like any other (`LookupUserProfile: Identity -> UserProfile`), just one the framework ships a default, sensible implementation for. This reuses a mechanism that already existed rather than inventing "override a system edge" as new: §10's implementation-versioning (a different accepted implementation per contract hash) already covers "ship a default, let it be replaced." The name for this class of shipped-but-ordinary default lands on `Std.*` (`Std.Now`, and presumably a `Std.UserProfile` or similar) — batteries-included, never magic.

**A node reads `Identity` the same way it reads any other edge, narrowed to exactly the field `scope` names** (`read:Identity:sub`), which closes the raw-vs-scoped question the prior-art comparison raised: never the whole object. Left open, and moved to `open-questions.md`: whether this `verb:edge:field` shape is actually the same mechanism as `every:`, generalized with field-narrowing and applied uniformly to every edge — or a genuinely separate declaration that happens to resolve through the same membrane and look syntactically similar.

## `membrane()`, first slice: assert-then-call, nothing but the NodeDef

First code against the membrane design above — written to test the "purely spec-derived, nothing configured beyond the NodeDef" claim directly rather than leave it as prose. `membrane(nodeDef)` returns `(payload: unknown) => Promise<OutputResult<O>>`; `membrane()` itself takes nothing else. Internally: `assertPayload` checks an unknown value's required fields, primitive types, and nullability against `nodeDef.input`'s field defs, collecting every violation rather than stopping at the first (`spikes/ts-prototype/src/membrane.ts`, `membrane.test.ts`).

Deliberately narrow, and the narrowing is stated in the file's own header comment rather than left implicit: no `every:` multi-input yet (`NodeDef.input` is still a single edge — that change comes with `every:` itself), no `scope`/identity resolution, no correlation-id log to resolve a multi-input node's edges from (no store exists yet in this spike), no compound/nested-edge or `many` fields in the asserted payload (`assertPayload` throws explicitly rather than silently skipping them), and a rejection is a thrown error, not yet the `Failed<In>` edge §3 calls for. Each is a real next increment, not a corner cut and forgotten — same shape of honest partial slice `elaborate()` and `nodeSchema()` were each built in.

## `every` lands; a pulse/wave model settles graph-level scheduling; `first`/`each` deferred to cycles

**A concrete execution model, drawn rather than described, resolves "no explicit ordering, still deterministic."** A node fires in the earliest discrete pulse where every edge it declared needing has appeared in some prior pulse — origins all share pulse 1 by construction (design-history.md, "The membrane": one external event populates every origin-shaped edge at once). For the diamond (`A -> B`, `A -> C`, `B -> C`, from the earlier "membrane" entry), `C`'s pulse is `1 + max(pulse(A), pulse(B))`. This is a real scheduling algorithm, not just a visualization — layered/topological, no priority or explicit sequencing needed, falling straight out of the DAG once cycles are excluded (§3, already decided). Not yet written into `design.md` §5; worth doing once more of the runtime exists to describe accurately.

**`first`/`each` were floated as two more top-level `InputSpec` kinds** (`first: A` fires once, on the first occurrence, drops later ones; `each: A` fires once per occurrence) alongside a possible `any` (waits for the first of *several distinct* edge types, the natural pair to `every`'s "all of several"). Resolved not to build `first`/`each` yet, for a reason sharper than "more work": a graph is invoked exactly once per one set of inputs — a fresh external trigger is always a *new* invocation (a new `correlation_id`), never a second wave into an existing one ("invocation," not "instance" — deliberately avoiding class-language for the same idea). That means within a single invocation, an edge type can only recur if a *cycle* produces it more than once; nothing else can. `first` vs. `each` only has something to distinguish once recurrence is possible at all, so both are inert without cycle/bounded-iteration support (§3's "declared iteration bound" — no such mechanism exists yet). Building them now would be API surface with nothing real for it to do. `any`, by contrast, is about breadth (which of several distinct types), not recurrence — it stays meaningful in a plain acyclic graph and is a cheap follow-on to `every` (same pulse-arrival mechanism, `min` instead of `max`), left out of this pass only because it wasn't the thing actually asked for.

**`every` itself** (`spikes/ts-prototype/src/types.ts`'s `InputSpec`, `InputPayload`; `define.ts`'s `every()`; `membrane.ts`) mirrors `OutputSpec`'s existing "kind is the discriminant" idiom rather than inventing a new one — `single` is literally the same `{ kind: "single", edge }` shape `single()` already produced for outputs, so one helper serves both sides. `every`'s payload is a bag keyed by edge name (`{ A: PayloadOf<A>, B: PayloadOf<B> }`), matching the `given`/`expect` name-as-key convention already decided for `.node` examples, and let each declared edge's `name` flow through as a literal type via generic inference rather than widening to `string` — confirmed by `tsc`, not assumed. `membrane()`'s return type now depends on `nodeDef.input.kind`: a `single`-input node still takes a direct payload; an `every`-input node takes `(correlationId, log)` and resolves to `undefined` — not an error — when not every declared edge has appeared yet for that thread, matching "it's just Promises, not `.reduce`" (design-history.md, "The membrane"). Backed by a first `Log` interface and an `InMemoryLog`, real but minimal — one entry per `(edgeName, correlationId)` pair, `latest()` only, no history of prior instances, no persistence. Reading is confirmed non-consuming (tested directly): two membrane calls against the same correlation_id resolve the same way, so two different downstream nodes can depend on the same upstream edge without racing or depleting it.

## Weir has no loop construct, and needed none — "cycles" were a drawing problem, not a design gap

Surfaced sketching what `.graph`/`.topology` YAML should look like (still undesigned) for the diamond from the two entries above. Drawing a case where `C`'s output feeds `A` again — visually a back-edge, `A -> B -> C -> A` — exposed that the *diagram* was lying, not the design.

**A node has no instance (§1: "a pure function... no instance state").** A classic cycle diagram implies going back to a place: the same box, revisited. But there is no persistent "the same box" to revisit — only a function, applied again to new data, at a later pulse. Drawn correctly, that's not one circle with an arrow curling back into itself; it's a second, separate circle also happening to be labeled `A`, fed by `C`'s output the same ordinary way any node is fed by anything (this file has an "accurate cyclic" vs. "antipattern" pair of reference images from the conversation that made the distinction concrete). Nothing points backward in time.

**This wasn't `design.md` §3 being wrong, exactly — it's subtler than that.** §3 said "Trace (feedback/loops) is excluded, or admitted only with a declared iteration bound," which correctly kept loops out but for an imprecise reason: it named the risk as *iteration count* (so it reached for a *bound* as the safeguard) rather than naming the actual reason a loop can't exist here at all — a `while` loop requires a mutable slot that gets re-entered and reassigned, and that's not a new prohibition, it's the *same* ambient-mutable-state exclusion already in force from the start of this design. Loops were never a distinct thing needing a special escape valve; they were already impossible, for a reason already on the books.

**What a loop gets you is still fully available — realized as forward-only unrolling through the log (§5) instead.** Every "iteration" is a genuinely new, distinct, append-only entry; recurrence is always a fresh pulse or a fresh invocation, never a revisit. Real, shipped precedent for exactly this distinction, from the marketing-automation platforms this design keeps drawing on: a HubSpot/ActiveCampaign workflow action that "enrolls" a contact back into the *same* workflow is not a go-to to the workflow's top — it's a brand-new, independent enrollment, indistinguishable from a loop when the workflow is drawn as a diagram, semantically nothing like one. "Always forward" is the same idea one level up: a graph is invoked once per one set of inputs (this file, "`membrane()`, first slice"), and a recurring trigger is always a *new* invocation, never a continuation of an old one.

**One real, different question survives, and it's worth being precise about which one.** Nothing here can deadlock or get stuck re-entering a position — there is no position to re-enter. What a self-sustaining chain of ordinary forward wiring *can* do is keep appending new edge instances to the log indefinitely. That's an unbounded-growth concern, not an infinite-loop concern, and probably wants a cost/pulse-count bound on an invocation if it ever wants one — not anything shaped like cycle detection.

`design.md` §3's "excluded, or admitted only with a declared iteration bound" is revised accordingly: no loop construct exists, none is needed, and there is nothing to bound at the topology level.

## A literal field type, for branching without narrowing shape

Surfaced designing `CompletedTodo`/`IncompleteTodo` as nominal refinements for `.topology` branching (`open-questions.md`'s `.topology` entry, still itself unresolved) — a decision that must be visible in the topology (§2's refinement rule) without inventing a *shape*-different edge for what's still conceptually "just a Todo."

**Spread already does the actual composition, with no new mechanism.** `edge CompletedTodo { ...Todo, is_complete: true }` was floated and initially over-thought as needing some kind of exclusionary/narrowing spread — it doesn't. A later explicit key overriding a spread-inherited one is what spread already means in any language that has it (object-literal semantics: later key wins). That's a different, easier case than the still-open "partial input, partial node-pinned default" item in `open-questions.md` (excluding some of an input edge's fields is subtractive; this is additive-with-override).

**What was actually missing: a shape for `is_complete: true` itself.** Every other field entry is a full `FieldDef` object (`type`, `label`, `description`, ...); `bool` isn't narrow enough to pin one value permanently. Resolved as its own field kind, `literal`, standalone rather than a modifier on `type: bool` — deliberately parallel to `closure`'s existing `literal:`/`expected:` split (design-history.md, "`.field`/`.edge` get real YAML..."), so "is this a real bool or a pinned constant" reads at a glance rather than hiding in an attribute. Scoped to booleans only for now (the surfaced need); string/numeric literals are a natural but undesigned extension.

**Mechanically**: `fields.schema.json` restructured from one shape to a top-level `oneOf` — the existing `type`-required object (moved into `$defs/typedField`, unchanged) or a new `literal`-required object (`literal: boolean`, optional `label`/`description`, no `nullable`, no `validations` — both meaningless on a fixed constant). `edge.schema.json`'s per-field `oneOf` (bare-string compound ref / typed object / `many` object) gained two siblings: the same `literal` object, and a bare boolean directly (`is_complete: true`) as sugar for it — consistent with the file's existing "presence/shape of the value is the discriminant" idiom (`oneOf`/`allOf`/`many` all work this way already). Verified against both schemas directly: the bare-boolean and explicit-`literal` forms validate, a `literal` field carrying `nullable` is correctly rejected, and existing typed fields (including plain `bool`) still validate unchanged — no regression.

## The pivot's authorship line, corrected: heuristic, not exclusivity

Raised rereading "The pivot" (above) against how authorship actually happens: *"the human doesn't write node bodies"* reads as a structural claim, but nothing enforces it and nothing should try to. A human can and should author, review, and edit their own node `Fn`s when they want to; nothing stops an agent from drafting `.edge`/`.node`/`.topology` files either — there is no mechanism, at the moment of writing, that can tell which hand typed which file, nor should there be one that cares.

**What the line is actually for: a fixed orientation point for debugging, not a control.** §6 already concedes ontology has no mechanical check — "nothing can tell you the edge set carves the domain correctly except review." The authorship split is the same kind of thing one layer over: not a fact about who typed a file, but a stance held regardless, because it gives whoever's debugging a first question to ask — is this a definition problem (ontology/topology, meant to be gotten right and stable) or an implementation problem (disposable, regenerable, §10) — that stays useful whether or not the boundary was actually respected while authoring. Kept in the docs for exactly that reason: it onboards the mental model, which is the actual job here, not enforcement.

## Acceptance gating, generalized one layer up: from implementations to declarations

Raised pressure-testing the correction above: if authorship can't be gated, is there anything real backing "human defines edges/nodes" at all, or is it advisory all the way down? Not quite — §10 already has a gate that doesn't care who typed anything: nothing is *written* until it passes its examples and generated property cases; only what's accepted persists. That mechanism doesn't inspect authorship, it inspects an artifact before letting it become real.

The same shape generalizes upward: gate `declarations/` the identical way, on human sign-off rather than passing tests, since ontology (§6) is the one layer with no mechanical check to gate on instead. Concretely buildable without inventing anything — required review on `declarations/**`, the same shape as CODEOWNERS/branch protection, stated as part of weir's own contract instead of left to whichever repo host happens to be in use. Deliberately not "detect and block agent-authored declarations": a declaration isn't real until a human accepts it, independent of who drafted the diff — exactly mirroring how an implementation isn't real until it passes acceptance, independent of who wrote *its* draft.

**Sequencing decided deliberately, not left open:** ship this as a required gate, not an optional one, from the start. A constraint shipped as optional from day one never gets pressure-tested — nobody's forced to feel where it actually binds — so there's no way to learn whether it was load-bearing or decorative. Loosening a well-understood hard constraint later (a permission governing who's allowed to be the accepting reviewer, §7's shape, not a new mechanism) is cheap; tightening a constraint everyone's already built habits around ignoring is not. Not yet built, and the loosening mechanism's exact shape is still open — see `open-questions.md`.

## `correlation_id` origin/lifetime: a gap surfaced by a sibling project's tool contract, not a design decision made here

`mental-museum` (a separate, docs-only sibling project — interactive teaching exhibits where a reader predicts an outcome before being shown it) independently designed a two-call agent-tool contract for that predict-then-reveal pattern: `setup_exhibit(params) -> {scenario, controls, prediction_prompt}` — no `actual` field — then, after the reader states a prediction, `reveal(params, prediction) -> {actual, delta, explanation_hooks}`. Assessed against weir's model as a candidate case, not built here.

**Confirms, rather than newly resolves, "nodes are tools, edges are their schemas"** (this file, "The pivot"). `setup_exhibit` and `reveal` map directly onto two nodes; `setup_exhibit`'s output edge type structurally excludes `actual`, so an agent holding only that edge has no path to leak an answer it was never given — the node-contract thesis (a node can't hide what it never had) demonstrated against an adversarial case (a misbehaving or jailbroken coaching agent) rather than a synthetic one. Doesn't newly decide anything about the still-open "prose blocks on node declarations" (`open-questions.md`): `prediction_prompt` is a real, motivating instance of content that field would carry, but the example doesn't settle whether such a block is required, optional, machine-checked, or documentation-only — a concrete candidate, not evidence toward any one answer.

**Surfaces a real gap: `reveal` must read a log entry written by a genuinely separate external invocation.** "`every` lands" (this file) resolved `every:`'s readiness check as "does an A-shaped and B-shaped edge exist yet for the current `correlation_id`," and in the same entry, reasoning toward why `first`/`each` aren't needed yet, stated: *"a fresh external trigger is always a new invocation (a new `correlation_id`), never a second wave into an existing one."* `reveal` is exactly the case that line didn't have in view: a fresh external trigger — a second tool call, arbitrarily later, after the reader has actually thought about their prediction — that must resolve against the *same* `correlation_id` `setup_exhibit`'s call used, specifically so `reveal`'s `every: [ExhibitState, Prediction]` can find `ExhibitState` already in the log. If `correlation_id` is minted fresh per external trigger, as that line implies, `reveal` can never see `setup_exhibit`'s output at all, and the pattern is unbuildable on weir as currently described.

**Not a contradiction, but an unaddressed boundary — left open, not resolved here.** The quoted line was reasoning about ruling out loop-shaped recurrence within one invocation; nothing in the `every:`/log design actually required `correlation_id` to be freshly minted per trigger, that was only ever the default assumption in service of a different question. Whether `correlation_id` is framework-minted per external trigger or caller-suppliable (an agent/tool-runtime passing the same exhibit/session identifier on both calls), and what its lifetime is (one request vs. a whole multi-call tool-calling session), is real and load-bearing — moved to `open-questions.md` rather than decided here, since nothing in this conversation actually settled it, only found it.

## `mental-museum`'s answer: identity minted by the earlier node's own payload, not inherited from an origin's `correlation_id`

`mental-museum`, building its actual `setup_exhibit`/`reveal` implementation (independent of weir), landed on an answer to the gap above worth recording, even though weir didn't design it. Their fix doesn't make `correlation_id` caller-suppliable at all — it sidesteps the envelope mechanism entirely. `setup_exhibit` mints a fresh id itself (`setupId`, a `randomUUID()`) and returns it as an ordinary field on its own output payload; the stored `{params, consumed: false}` lives in a session store keyed by that id. `reveal(setupId, prediction)` requires the id as an explicit argument, looks up the stored params (never trusting params passed directly to `reveal` — that's what stops replay-with-different-params), and rejects an unknown id or a second reveal against an already-consumed one.

**Reframes the question rather than answering the one asked.** This isn't "correlation_id, but caller-suppliable" — it's identity minted by a node, carried as ordinary edge data (visible in the type, not envelope machinery), with once-only consumption enforced by the node's own logic rather than by `every:`/the log. Whether `setup_exhibit` counts as an origin node in weir's sense (its edges are handed in directly by the triggering tool call) matters here: origin nodes are already where nondeterminism is licensed to enter (this file, "The membrane"), so a fresh random id minted there isn't a new kind of exception — it's the same allowance the design already made, just producing an id instead of, say, `Std.Now`.

**One thread this doesn't resolve, left for whenever `reveal`'s edge is actually designed: what kind of thing is the session-store lookup itself.** `reveal` needing to fetch `{params, consumed}` by `setupId` is either an ordinary node (`LookupSetup: SetupId -> SetupRecord`, keeping "effects are data" intact — the lookup is itself an edge a node reads, same as any other) or a bare side effect living inside `reveal`'s own `Fn`, which would be the first crack in that rule for a non-origin node. Not decided; noted for whenever this pattern gets designed into weir for real rather than just watched from outside.

## `Failed<In>` built: a plain union, not retroactively tagged like `oneOf`

`membrane.ts`'s own header comment had carried "turning a rejection into a `Failed<In>` edge rather than a thrown error" as an explicit not-yet-built gap since "`membrane()`, first slice" (this file). Built now: a rejected `assertPayload` or an uncaught throw from `Fn` resolves `membrane()`'s returned promise to `Failed<In>` — `{ input, reason? }`, exactly §3's decided shape — instead of rejecting it. Nothing escapes the boundary as an exception. `Fn` may also construct and return `Failed<In>` explicitly, same opt-in shape `env` already has.

**The judgment call, made explicit because the docs don't pin it down.** §3 and "Failure as an edge" (this file) both describe the result loosely as "every node's real output signature is `one of {successes, Failed}`" — read most literally, that's the same tagged `{edge, payload}` shape `oneOf`/`allOf` outputs already use. Implemented instead as a plain `OutputResult<O> | Failed<In>` TypeScript union at `membrane()`'s own return type, with no tag layer added. Concretely: a `single`-output node's success value stays exactly what it always was (`birthday` still resolves to a bare `{age, nickname}`, not `{edge: "Person", payload: {...}}`) — retroactively tagging every existing single-output node's success shape to make room for a uniform `oneOf`-style `Failed` branch would have been a much larger, breaking change to a calling convention 25 existing tests and every other node already depend on, for a wire-format detail neither §3 nor "Failure as an edge" actually specifies at that level of precision — both describe the *type-theoretic* shape (a coproduct with one more branch), not the runtime tagging mechanics.

**What this leaves open, genuinely, not just deferred:** a caller can't yet distinguish "a successful `single`-output payload that happens to have a field named `input`" from "a real `Failed<In>`" by shape alone — there's no discriminant tag on `Failed<In>` itself, matching §3's literal `{ input, reason? }` and nothing more. Untested in practice since no real edge has collided on that field name yet, but it's a live ambiguity, not a solved one. Revisit if/when a real `.edge` ever wants a field called `input`, or when `.topology`/the runtime need to route a `Failed<In>` branch the same mechanical way they'd route an `oneOf` tag — that's the moment "should `Failed` actually be tagged like `oneOf`'s other branches" stops being hypothetical.

## `.topology` built: a nested `then:` map, resolving both remaining sketch gaps

`open-questions.md`'s `.topology` entry carried a real sketch already — a nested `then:` map, node name as key, fan-out as several keys under one `then:`, convergence (a node fed by more than one parent) needing no special join syntax at all — but left two things unresolved: how several independent origins sit in one file, and whether "graph" should replace "topology" as the vocabulary. Neither turned out to need real design work once looked at directly.

**Several top-level keys are independent origins.** The sketch's own "plausibly just several root keys in the same map" was the only shape that made sense once considered: nothing about a second, unrelated root key conflicts with anything already decided, and no alternative was ever seriously in play.

**Stays `.topology`, not `.graph`.** Used everywhere already — the extension itself, `design.md` §10, `getting-started.md`'s build order — with nothing raised against it beyond the word having been reached for once in conversation. Relitigating it would have been costless to avoid and pointless to do.

**Built:** `parseTopologyFile`/`Wiring` (`elaborate.ts`), extending the same load-and-validate pattern `.field`/`.edge`/`.node` already established — every node name a `.topology` file mentions is resolved against the already-loaded `.node` set, the same "Cannot resolve X" failure mode as an unresolved edge reference. No cycle detection: a repeated name (`birthday.then.birthday`) is a legitimate distinct application, not a cycle ("Weir has no loop construct," this file) — and the YAML itself is always a finite tree, so nothing can actually recurse forever regardless. `elaborate()` globs `**/*.topology` the same way it globs the other three extensions and merges however many files it finds — untested by any real fixture yet (both example directories use exactly one file each), a natural generalization of the same convention rather than a new one.

**Two real `.topology` files now exist** — `examples/person-birthday/src/topology/main.topology` (`birthday.then.expect_Person_age_42`, a straight pipe) and `examples/todo-list/src/topology/main.topology` (`CreateTodo` fanning out to both `AddTodoToList` and `CompleteTodo`) — the first real fan-out example in the repo, proving that branch of the mechanism against real files rather than only synthetic fixtures.

## The runtime, built narrow on purpose — and `Failed<In>` routing turns out to need nothing new from `.topology`

`runtime.ts`'s `runNetlist` (docs/getting-started.md step 5) walks a `Program`'s `wiring` as a worklist — a node is attempted once after each declared parent fires, firing is idempotent, and the *outcome* matches the decided pulse/wave model ("`every` lands," this file) without needing to number pulses explicitly. Deliberately narrow: `single`-output nodes only (`oneOf`/`allOf`/`many` are recorded as `unsupported`, not crashed past), and no `Failed<In>` routing — collected separately in `failures` instead of the shared `Log`, since `Failed<In>` isn't a real, named edge yet and there's nowhere honest to log it.

**Raised directly, mid-build: could a `.topology` file route a failure by just listing a handler next to the success path?**

```yaml
CreateTodo:
  then:
    AddTodoToList: {}
    HandleFailed: {}
```

**Resolved: yes, and it needs no new topology syntax at all — the gap is entirely on the edge/type side, not the wiring side.** `then:`'s readiness check already doesn't care *which* edge shows up under a parent; it only checks whether each listed child's own declared `input` is now satisfied (this file, "`.topology` built"). `HandleFailed` sitting next to `AddTodoToList` is exactly the right shape once `HandleFailed` declares `input: Failed_Todo` (or however it ends up named) — the runtime would log `Failed<Todo>` as a real edge instance on failure, and `HandleFailed` becomes ready through the identical mechanism `AddTodoToList` already uses. What's missing is only that `Failed<In>` has to become a real, *named* `.edge`-shaped thing — parameterized by the failing node's *input*, not its output, so nodes sharing an input edge (any node consuming `Todo`) could share one `Failed_Todo` edge and one handler catches failures from several different nodes uniformly. The exact same shape `Pass`/`Fail` needed as real `.edge` files before `oneOf` routing could work (`examples/person-birthday/src/edges/Pass.edge`/`Fail.edge`, added earlier this session) — not a new mechanism, the same one-more-declaration gap.

**A natural follow-on question, raised immediately after: could one `HandleFailed` node catch several different nodes' failures, rather than one handler per failing input shape?** Not `any` in the dynamic-typing sense — that would throw away the entire reason `Failed<In>` carries a typed `input` in the first place, "so a retry node has something to re-emit" (design.md §3) requires that something to actually be typed. weir's own `any:` — the still-unbuilt `InputSpec` kind, `every`'s "first of several" pair ("`every` lands," this file: "waits for the first of *several distinct* edge types... a cheap follow-on to `every`, same pulse-arrival mechanism, `min` instead of `max`") — is the real answer, and needs no new mechanism at all, just building the one already designed. `HandleFailed` declaring `input: any(Failed_Todo, Failed_Person, ...)` fires on whichever named `Failed_*` edge shows up first, each one still fully typed — one handler, several concrete failure shapes, exactly the ergonomics wanted without inventing anything past what "`every` lands" already spec'd out.

**Not built now — the natural next increment, not this one.** Doing it would mean: deciding how `Failed<In>`'s edge name is derived from the failing node's input edge (a naming convention, not just a mechanism), teaching the elaborator to synthesize that edge automatically per declared input shape rather than requiring it hand-authored, actually building `any:` (still just designed, per "`every` lands"), and teaching `runNetlist` to log a `Failed<In>` result under the synthesized name instead of `failures`. Left for whenever `Failed<In>` routing is actually being built, not invented in passing here.

## `many` is a collection, keyed by index, not an array

Building `oneOf`/`allOf`/`many` output routing into `runtime.ts` surfaced a real, previously undecided question: `many`'s runtime shape. `Payload<F>`/`OutputResult<O>` had it as a bare `PayloadOf<E>[]` since "Compound fields embed literally" first built `many`, never revisited.

**Resolved: `many` is a collection keyed by the referenced edge's own declared `index` field — `Record<string, PayloadOf<E>>` — never a positional array.** Raised directly: `given`/`expect` were already deliberately keyed by edge *name* over `Tagged<E>[]`-shaped arrays for `oneOf`/`allOf`, specifically because "an array of wrapper objects" was worse than a name-keyed object ("`.node` examples become required..." this file). `many` is a different case — N instances of the *same* edge, not several different ones — but the same instinct against bare arrays applies, and `EdgeDef.index` — "the field that uniquely identifies an instance, where one exists," already load-bearing in `hash.ts`'s fingerprint — was already sitting there unused as exactly the right key.

**A collection is never N separate edge instances, either.** The natural-seeming alternative — a `many`-output node produces N separate instances of the referenced edge, each logged individually — was never built and turns out to be the wrong shape entirely: it would have required `Log` to hold multiple values per `(edgeName, correlationId)`, a real capability gap `runtime.ts`'s design had been carrying since first built. Resolved instead as "one edge, one collection payload" — a `many`-output node produces exactly one edge instance whose payload happens to be a collection, logged with the same single `log.append()` call `single`/`oneOf`/`allOf` already use. `InMemoryLog` needed no change at all.

**`index` is now required wherever an edge is used inside a `many`** — a many-referenced edge with no declared index is an elaboration-time error (`elaborate.ts`'s `requireIndex`, both the field-level `many:` and the node-output `output: {many: ...}` cases), not a silent fallback to a synthetic key. A synthetic key (a fresh UUID per instance) was considered and rejected: it would have bought nothing over the array it was replacing, since a key nobody chose carries no more meaning than a position does. Cost: `Todo.edge` (`examples/todo-list`) needed an `id` field it didn't have — the same shape of gap-closing as `Pass`/`Fail` needing real `.edge` files earlier.

**One real subtlety, caught by a test rather than assumed away: object keys are always strings, even when the index field's own type isn't.** A `uint8` index field valued `8` stores under the collection key `"8"`, not `8` — `assertPayload`'s consistency check (does the entry's key match its own index-field value) compares by string form for exactly this reason, confirmed against a numeric-index fixture before trusting it.

## `Failed<In>` routing built, for `single`-input nodes — the plan from last time, done

The plan this file already recorded ("The runtime, built narrow on purpose... `Failed<In>` routing"): give `Failed<In>` a real name in the edge system, teach the elaborator to synthesize it automatically, teach the runtime to log a failure under that name instead of `failures`. Built, minus `any:` itself (still just designed, not this entry's job).

**Naming convention: `Failed_<EdgeName>`**, one per declared edge, shared by every node that fails on that same input — `failedEdgeName()` (`types.ts`), a single named function `elaborate.ts` and `runtime.ts` both call, so the synthesis side and the logging side can never drift out of sync with each other.

**`elaborate()` synthesizes one `Failed_<EdgeName>` edge per declared edge, unconditionally** — `{ input: <edge>, reason }` — right after `.field`/`.edge` resolution finishes, before `.node` files are parsed. Considered scanning nodes for which edges are actually used as some node's input and synthesizing only those; rejected for a real reason, not just simplicity: it would need two passes over `.node` files (discover input edges, then resolve `input: Failed_Todo` references against edges that don't exist until the first pass completes), where synthesizing for every edge sidesteps the ordering problem entirely and costs nothing but a few extra in-memory `EdgeDef`s. Iterates a snapshot of `edges` taken before synthesis starts, so a synthesized edge never grows its own `Failed_Failed_*` counterpart.

**`runtime.ts` routes a `single`-input node's failure to `Failed_<InputEdgeName>` instead of `failures`** — the exact same `log.append` a success would get, so a downstream node declaring that edge as its own `input` becomes ready through the identical readiness mechanism `AddTodoToList` already uses, no new routing logic needed (confirmed directly: a `handleFailed`-shaped node consuming `Failed_Start` fires once `failing`'s failure is logged, in the same worklist pass). The worklist already re-checks a fired node's children regardless of whether it succeeded or failed — `tryFire` returns `true` either way — so this needed no scheduling change, only where the result gets logged.

**`every`-input `Failed<In>` still collects in `failures`, unrouted — a real, separate next increment.** Its bag shape (`{A: ..., B: ...}`) doesn't have a natural single-edge name the way a `single`-input node's `Failed<In>` does; giving it one is a genuinely different design question (per-edge-combination synthesis? a bag-shaped edge type that doesn't exist yet?), not a small extension of what got built here.

**Left exactly where the plan said it would be: `any:` itself.** One handler catching several different nodes' failures (`input: any(Failed_Todo, Failed_Person, ...)`) still needs `any:` actually built, not just designed. Nothing here moved that forward.

## `assertPayload` now enforces `validations`/`enumValues`, closing the gap the previous entry's own test surfaced

The `AddTodoToList`-failure test above, in the course of proving something else, incidentally proved `assertPayload` was weaker than it looked: `Todo.edge`'s `title` declares `minLength: 10`, but only a wrong-*typed* value rejected — a too-short string sailed through untouched. Not a broken promise (design.md never claimed runtime enforcement, only that `validations` are structural for hashing and generator specs for property tests, §6) but a real gap, recorded in `open-questions.md` and closed the same session.

**Built: `validationErrors()` (`membrane.ts`), called once a scalar's type already checks out.** Numeric fields get `min`/`max`; string fields get `minLength`/`maxLength`/`pattern`; any field with `enumValues` gets checked against it regardless of the other two. Collected into the same `errors` array everything else already accumulates into — a `minLength` violation and a wrong-typed sibling field both show up in one thrown message, same "list every violation" discipline `assertPayload` already had for type/nullability.

**Immediately caught something else: the repo's own example data had been silently invalid the whole time.** Every real `.node` example file in `examples/todo-list` used `"Buy milk"` (8 characters) as a `Todo.title`, violating the `minLength: 10` `Todo.edge` itself declares — nobody had noticed, because nothing had ever checked. Turning enforcement on made `CreateTodo`'s own hand-authored example fail against its own edge's declared rule the moment a real end-to-end test exercised it. Fixed to `"Buy milk and eggs"` across all three `.node` files and the equivalent test fixture — the same shape of latent staleness this session already found twice (the stale `node.schema.json`, `AddTodoToList.node`'s pre-`every:` YAML), each time only surfaced by actually running something real against the file, never by reading it.

## `.topology` gets a generated JSON Schema, closing the last gap in editor tooling

`schema.ts` already generated JSON Schema for `.field`/`.edge`/`.node`; `.topology` was the one file kind still validated by nothing but `parseTopologyFile` itself throwing at elaboration time. `topologySchema()` closes it, recursive via `$defs/topologyNode` since the nested `then:` map has no fixed depth — a node is `null`, or an object whose only recognized key is `then:`, whose value is a map of more of the same. Matches `parseTopologyFile`'s own rules exactly: `then` is the only key at any level, a leaf is `null` or `{}`, fan-out and multi-parent convergence both fall out of the same recursive shape with no special-casing.

**What it still can't check, same limitation `nodeSchema()` already has:** a `.topology` file mentioning a node name that no `.node` file declares. Cross-file name resolution needs `elaborate()`'s actual information, not just the shape of one file in isolation — the same "confirmed harder than hoped, not softened" conclusion reached twice already for `.node`'s `input`/`output` names. Verified against both real `.topology` files (`examples/person-birthday`, `examples/todo-list`) before wiring it into `.vscode/settings.json` and `scripts/generate-schemas.ts` alongside the other three.

## `any` built: the coproduct-shaped `InputSpec` sibling `every` left on the table

"`every` lands" (this file) already named `any` as "a cheap follow-on to `every` (same pulse-arrival mechanism, `min` instead of `max`), left out of this pass only because it wasn't the thing actually asked for." Built now, mirroring `every`'s own implementation file-for-file (`types.ts`'s `InputSpec`/`InputPayload`, `define.ts`'s `any()`, `membrane.ts`, `elaborate.ts`'s `resolveInputSpec`, `schema.ts`'s `nodeSchema()`) rather than inventing a new pattern.

**Payload shape settles the one real design choice this needed: `any` is input's `oneOf`-shaped sibling, not another `every`-shaped bag.** `every`'s payload is a name-keyed bag because every declared edge is guaranteed present by the time `Fn` runs; `any` guarantees only one of several distinct edges showed up, so `Fn` needs to know *which* — resolved as the same `{edge, payload}` tag `oneOf`'s output already uses (`Tagged`, `types.ts`), not a new shape. This completes a symmetry that was already implicit: `every`/`any` are `allOf`/`oneOf`'s input-side counterparts, product and coproduct on both sides of a node now.

**`membrane()`'s `any` branch scans declared edges in the same order `every` already iterates them, but stops at the first one whose log entry exists** rather than requiring all — the literal "min instead of max" the design conversation named. A real but rare race — more than one declared edge already logged by the time the check runs — resolves deterministically to the first in declared order, an implementation judgment call rather than a modeled decision, consistent with `every`'s own check-in-order convention.

**`runtime.ts` needed no logic change at all** — confirmed directly, not assumed: the worklist's existing non-`single` branch already calls `membrane()` with `(correlationId, log, identity)`, the exact shape both `every` and `any` share, so an `any`-input node fires through the identical mechanism the moment it's wired in. Only a naming cleanup followed: the cast-helper type `AnyEveryInvoke` (TS `any`-cast + `EveryInvoke`, predating this work) now collided in name with the real `any` InputSpec kind, renamed `AnyMultiInvoke`. `any`-input `Failed<In>` — tagged, not bag-shaped — has the same no-synthesized-edge gap `every`-input `Failed<In>` already had, and lands in the same unrouted `failures` list for the same reason (`elaborate.ts`'s `synthesizeFailedEdges` stays single-input only).

**Scoped to the mechanism plus unit tests mirroring `every`'s own test files** (`membrane.test.ts`, `elaborate.test.ts`, `schema.test.ts`, `runtime.test.ts`) — deliberately not extended into a real `examples/todo-list` fixture (a `HandleFailed`-shaped node consuming `any(Failed_Todo, Failed_...)`, the concrete case "The runtime, built narrow on purpose..." (this file) describes) the way `every`-input `Failed<In>` routing was proven against real files. That end-to-end proof, and `any:`'s use to let one handler catch several different nodes' failures, are left for whenever `Failed<In>` routing actually gets extended to cover `every`/`any`-input nodes — this pass only builds the `InputSpec` kind itself.

**A live question, worth flagging even though it wasn't resolved here:** is `any` even the right name for what got built, or should the breadth-of-several-distinct-edges kind be called `first` instead — leaving `any` for something else, or nothing? Recorded as its own entry in `open-questions.md` ("Is `any` actually the right name...") rather than decided or renamed in passing; `any` ships as named until it gets dedicated attention.

## `every`-input `Failed<In>` routed — a synthesized bag-shaped edge, `any`-input's still doesn't get one

The gap this file's own previous entry named directly ("every-input `Failed<In>` still collects in `failures`, unrouted — a real, separate next increment... giving it one is a genuinely different design question: per-edge-combination synthesis? a bag-shaped edge type that doesn't exist yet?") gets resolved: per-edge-combination synthesis, no new field-model capability needed.

**The `any`-input half of that same original gap turns out to be a different, harder problem, so this pass deliberately narrowed to `every` only** — raised directly mid-design (thinking of `any` as membrane switching over a handful of shadow single-input consumers): an `any`-input node's *success* path genuinely needs the `{edge, payload}` tag (`Fn` has to know which of several distinct edges fired), but that's a discriminated union — weir's field model has no variant/tagged-union field type, only fixed compound shapes, so it can't be synthesized as a real edge the way `every`'s fixed-shape bag can. (A cheaper fix exists — reuse the already-synthesized single-input `Failed_<Edge>` for whichever edge actually matched, dropping the tag at the logging layer rather than the type layer, since `Failed<In>`'s TS contract only binds what `membrane()` returns to its direct caller, not what `runtime.ts` chooses to log it as — but that's real, separate work, deliberately deferred rather than folded in here to keep this pass to one mechanism.)

**Naming: `Failed_<A>_<B>`, names sorted alphabetically before joining.** `every`'s own readiness check treats its declared edges as a set, not a sequence — `every(A, B)` and `every(B, A)` are the same requirement — so the synthesized edge has to be order-independent too, or two nodes declaring the same combo in different orders would each get their own, wrongly-distinct `Failed_*` edge. `failedEveryEdgeName(edges)` (`types.ts`) sorts before joining, named once and shared by `elaborate.ts`'s synthesis and `runtime.ts`'s routing, mirroring `failedEdgeName`'s existing single-input convention exactly.

**Shape: flat fields, no `input` wrapper** — `Failed_A_B` gets `{A: <embed>, B: <embed>, reason}` directly, not `{input: {A, B}, reason}`. `every`'s bag payload is already a fixed multi-field shape once it fires (all declared edges guaranteed present), so each field can just embed its own edge literally — the same "a field can be a whole embedded edge" capability `Failed_<Edge>`'s `input` field already used for the single-input case, applied once per combo member instead of once. No new field-model work, just the existing mechanism used N times in one edge instead of once.

**`elaborate()` can't synthesize combo edges unconditionally the way `synthesizeFailedEdges` synthesizes one per plain edge** — every possible subset of declared edges is a powerset, not a linear scan, so which combos exist has to be discovered by actually looking at what's declared. `elaborate()`'s single read-and-parse loop over `.node` files split into three steps: read all `.node` text into a map first, a raw pre-scan of just each file's `input.every` (plain YAML, no full resolution) to collect distinct combos keyed by sorted edge names, `synthesizeEveryFailedEdges` for whatever that pre-scan found, *then* the real `parseNodeFile` pass over the same already-read text — so a `.node` file can legally declare `input: Failed_A_B` and have it resolve, the same way `input: Failed_Todo` already could for the single-input case.

**Proven against the real `examples/todo-list` files, closing the loop `9ce2506` opened** ("Prove every-input `Failed<In>` stays unrouted, against the real todo-list files") — the same malformed-`Todo` fixture that previously proved the failure landed unrouted in `failures` now proves it routes to `Failed_Todo_TodoList` instead, `failures` empty.

## `any` comes back out: it was never a runtime primitive, just sugar wearing one — and `every` becomes `allOf` to match

Built in `6d2558c`, `any` gave `Fn` a `{edge, payload}` tag and a real `AnyInvoke`/`membrane()` branch for the first of several distinct edges to arrive. Working through a concrete use case — `any(Bird, Turtle, Dog) -> Animal`, a widening node — surfaced that the tag was never load-bearing: decomposed into `WidenBird: single(Bird) -> Animal`, `WidenTurtle: single(Turtle) -> Animal`, `WidenDog: single(Dog) -> Animal`, each node is fully typed with no runtime discriminant, closer to "no ambient dispatch" than a single `Fn` internally branching on a string tag. `elaborate()` now desugars a `.node` file's `input: {oneOf: [...]}` into N ordinary single-input `NodeDecl`s at parse time (`parseOneOfNodeFile`), named `<Name>__<EdgeName>` (double underscore — edge names already contain single underscores, `Failed_Todo_TodoList`), never surviving into the runtime `InputSpec` union at all.

**Renamed `any` to `oneOf`, not kept and not renamed to `first`.** `any` collides with TypeScript's own `any` — homonymy, not a real semantic relationship. `first` was floated and dropped: it implies exclusivity ("the winner"), which doesn't match the real desugared behavior (next paragraph). `oneOf` won as `oneOf`'s own dual on the input side — `single` already proves "same word, different mechanism by position" is a pattern this project is comfortable with, and `output: oneOf: [Pass, Fail]` was already real YAML before this change (`examples/person-birthday`).

**A real behavior change surfaced along the way, not just a rename.** The old `any` was one node with one `fired` entry — first edge to arrive wins, the other is silently ignored forever if it later shows up too. Desugared into N separate nodes, each tracked in `fired` independently, both fire if both edges genuinely occur in one invocation. This is a correction, not an accepted regression: the old behavior silently dropped a real failure if two distinct `Failed_*` edges both occurred. An exclusive "first wins" primitive, if ever genuinely needed, is separate, new work — not preserved here.

**`.topology` needed a real mechanism, not just a naming change, to keep the original name writable.** `runtime.ts`'s worklist only attempts a node when something pushes it via `wiring.feeds` — never a periodic scan — so a desugared shadow needs `.topology` to reference it, directly or aliased, or it never fires even once its input is logged. `NodeNameResolver` changed from `(name) => void` (validate-or-throw) to `(name) => string[]` (resolve-and-expand); a `.topology` reference to the original name — as either a `then:` parent or a child — expands to all its shadows uniformly. Deliberately imprecise: a shadow gets redundantly checked from a parent that could never actually produce its edge, and that's fine — `tryFire`'s own readiness check and the `fired` set make a wasted attempt free.

**Also resolved the `any`-input `Failed<In>` gap this same work had deferred** (`c9d3676`: "any-input `Failed<In>`... still collects in `failures`, unrouted") — for free, not as separate work: after desugaring, every former `any`-node is an ordinary single-input node, and its failures already route through the mechanism built for that case.

**A real, previously-unnoticed bug surfaced and closed along with the primitive:** `hash.ts`'s `fingerprintInput` had no `any` case and silently mis-fingerprinted an `any`-input node as `every`. Moot now — no node ever carries a tagged-union input kind to mis-fingerprint.

**`every` becomes `allOf`, completing the symmetry — pure rename, no behavior change.** `every` (input) and `allOf` (output) already meant the same thing; `allOf`'s own doc comment was always "every listed edge fires." They carried different names purely by build order — `every` existed before `oneOf`/`allOf` did as output kinds to mirror. `single`↔`single`, `oneOf`↔`oneOf`, now `allOf`↔`allOf`. `define.ts`'s `every()` was deleted outright rather than renamed: confirmed the existing output `allOf()` is already structurally identical to what the input side needs, so both positions share one function, same as `single` already does.

**Two other rename candidates were tried and rejected for colliding with weir's own vocabulary, not just external ones.** `spread` is already load-bearing for `.edge` field-map composition (design.md §2) and already the candidate name for a different open question (`open-questions.md`, "partial input, partial node-pinned default") — reusing it a third way would have been worse than the collision it was meant to avoid. `poly` collides softer, with weir's existing parametric-generics "polymorphism" (`Animal<T>`) — a different kind of polymorphism than "several unrelated concrete types."

## Input `oneOf` corrected to `anyOf`, same day as the rename that introduced it

Spot-checked independently — a second conversation, working from the same repo state, reached the same conclusion without seeing this file. Output `oneOf` (`types.ts`'s `OutputSpec`, untouched by any of today's work) is a real coproduct: `OutputResult` for that kind is a union type, `Fn` returns one value, so the type system guarantees exactly one branch every call — matching JSON Schema's own `oneOf` keyword ("exactly one subschema validates"), which `schema.ts` already uses natively elsewhere in the same file. Input `oneOf` (built earlier today, "`any` comes back out," this file) does not carry that guarantee: it desugars into N independent single-input nodes with no cross-shadow exclusivity, by deliberate design — if two listed edges both occur in one invocation, both shadows fire. The group produces zero, one, or up to N firings, never a guaranteed one. That's JSON Schema's `anyOf` ("one or more validate"), not its `oneOf`.

**Traced to one sentence in that entry's own reasoning:** "`oneOf` won: it's `oneOf`'s own dual on the input side (a coproduct — exactly one of several concrete types is relevant per firing)." "Per firing" is true of any individual shadow in isolation — each shadow's own input genuinely is exactly one edge type — but the analogy was drawn at the wrong grain: it doesn't hold for the group across firings, which is the property that actually matters for the word "coproduct" to apply.

**Resolved naming matrix**, settled directly:

| | input | output |
|---|---|---|
| `allOf` | all must be present | all fire |
| `anyOf` | one or more may fire, independently | — |
| `oneOf` | — | exactly one fires |

`allOf` stays genuinely dual, same as `single` — one word, one meaning, either position. `anyOf` and `oneOf` are not: each is single-position only after this correction, and deliberately so — there is no coherent "output anyOf" (`Fn` returns exactly one value per call, so "zero or more of these may fire" has no output-side meaning the way it does for independent input-side node firings), so none was built.

**Pure rename, smaller in scope than `every`→`allOf` or the `any`→`oneOf` desugaring itself** — full spec at `docs/superpowers/specs/2026-08-31-oneof-input-becomes-anyof.md`. `parseOneOfNodeFile`→`parseAnyOfNodeFile`, `defineOneOfNodes`→`defineAnyOfNodes`, `oneOfAliases`→`anyOfAliases`, `schema.ts`'s input-position conditional/property key. Never touched `types.ts`, `membrane.ts`, `runtime.ts`, or `hash.ts` — input `oneOf` never became a runtime `InputSpec` kind in the first place, so none of them ever knew its name to begin with.

Full design at `docs/superpowers/specs/2026-08-31-any-desugaring-design.md`.

## `closure` renamed to `fixed`; `pin` closes "partial input, partial node-pinned default"

**The rename was surfaced by a reader, not by re-deriving the design.** `closure` borrowed only the verb from general-programming closures ("a node closing over a literal," `examples/person-birthday/README.md` decision 4, which already flagged the choice as "more invention than transcription from the docs") — dropping the function value, the deferred invocation, and the captured environment that make a closure a closure, keeping only "a value got fixed at some point." A reader with a standard CS background read `closure` and expected an unsaved/immediately-invoked function, correctly, since that's what the word means everywhere else. `fixed` says the true thing directly. Pure rename: `NodeDef.closure` → `NodeDef.fixed`, `ExpectClosure`/`LiteralClosure` → `ExpectFixed`/`LiteralFixed`, same shapes, same behavior.

**`pin`, the third `fixed` kind, resolves the open item directly** (`open-questions.md`, "Partial input, partial node-pinned default" — `CreateTodo.node` forcing a caller to supply `is_complete`, which should always start `false`). `spread` and `poly` were already noted, above, as rejected candidate names for this same open question during the `every`→`allOf` work; `pin` was not among those candidates and doesn't collide with either. `fixed.pin: Partial<InputPayload<In>>` (single-kind input only) names which fields of a node's input edge the node itself supplies — those fields disappear from what a caller may pass in `given`/an invocation, and must appear in `expect` matching the declared pin exactly. Deliberately declarative-only, matching how `expected`/`literal` already work: no runtime injection, `Fn`'s type is unchanged, `Fn` is trusted (and example-checked) to actually produce the pinned value. This is why the `Todo` edge itself never needed a `CompletedTodo`-style literal-pinned sibling for this case — `is_complete` must stay a real mutable bool at the edge level (`CompleteTodo.node` flips it later on the same edge); the pin belongs to `CreateTodo` specifically, not to `Todo` generally.

**A `method`/`fixType` discriminant tag alongside the data (`fixed: { method: "pin", is_complete: false }`) was considered and rejected**, for two concrete reasons past style preference. It puts the discriminant in the same namespace as real field names, so an edge with a field literally called `method` couldn't be pinned without a key collision — nesting under `pin:` keeps the tag and the data in disjoint namespaces unconditionally. And it requires every reader of `fixed` (`hash.ts`, `netlist.ts`, the elaborator) to strip the tag key before treating the rest as `Partial<InputPayload<In>>`, where nesting needs no such filtering — the value at `fixed.pin` already *is* the shape it claims to be. Same reasoning `output`'s `oneOf`/`allOf`/`many` already settled on (key presence as the discriminant, no separate `kind:` property) — `fixed` just applies it a second time, keeping the file format's one idiom instead of adding a competing one. Checked against a relational-modeling framing too: a `fixed_type` enum column plus one generic payload column is the classic polymorphic-association pattern, and carries its classic weakness — the type column and the payload column are two facts that can drift out of agreement, with nothing in the schema stopping it. Three mutually-exclusive nullable columns (one per kind, `CHECK` at most one non-null) is the direct relational shadow of nesting-by-key: which column is populated *is* the type fact, nothing else to disagree with it. The usual cost of that pattern — doesn't scale if the variant set grows often, each new kind is a migration — doesn't bite here, since `fixed` is a small, closed set of three structural node roles (origin / assertion / partial-default), not an open-ended one.

Full spec at `docs/superpowers/specs/2026-09-09-fixed-pin-node-defaults.md`.

## `pin` reconsidered, same day — paused in favor of trying spread-built edge variants first

Reviewing the spec above surfaced the question it had already named but not weighed seriously enough: `pin` versus a second, nominally distinct edge built with spread (`edge TodoInput { ...Todo, is_complete: false }`), the same fork the spec's own Motivation section raised and set aside in one sentence. Worth re-raising because the `pin`/`fixed` design had by this point grown substantially past its original size (a rename touching seven source files plus examples, three rounds of naming for the wrapper key, a considered-and-rejected restructuring to nest `bind` under `input`/`output`) — proportionate to weigh the alternative again with that real cost now visible, not just estimated up front.

**Checked, not assumed: spread (`...Todo`) is designed but not built.** `design.md` §2 decides it; `schema.ts`'s `literalFieldShape()` doc comment and this file's own `CompletedTodo` example use it as motivating shorthand throughout — but no code anywhere parses a `...`-key in a `.edge`'s `fields:` map. `edgeSchema()`'s field-value `oneOf` recognizes exactly four shapes (bare-string reference, typed field, `{ many }`, literal) and none of them is spread. This means neither path is free: `pin` was ready to implement; a second-edge-via-spread path first needs spread itself built.

**Decision: pursue spread → a second, nominally distinct input edge, first.** Preferred as more declarative and a cleaner separation of concerns — `CreateTodo`'s creation-shaped input becomes its own real, named edge (a candidate term floated: "edge variant"), not a narrowing annotation bolted onto an existing one. This also directly extends an already-decided need: `CompletedTodo`/`IncompleteTodo` as nominal lifecycle refinements (this file, "A literal field type, for branching without narrowing shape") wants the same spread mechanism, so building it once serves both cases rather than just this one.

**`pin` is paused, not abandoned** — the design and its implementation plan stay as written (`docs/superpowers/specs/2026-09-09-fixed-pin-node-defaults.md`, `docs/superpowers/plans/2026-09-09-fixed-pin-node-defaults.md`), marked paused, worth revisiting once spread exists and `CreateTodo` is rebuilt on it — if a case turns up that spread genuinely can't reach (something that has to narrow a *node's* input specifically, not an edge's shape), `pin` is already fully designed for it. `open-questions.md`'s "partial input, partial node-pinned default" item is restored, not left resolved, since nothing has shipped yet either way — updated to record this session's direction.

The `closure`→`fixed` rename is unaffected by this — it was motivated by the name itself being misleading, independent of whether `pin` ships, and `expected`/`literal` still need a home key regardless of how `CreateTodo` ends up solving its own problem.

## Spread built, `literal` wired up for real, and a fix wave that caught two silent bugs

Two long-decided-but-never-built pieces landed together. **Spread** (`...Name:` inside a `.edge`'s `fields:` map) was decided in `design.md` §2 the day this file's own "seed" section talks about, and every design-history entry about `literal` since ("A literal field type, for branching without narrowing shape", "`pin` reconsidered, same day") used `edge CompletedTodo { ...Todo, is_complete: true }` as its motivating example — but nobody had actually written the parser for it. `elaborate.ts`'s `parseEdgeFile` now scans a `.edge` file's `fields:` for a key matching `/^\.\.\.(.+)$/` before its normal per-key loop runs: zero matches is unchanged behavior, more than one throws (`"fields" may spread from at most one source, found N"`), exactly one resolves the named source edge through the same `FieldResolver` a bare-string field reference already uses, rejects it if the resolved thing isn't an edge (`!("fields" in resolved)`, the same shape `many:` already checks for the same reason), and seeds the new edge's fields from the source's own `fields` before any locally-declared key gets applied on top — so a same-named local key replaces the source's field whole-value, regardless of where it's written in the YAML. `index` inherits from the spread source when the local file doesn't declare its own, the one piece of behavior not discussed explicitly before writing the spec (`docs/superpowers/specs/2026-09-09-edge-spread.md`) — losing an inherited `index` by default would have been a real, easy-to-miss correctness regression on every spread-built edge with an identity field, not a neutral omission. Deliberately **single-source only** — `{ ...A, ...B }` is a parse error — matching Rust's own struct-update syntax (`..a`, never two) and sidestepping the diamond problem (whose field wins on a name collision between two sources) rather than inventing a resolution rule for it. The TS-level `defineEdge` API needed no new code at all: plain object spread (`{ ...Dough.fields, done: ... }`) already does exactly this, confirmed while writing the spec, because `Dough.fields` is already an ordinary JS object.

Applied to the real fixtures, not just tested in isolation: `examples/recipe/src/edges/BakedCookies.edge` and `Cookies.edge` had hand-duplicated `title`/`servings` verbatim across three files despite `Dough.edge`'s own description calling them "the same dish... one real stage further along." `BakedCookies.edge` is now `fields: { "...Dough":, done: {type: bool, ...} }`; `Cookies.edge` is now `fields: { "...BakedCookies":, done: true }`. `Recipe.edge` stays untouched and outside the chain on purpose — it carries `temperature`/`ingredients`, which `mix` consumes/transforms rather than passes through, so spreading it into `Dough` would pull in fields that don't belong there. Not every edge in a lifecycle needs to be in the spread chain, only where the shape is genuinely a superset.

**The syntax decision, recorded plainly rather than left ambiguous:** a spread key is `...Dough:` with an empty (`null`) value — YAML's plain "key with nothing after the colon" shorthand, never the bare `...Dough` with no colon (not valid YAML inside a mapping) and never a non-null value (a validation error, not silently ignored — see below). The shipped fixtures write the quoted form, `"...Dough":`. That's a defensive choice, not a parsing necessity: verified directly during this same fix wave, against the actual pinned `yaml` package, that the unquoted `...Dough:` parses to the identical AST (`{"...Dough": null}`) as the quoted form — three dots followed immediately by more characters on the same line is a distinct token from YAML's reserved bare `...` document-end marker, which requires nothing else on that line. Quoted is simply the convention that shipped; treat it as the house style rather than inferring one is required.

**The `literal` field kind got the same treatment** — designed in the same earlier session as spread (`schema.ts`'s `literalFieldShape()` already validated the YAML-authoring shape) but, like spread, never wired past that one layer. This branch adds `LiteralFieldDef` to `types.ts` (`{ literal: boolean; label?; description? }`, folded into `EdgeDef`/`AnyEdgeDef`/`Payload`'s field-value unions alongside `FieldDef | AnyEdgeDef | ManyEdgeDef`), `defineLiteral` to `define.ts` (an identity helper, same "define and return unchanged" shape as `defineField`/`defineEdge`), and real recognition in `elaborate.ts`'s `parseEdgeFile` for both the bare-boolean sugar (`is_complete: true`) and the explicit `{ literal: ... }` object form.

**A real, previously-silent bug surfaced and got fixed as part of wiring `literal` into hashing.** Before this branch, `hash.ts`'s `fingerprint()` had no `literal` branch, so a literal field fell into the generic scalar case and fingerprinted as `{ type: f.type }` — with `f.type` simply `undefined`, since a `LiteralFieldDef` has no `type` at all. That's indistinguishable from a malformed scalar field, and worse, it means two edges differing only in a literal field's pinned value (`{ literal: true }` vs. `{ literal: false }`) hashed identically — schema drift detection would silently miss exactly the change it exists to catch. Fixed by giving `fingerprint()` a real `"literal" in value` branch, `{ literal: value.literal }`, checked before the fields fall through to the scalar case.

**A second, structurally identical gap was caught by the whole-branch review after all four planned tasks had already landed individually clean — this fix wave's actual reason for existing.** `membrane.ts`'s `assertPayload` discriminates every field the same three ways `fingerprint()` used to (many / compound edge / else-scalar) and never gained a fourth branch for `literal` alongside it — a literal field fell through to the scalar branch, which calls `typeofFor(field)`, which has no `"literal"`/pinned-boolean case and defaults to `"number"` for anything that isn't `utf8`/`datetime`/`bool`. Concretely: asserting a real `{ literal: true }` field against a matching `{ is_complete: true }` payload produced a confusing `is_complete should be number, got boolean` error instead of accepting it. Currently unreachable from anything in `examples/` — no `.node` file in this repo declares an input edge carrying a literal field yet — but a real, load-bearing gap the moment one does, and this branch's own `Cookies`/`BakedCookies` chain (a literal field, `done`, sitting right there in `Cookies.edge`) makes it an easy trap for whatever gets built on top of this branch next. Fixed the same way `hash.ts` was: `assertPayload` now checks `"literal" in fieldDef` before falling into the scalar branch, comparing the payload value against the pinned constant directly and reporting `<key> is pinned to <value>, got <describeType(value)>` on a mismatch — a clear rejection, not a wrong-typed one. `assertPayload`'s own doc comment, which claimed the "same recursive discriminant... as hash.ts's fingerprint()" back when both functions only had three branches, is corrected to name the real fourth branch on both sides.

Full spec and plan: `docs/superpowers/specs/2026-09-09-edge-spread.md`, `docs/superpowers/plans/2026-09-09-edge-spread.md`.

## `CreateTodo` rebuilt on spread — the case that started all of this, finally closed

The previous entry's prediction landed almost immediately: "no `.node` file in this repo declares an input edge carrying a literal field yet... a real, load-bearing gap the moment one does." `CreateTodo.node` is now exactly that node.

**The original open question, closed for real.** `open-questions.md`'s "partial input, partial node-pinned default" item — `CreateTodo.node` forcing a caller to supply `is_complete`, which should always start `false` — is what started the whole spread/`fixed.pin` exploration two days ago. Spread got built and proven against `examples/recipe` first, deliberately, before circling back to the case that actually motivated it (`design-history.md`, "`pin` reconsidered, same day"). This entry is that circle-back.

**`NewTodo`, a spread-built edge, not a node-scoped narrowing.** `edge NewTodo { ...Todo, is_complete: false }` — spreads `Todo`'s full shape, then pins `is_complete` to a literal `false`. `CreateTodo.node`'s `input` moves from `Todo` to `NewTodo`; `output` stays `Todo`, unchanged. `Todo` itself is untouched, so `CompleteTodo` (which still needs `is_complete` as a real mutable bool) keeps working exactly as before — the same reasoning that ruled out pinning the field on `Todo` itself back when this was first raised.

**A field pinned via spread still crosses the wire — it's constrained, not removed — and that turns out to be the better outcome, not a compromise.** `fixed.pin`'s design would have made `is_complete` disappear from what a caller supplies at all. Spread's `NewTodo` keeps the field present, but only ever valid as `false`. Concretely: `CreateTodo.node`'s example still writes `is_complete: false` in its `given`. The upside, not available to `fixed.pin`'s declarative-only design: because `membrane.ts`'s `assertPayload` now has a real `literal` branch (previous entry), a caller who tries `is_complete: true` is rejected outright at invocation — `NewTodo: is_complete is pinned to false, got boolean` — proven by a new `runtime.test.ts` case against the real `examples/todo-list` fixtures. `fixed.pin` was explicitly scoped to never get this (docs/superpowers/specs/2026-09-09-fixed-pin-node-defaults.md's "declarative only, matching expected/literal's current level of enforcement" — written before `membrane.ts` had that enforcement to match). Spread ends up stricter than the mechanism originally designed to solve this, for free.

**`CreateTodo`'s existing implementation needed no change at all.** Because `NewTodo` spreads the *entirety* of `Todo` (not a narrower subset), the two edges are structurally identical at the payload level — same fields, same types, the only difference is `is_complete`'s `FieldDef` being a `literal` on one side and an ordinary mutable field on the other, and `Payload<F>` maps both to plain `boolean`. The pre-existing identity `Fn` (`(payload) => payload`) and the pre-existing `runtime.test.ts` integration test both kept working unmodified. This is the same "no proliferation" property spread was chosen for over a node-scoped mechanism in the first place, now paying off concretely: the caller-facing contract tightened without touching the node's own logic.

`fixed.pin` (docs/superpowers/specs/2026-09-09-fixed-pin-node-defaults.md) stays parked, not deleted — a real design for the case spread can't reach (narrowing a *node's* own input independent of any edge's shape), should that case ever actually turn up. It hasn't yet.

## Sealed contract export and implementation metadata — the isolation boundary, made concrete

**Where this came from.** Talking through weir's eventual authoring surface — humans designing edges/nodes, a separate isolated agent writing each `Fn` — surfaced that "the human doesn't write node bodies" (this file, "The pivot's authorship line, corrected") had already been revised from a structural claim to an unenforced stance, for the same reason any soft convention drifts: ontology-reasoning and implementation-reasoning shared one continuous context, so nothing actually stopped one leaking into the other. Genuinely isolating the implementing agent — fresh context, no session history, no visibility into *why* the ontology was shaped this way — turns that into a real, enforced property, and gives it a real test: if an isolated agent, given only the contract, produces a correct implementation, that's evidence the contract was complete; if it can't, that's a signal about the *declaration*, not the agent. Separately, a LinkedIn post (Hugo Matinho, a CRAP-metric — `complexity² × (1−coverage)³ + complexity` — Kiro skill for flagging risky AI-generated code) prompted the complementary question: what's worth recording *about* an accepted black box, purely as analytics, without turning it into something agents optimize against.

**`exportContract`, the sealed payload.** A pure function (`contract.ts`) producing exactly what crosses the isolation boundary — full input/output edge shapes, description, examples, `closure`, `scope`, and the `Failed<In>` shape `Fn` may always return instead — and nothing about topology, sibling nodes, or design rationale. First implementation reused `netlist.ts`'s existing field-serialization logic wholesale, which flattens a compound or `many` field to a bare edge-name reference — correct for `netlist.ts` itself (which also emits a top-level `Netlist.edges` registry to resolve that name against) but wrong here: `SealedContract` carries no such registry, so any node with a nested or `many` field produced a payload an isolated agent structurally could not use. Caught by the final whole-branch review, which ran the function against a realistic compound/`many`-field edge and showed the dangling references directly rather than reasoning about it abstractly — exactly the kind of defect two prior clean task-level reviews couldn't see, because neither task's tests exercised a non-scalar field. Fixed by making `edgeShape` recurse for compound/`many` fields (embedding the referenced edge's full shape, at any depth) and delegating to `netlist.ts`'s serializer only for genuine scalar/literal leaves — the same no-cycle-guard recursion `hash.ts`'s `fingerprint` already does through nested edges, reused as precedent rather than re-litigated.

**`computeImplementationMetadata`, deliberately not a CRAP score.** A second pure function (`metadata.ts`), using the TypeScript compiler API (first library use in this codebase, not just `tsc`) to derive McCabe cyclomatic complexity and a line count from accepted implementation source. CRAP's own formula needs a coverage term this spike has no way to produce; computing a composite against an assumed-zero coverage would make every function score as if untested, which is worse than not scoring at all. Raw facts only, stored as `<node>/<hash>.meta.json` sibling to the implementation file, never read by the elaborator, `hash.ts`, or any acceptance logic — a side-channel, exactly per the instruction that prompted it: no automatic behavior, nothing for an agent to optimize against.

Full spec and plan: `docs/superpowers/specs/2026-09-10-sealed-contract-and-implementation-metadata.md`, `docs/superpowers/plans/2026-09-10-sealed-contract-and-implementation-metadata.md`.

## The generator mechanism, built — and a false-green bug that three clean task reviews couldn't see

**Where this came from.** `design.md` §6 named the generator mechanism ("edge definitions double as generator specs... property tests are close to free here") without ever specifying how it runs; this concretizes it, plus a minimal structural fuzz harness that runs generated cases through a node's real `Fn` — catching crashes and wrong-shaped returns without needing the still-undesigned `∀ p . ...` property-assertion DSL to exist first. Directly follow-on from the sealed-contract/metadata work above, which named the generator as a prerequisite piece for the eventual acceptance pipeline (`design.md` §10).

**`generate.ts`: a seeded, boundary-biased per-field/per-edge generator.** A small inline mulberry32 PRNG plus per-scalar-type generation (numeric min/max/min±1/zero, string min/maxLength, `enumValues` cycling, bool alternation, literal pinning), recursing into compound and `many` fields the same three-way discriminant `assertPayload`/`hash.ts`'s `fingerprint()` already use elsewhere. Two real defects in the plan's own sample code surfaced during task review (not implementer error): the `pattern`-throws-immediately guard was wired for `utf8` fields but never reached `datetime` fields, which share the same validation shape; and the numeric boundary set computed `min+1`/`max-1` unconditionally, generating out-of-range values for a tight `min===max` field. Both fixed same-task, same-review-round. A third instance of the identical *pattern* (a validation legal on `datetime` — this time `minLength`/`maxLength` — silently unenforced by generation) survived two more clean task reviews and was only caught by the final whole-branch review's empirical probing, below.

**`fuzz.ts`: structural output validation, then `fuzzNode`.** `resultMatchesOutput` dispatches on `OutputSpec.kind`, reusing `assertPayload` per branch; `many`-kind output needed its own per-entry/index check (caught and fixed in the spec itself, before implementation, when writing the plan surfaced that a node's `many` output is a bare `Record<string, PayloadOf<E>>` standing alone, not a `many` *field* nested inside another edge — `assertPayload`'s own many-field branch expects an enclosing key that doesn't exist at the output level). `isAcceptableResult` also accepts `Failed<In>`'s shape, since every node's real output signature is "one of `{successes, Failed}`" (`design.md` §3) — deliberately chosen to invoke nodes through the real `membrane()` boundary rather than calling `Fn` directly, reusing input validation/envelope/scope wiring at the cost of losing the ability to tell a genuine `Fn` crash apart from a deliberate `Failed<In>` return (both look identical by the time `membrane()` returns them) — a tradeoff decided explicitly during brainstorming, not discovered as a surprise.

**The false-green bug the final review caught.** `membrane()` returns `Failed<In>` for three distinct reasons, not two — `Fn` threw, `Fn` deliberately returned `Failed`, or **the input `assertPayload` rejected the generated payload before `Fn` ever ran**. `fuzzNode`'s acceptance check treated all three as equally legitimate. Combined with `generateDatetimeValue`'s unenforced length validations (above), this produced a demonstrated false green: a node with a garbage-returning `Fn`, fuzzed against a `datetime` field whose declared `maxLength` a 24-character ISO string can't satisfy, reported `passed === total, failures: []` — every generated case was rejected at the input boundary and silently counted as a pass, so the fuzz run tested nothing. Invisible to three individually-clean task reviews because it only exists where `generate.ts` and `fuzz.ts` meet — no single task's diff contains both halves of the interaction. Found by the final reviewer's own empirical probes against the real modules (not abstract reasoning), the same method that caught the compound-field bug in `exportContract` above — recorded here for the second time as the same lesson: cross-module interaction bugs are structurally the kind of thing a task-scoped review cannot see, no matter how careful, because the bug doesn't exist in either task's diff alone. Fixed by validating each generated case against its declared input *before* invoking `membrane()`, treating a rejection there as a generator defect (a loud thrown error, naming the case) rather than a node outcome folded into `passed`/`failures`; `generateDatetimeValue` now throws on an unsatisfiable length declaration, the same idiom already used for `pattern`.

**What stayed deliberately out of scope, this time confirmed rather than just asserted.** Nullable fields never generate `null` — a real spec gap (nullability was never named as a boundary case), not an implementation deviation; left for a future spec revision. Every field in a generated payload shares one `caseIndex`, so per-field boundary coverage is thorough but cross-field combinations are never explored (a bool and a 2-value enum on the same edge only ever see 2 of 4 combinations) — inherent to the per-`caseIndex` design this plan committed to, `generateManyValue`'s own `caseIndex + i` fix (below) being the visible precedent for the general remedy, scoped here to collections only by design, not yet generalized.

**`generateManyValue`'s own collision bug, same session.** The plan's sample code reused one `caseIndex` for every entry generated inside one collection — harmless for most index-field types (which still vary by content even at a shared boundary case) but a guaranteed total collapse for an `enumValues`-typed index field (`enumValues[caseIndex % length]` has no random fallback at all), silently shrinking every such collection to one entry regardless of how many were rolled. Fixed by diversifying the per-entry index (`caseIndex + i`) rather than reusing the bare outer index.

Full spec and plan: `docs/superpowers/specs/2026-09-10-generator-and-fuzz-harness.md`, `docs/superpowers/plans/2026-09-10-generator-and-fuzz-harness.md`.

## The acceptance gate, built — the piece the last two entries were both prerequisites for

**Where this came from.** `design.md` §10 names the accept-before-persist gate directly — an implementation "is written once it passes both its examples and generated property cases (§6), never overwritten" — and `getting-started.md`'s build-order step 3 has listed it as the authoring format's last unbuilt half since the step was first written. Both of this session's prior two entries named it as the reason they existed rather than as incidental follow-on work: the sealed-contract entry above built `exportContract` and `computeImplementationMetadata` as pieces of "the eventual acceptance pipeline (`design.md` §10)," and the generator entry built `fuzzNode` as a directly named prerequisite for the same thing. Neither piece did anything on its own — a contract nobody checks against and generated cases nobody runs through a gate are both inert. This is the entry where they add up to something: `accept.ts`'s `acceptImplementation` is the gate itself.

**The scope call on "generated property cases," stated plainly rather than left to be inferred from the code.** §10's acceptance bar reads as if it means real semantic correctness — but §6's actual property assertions (`∀ p . birthday(p).age == p.age + 1`) still have no representation in `types.ts`, no assertion language, no evaluator, and designing one is separate, substantially larger work that this gate deliberately doesn't wait on. What "generated property cases" means here instead is what was already built: examples checked by exact equality, and generated cases checked only *structurally*, via `fuzzNode` — does the result match the declared output shape, or `Failed<In>`? That's a real bar, not a token one (it catches crashes and wrong-shaped returns), but it is a weaker bar than §10's own wording suggests, chosen on purpose so the pipeline shipped now rather than blocking on a DSL. Worth being honest about in this file for the same reason the generator entry was honest about `∀ p . ...` not existing yet: the gap is a known, named scope cut, not a distinction anyone missed.

**Source text crosses the boundary, not a loaded `Fn`.** `acceptImplementation` takes a candidate as a source string, writes it to a fresh temp path, and dynamically imports it — never accepts an already-loaded function value. That's not incidental: source text is what an isolated agent's draft actually is (the sealed-contract entry above is the reason "isolated agent" is even a real actor in this design), and it's also already what `computeImplementationMetadata` consumes. Accepting an `Fn` instead would have meant some caller holding both a loaded function and its source and being trusted to keep them in agreement — exactly the kind of two-facts-that-can-drift shape this file has rejected before (`fixed`'s `method`/`fixType` tag, "Polymorphic-association pattern," above). One artifact, one boundary.

**`invoke.ts` fell out of writing the plan, rather than being planned up front.** Sketching `acceptImplementation`'s example-checking loop surfaced that it would duplicate, near-verbatim, the `single`/`allOf` branching `fuzzNode` already had to do to run a generated case through `membrane()` — same cast idiom, same "append to a fresh log under one correlation id" shape for `allOf`. Extracted to `invoke.ts`'s `invokeWithInput` before either caller's code was finalized, so there's exactly one place the `single`/`allOf` split and `membrane()`'s call-shape cast live, not two copies quietly able to drift. It also collapsed `fuzzNode`'s own two near-identical invocation loops (one per `InputSpec` kind) into the one loop `fuzz.ts` has now.

**Cleanup lives in a `finally`; what propagates out is deliberately narrow.** `fuzzNode` picked up two throw paths in its own final-review fix wave, above: a generated case that fails input validation before `Fn` ever runs, and a `many`-output declaration missing its `index`. Both are generator or declaration defects, not verdicts on the candidate being accepted — a candidate can't be blamed for a generator handing it garbage, or for a contract that was never fuzzable in the first place — so `acceptImplementation` lets both propagate out unmodified rather than catching them and folding them into a rejection. What it does guarantee, regardless of which of those paths is taken: the temp directory holding the draft is always removed, via a `finally` wrapping the whole write-run-check sequence, so a thrown generator defect doesn't leak a draft file next to (or worse, in place of) whatever the implementation tree already holds for that contract.

**The second consecutive branch where the same mechanism produced a false green.** The final whole-branch review's own empirical probing found that a node declaring no examples accepted a candidate that fails on every single input — `accepted: true`, fuzz report `{total:10, passed:10, failures:[]}` — because nothing about the check changes shape when `examples` is empty; `checkExamples` just iterates zero times and `fuzzNode` is left alone to carry the whole bar. That's the previous entry's bug again, wearing different clothes. There, a fuzz harness counted a *generator's* invalid output as a passing case, so a broken implementation reported a perfect green; here, with no examples declared, a candidate that fails on every input reports the same perfect green. Both times the root mechanism is identical: `Failed<In>` is indistinguishable from a legitimate outcome by the time it reaches a pass/fail check, so **any check whose pass predicate accepts `Failed<In>` is vacuous unless something else constrains the result** — the generator entry's assertion of well-formed input, or here, at least one declared example. And both times it was invisible to task-scoped review, because neither task's diff alone contains the interaction that produces the bug (there, `generate.ts` meeting `fuzz.ts`; here, a `NodeDecl` with an absent `examples` field meeting a fuzz harness that was never wrong on its own terms), and found only by the final whole-branch review running real probes against the built modules rather than reasoning about them abstractly.

Full spec and plan: `docs/superpowers/specs/2026-09-10-acceptance-pipeline.md`, `docs/superpowers/plans/2026-09-23-acceptance-pipeline.md`.

## Property assertions, built — the notation §6 has carried since the seed, finally given a mechanism

**Where this came from.** `design.md` §6 has named properties and shown their notation — `∀ p . birthday(p).age == p.age + 1` — since early in this history, without ever specifying how one would be authored, evaluated, or checked. Three consecutive specs deferred it in turn: the sealed-contract spec, the generator/fuzz-harness spec, and the acceptance-pipeline spec, whose own Motivation section said out loud that the gate it was about to ship checked something "narrower than §6 describes, deliberately... not §6's `∀ p . ...` property assertions, which still have no representation in `types.ts`." That admission is what this entry closes.

**Why a data expression rather than host code.** §10 keeps `Fn` out of a node's declaration on purpose — a `.node` file is a data format, and executable code can't be authored in YAML, fingerprinted structurally, or carried across the still-open "which host language elaborates" question. A property predicate is exactly the same kind of thing a `Fn` is — a function from an invocation to a boolean — so the same argument applies without modification: a TypeScript predicate would have been free to write and impossible to keep as data. `PropertyExpr` (`types.ts`) pays for the alternative instead: a small key-as-discriminant expression tree (`get`/`lit`/`eq`/`ne`/`lt`/`lte`/`gt`/`gte`/`add`/`sub`/`and`/`or`/`not`/`implies`) that a predicate would have gotten for free in any host language, evaluated by a matching interpreter (`property.ts`) rather than executed directly. The cost is real — a grammar and an evaluator instead of a closure — but it's the same cost `Fn`'s own exclusion already accepted, applied one layer down.

**`implies` kept as a primitive, not desugared.** `or(not(a), b)` is logically equivalent and would have kept the grammar one operator smaller. Rejected for two reasons that both matter more than grammar size: these are contracts a human authors and later reads, and `implies(input.age > 200, ...)` says what was meant in a way `or(not(...), ...)` doesn't; and the antecedent/consequent structure `implies` carries is exactly what a future check for antecedent-level vacuity (below) would need to inspect — desugaring it away now would mean re-deriving that structure later from a pattern-match on `or`/`not`.

**The vacuity guard, and the pattern behind it, for the third time.** Evaluating a property only against cases where `Fn` produced a real output — skipping `Failed<In>` — is the obviously correct design, and on its own it would have been the *third* consecutive shipped instance of the false green this file has now named twice: "any check whose pass predicate accepts `Failed<In>` is vacuous unless something else constrains the result" (above, "The acceptance gate, built"). The first instance let a generator's invalid output count as a passing fuzz case; the second let a candidate that failed on every declared example's input still get accepted because nothing constrained an empty `examples` list. A node whose properties are checked only against real outputs, with nothing else requiring a real output to exist, is the same shape a third time — every property would pass, vacuously, on a candidate that produces `Failed<In>` for every generated case. `accept.ts` closes it the same way the second instance was closed, generalized: a node declaring properties is rejected as `vacuous` unless at least one generated case produced a real output for those properties to actually run against. Worth stating plainly, because it's a real limit rather than a loose end: the guard is output-level only. A property like `implies(input.age > 200, ...)` can pass every check while its antecedent is never once true across every generated case — nothing currently guards against that, and closing it would need something closer to per-branch coverage than per-node output coverage. Left open, not solved here. The threshold is also exactly one: a candidate correct for its declared example and exactly one generated input, throwing on the other ninety-nine, is accepted with `realOutputs: 1` and a clean sweep of zero violations — the guard only distinguishes zero real outputs from at least one, nothing more. `FuzzReport.realOutputs` is exposed on the report specifically so a caller who wants a harder bar (some fraction of `count`, say) can gate on it without a change here; raising the threshold in `accept.ts` itself isn't done, deliberately — any fixed fraction would reject a legitimately selective node whose properties only apply to a narrow slice of generated inputs.

**What it cost to make acceptance mean more.** Properties are folded into the contract hash (`hash.ts`'s `fingerprintNode`), sorted by name so declaration order can't spuriously invalidate an accepted implementation and duplicate names throw rather than silently colliding — the same reasoning `closure` was already in the hash for: a strengthened invariant should force regeneration, not sit unchecked against an implementation accepted before it existed. Putting properties there rather than leaving them as the sealed contract's own concern is also what exposed that `examples` and `scope` are *not* in the hash — the first deliberately, per `fingerprintNode`'s own comment; the second not deliberately at all, just never noticed until this session read the function closely. Recorded as a single open question — which parts of a node declaration are contract, and which are commentary — rather than fixed here, since changing what's in the hash shifts every already-accepted hash and deserves its own decision.

Full spec and plan: `docs/superpowers/specs/2026-09-23-property-assertions.md`, `docs/superpowers/plans/2026-09-23-property-assertions.md`.

## Invocation records and replay, built — the pin resolved to an identity, not a field

**Where this came from.** `getting-started.md`'s build order has listed "replay against the implementation version an invocation was pinned to" as step 5's last unbuilt item since it was written, and §10 states the requirement directly: an invocation records which implementation version it actually ran under, immutable once written. The acceptance gate built earlier this session removed the actual blocker — `accept.ts` now produces the `<contract-hash>.ts` there would be to pin against — which is what made this session's work representable at all.

**The pin was an identity, not a hash.** This file's own "Composition parser deferred" entry left "the version-pin field's exact name/shape on the envelope" open. It resolves to the node's own name, not a new field: §10 guarantees one accepted implementation per contract state, never overwritten, so `(node name, contract hash)` already determines the implementation file uniquely. The envelope already carried the hash, under the name `schemaHash`; what it had never carried was the node's own name. Adding `Envelope.node` closes the open item directly, and closes it by recognizing what was already there rather than by inventing something new.

**Nothing was persisted, so there was nothing to pin.** `buildEnvelope` was built per invocation, handed to `Fn` if it declared `env`, and then discarded — `Log.append` never took an envelope at all. §10's sentence had nowhere to be recorded: a pin field on a transient object pins nothing, because the object itself doesn't survive the invocation that built it. That's why this became a `Trace` — a durable artifact recording one entry per invocation — rather than a field grafted onto something that was already being thrown away.

**A conflation settled.** §1 lists the envelope as carrying a "schema hash," and §5 defines that as the hash of the *edge* an instance was written under — the thing replay-on-mismatch migrates or refuses against. But `membrane.ts` had been setting that same field to the *node contract's* hash all along, a different value under the same name. Both were wanted, just at different grains: `contractHash` is fixed for the whole invocation, while an edge's `schemaHash` is only knowable once a specific output edge is chosen, which for an `allOf`-output node can be three different values from one invocation. Rather than picking a winner, each got its own name and its own home — `contractHash` stays on the invocation-level `Envelope`; `schemaHash` moved down to `InstanceEnvelope`, attached per logged instance where it's actually well-defined.

**The membrane's rule held under pressure.** The obvious fix for getting the envelope somewhere durable was to pass a recording sink — a `Trace` or `Log` — into `membrane()` and let it record as it went. Refused, on the strength of a sentence `membrane.ts` already stated about itself: `membrane(nodeDef)` "takes nothing but the declaration itself... never separately configured." A recording sink is exactly the separate configuration that rule forbids, so the envelope comes **out** of `membrane()`'s return instead of a sink going **in** — `{ result, envelope }`, `envelope` present iff `Fn` actually ran. Worth recording plainly: this is a case where a principle the codebase had stated about itself actually changed a design, rather than being quietly stepped around once it became inconvenient.

**Replay refuses rather than pretends.** `replayInvocation` resolves the pinned implementation by the *recorded* `contractHash`, not by re-hashing the caller's declaration — but it does re-hash the declaration once, to compare. Declarations aren't versioned anywhere, only implementations are, so if the supplied declaration no longer hashes to the recorded value, there is no faithful way to represent what "replay" would even mean: not merely unimplemented, but not currently representable. §5's own doctrine — replay on mismatch migrates through a declared rule or refuses — already said what to do when there's no migration story, so `replayInvocation` refuses, naming both hashes.

**That same guard is also why `resolveImplementationAt` proves less inside replay than it looks like it should.** `replayInvocation` checks `hashNode(node).hash === entry.envelope.contractHash` *before* it ever resolves an implementation. Past that check, the recorded hash and a freshly-derived one are provably the same value — so within `replayInvocation`, calling `resolveImplementationAt` with the recorded hash is indistinguishable from calling `resolveImplementation` and letting it derive one. `replay.test.ts` can't be the thing proving the pin does its job, then, and it isn't: the real proof — that the *old* pinned implementation runs even after a node has since gained a newer accepted one — lives in `implementation.test.ts`'s mutated-declaration case, which is the only place the recorded hash and a re-derived one are actually forced apart. `resolveImplementationAt` still earns its keep: for a caller that resolves by hash directly without going through replay's guard, and for the day a migration story relaxes that guard and the two hashes are allowed to legitimately disagree. It just isn't earning it inside `replayInvocation` today.

Full spec and plan: `docs/superpowers/specs/2026-09-23-invocation-records-and-replay.md`, `docs/superpowers/plans/2026-09-23-invocation-records-and-replay.md`.

## `scope` folded into the contract hash — a deferral reversed once its reason was checked

**The deferral was vacuous, and only checking it showed that.** Adding property assertions to `fingerprintNode` surfaced that `scope` wasn't hashed either, and open-questions.md parked it with a reason that sounded solid: "changing what's in the hash shifts every existing accepted hash and deserves its own decision, not a drive-by fix." Checked directly, that premise was false — no `implementations/` tree exists in this repo and no `<contract-hash>.ts` file lives anywhere outside a test's temp directory. There were no accepted hashes to shift. A cost that hadn't been paid yet was being treated as sunk, and the fix that looked expensive was free. The lesson generalizes past this field: a deferral's stated reason is a claim about the world, and it goes stale silently — nothing fails when it stops being true.

**Behavioural versus verification is the line that actually separates the two omissions.** `scope` and `examples` were parked as one question and they aren't one question. `scope` feeds `narrowIdentity`, so it determines what data `Fn` receives at runtime: change `read:Identity:sub` to `read:Identity:iss` and, unhashed, the accepted implementation resolves unchanged and reads `undefined` — silently, with `acceptImplementation` declining to re-check because the hash says nothing changed. `examples` can't corrupt a result that way; leaving it unhashed weakens an acceptance gate. Corrupting a result and weakening a gate are different severities, and they were being deferred at the same one. `examples` stays out; the entry now argues for it on its own terms rather than by association.

**Replay is what raised the stake.** The hole existed the whole time as acceptance hygiene, but `replayInvocation`'s drift refusal is only as good as `fingerprintNode`'s coverage — a declaration whose `scope` had widened since the recorded invocation passed the drift check untouched, resolved the very same pinned implementation, and replayed "successfully" with the newly-declared field simply absent from the replayed `identity`. The replay spec had a sentence claiming the guard caught "a different `scope`"; it was struck during that branch precisely because it wasn't true. It is restored now, with a note saying why it was ever struck — a spec that quietly drops a claim it can't honour leaves nothing behind to notice.

**Sorted and de-duplicated, unlike properties.** Scope sorts for the same reason properties do: declaration order carries no meaning, so reordering a list mustn't invalidate a good implementation. But a duplicate property name *throws*, and a duplicate scope doesn't — it de-duplicates. A repeated property name makes the sort ambiguous and makes a violation report (which identifies a property by name) unreadable; a repeated `read:Identity:sub` is redundant but perfectly unambiguous, because narrowing to the same field twice is that one narrowing. Same sort, opposite duplicate handling, and the difference is whether there's anything for a declarer to disambiguate.

**Arity and `scope` are orthogonal on purpose — confirmed against my own earlier code.** Fingerprinting `scope` surfaced a nearby question that looked like a loose end: `callFn` decides whether `Fn` receives an `env` on `fn.length >= 2`, not on whether a `scope` was declared, so a node with no `scope` can still be handed an envelope. That's intended. `scope` decides what's *inside* `envelope.identity`; arity decides whether the implementation asked for the envelope at all — and identity is one of its eight fields, so a node wanting `correlationId` or `step` while declaring no scope is an ordinary case, not a contradiction. The same middleware of mine this file already cites resolved it identically: its handler signature always carried the scoped-environment parameter, and the declared list narrowed that parameter's *type* (`Record<Declared[number], string>`) rather than gating its presence — declare nothing and you still got the parameter, holding an empty object. Worth recording because an earlier open-questions entry asserted the opposite ("`scope` determines whether a node's `Fn` is called with a second `env` argument") and reasoned from it; that claim was wrong and is gone.

## The vacuity guard widened — the false-green pattern's third instance was inside the guard built for its second

**The guard was right about the mechanism and wrong about its own scope.** `accept.ts` rejected a candidate whose generated cases never produced a real output, but only `(nodeDecl.properties ?? []).length > 0 && fuzzReport.realOutputs === 0` — a node declaring no properties skipped the check entirely. The spec that introduced it states the general rule correctly — *"a check whose pass predicate accepts `Failed<In>` is vacuous unless something else constrains the result"* — then conditions the guard on properties anyway, and so became the third instance of the thing it names. Worth recording precisely because the reasoning was one sentence away from complete.

**What the scoping missed: properties weren't what made a run vacuous, they were what made it visible.** With properties declared, zero real outputs means every property passed vacuously and that's legible as an absence. With none declared, the emptiness is exactly as total and nothing reports it. `fuzz.ts`'s `isAcceptableResult` is `resultMatchesOutput(output, result) || looksLikeFailed(result)` — a failure is a legitimate node outcome, by design — so a candidate that fails *every* generated case satisfies the structural bar perfectly, drawing zero failures, having been examined by nothing.

**The candidate that got through is the one the acceptance gate exists to stop.** An implementation returning the right answer for its declared example and throwing on every other input: examples pass exactly, so `exampleFailures` is empty; all twenty generated cases throw, so all twenty become `Failed<In>` and the structural bar reports clean; no properties, so no guard. Verified by probe before changing anything — `accepted: true`, written to disk. §10's whole premise is that acceptance means *checked*, and here it meant "special-cased its examples convincingly."

**The rule is now `realOutputs === 0`, unconditionally**, with a trade-off taken knowingly: a legitimate node whose valid domain is too narrow for the generator to ever hit is now refused rather than accepted unchecked. Refusing is the honest outcome — "the generated cases never exercised this contract" is a real problem, and the rejection says so — and it costs nothing today for the same reason fingerprinting `scope` did: no accepted implementations exist on disk yet.

**The recurring lesson, stated generally since three instances is a pattern rather than an accident.** Every one of these has the same shape: a pass predicate that admits `Failed<In>`, and no independent constraint forcing a real result to exist. The check isn't wrong — a failure genuinely is a legitimate outcome — it's that *accepting failures* and *verifying behaviour* cannot be the same predicate. Any future gate that treats `Failed<In>` as passing needs a companion assertion that something, somewhere, succeeded. Scoping such a companion to a subset of nodes is how this one got missed.

## Iteration: it's a Petri net, and the loop was never the missing piece

**`while` needs ambient state; recursion doesn't — and weir already has the recursive form.** The framing that unlocked this, Jordan's: a `while` loop needs a mutable cell the condition reads and the body writes, which is exactly what the readme's opening line bans. Tail recursion gets the same iteration with none of it, because each call receives a *new value* rather than mutating an old one — `const tick = (t) => t + 1; const whenThree = (t) => t > 2 ? true : whenThree(tick(t))`. A node emitting an edge instance that transitively feeds itself *is* that: fresh forward execution, which is what this file already said recurrence should be. So there is no loop construct to design, and "weir has no loop construct, and needed none" was right about the construct while being wrong about the capability.

**The base case is `oneOf`, already built.** `whenThree` terminates by returning a different *type* in the terminating branch. In weir that's `output: { oneOf: [Assessment, InvestigationComplete] }` — emit `Assessment` and it routes back round, emit `InvestigationComplete` and nothing consumes it, so the graph goes quiet. Termination is a branch nothing routes back, not a primitive.

**What actually blocks iteration is that the log clobbers — the banned mutable cell, hiding in the runtime.** `InMemoryLog` is `Map<(edgeName, correlationId) → LoggedInstance>` and `append` overwrites, so there is exactly one instance per edge type per correlation, with no history and no per-instance identity. `design.md` §5 specifies this ("reading each named edge type's **latest instance**"), so the store is faithful to the design rather than a shortcut. But under latest-wins, `tick` cannot produce a successor: the new `Person` overwrites the old one, leaving one mutable cell instead of `t` and `t+1`. The ambient state the design forbids in node bodies was sitting in the execution machinery the whole time. This also means the candidate fix recorded in `open-questions.md` — re-key firing by consumed input edge-instance ids — presumes instances that are individually identified and retained, and today they are neither.

**The execution model is a Petri net, and naming it buys the theory rather than re-deriving it.** Places hold tokens; transitions fire when their input places hold tokens, consuming them and producing new tokens downstream. That is precisely the rule settled here — a node fires once per unconsumed instance of its input edge, oldest first, with consumption tracked per node rather than exclusively (two nodes downstream of one edge must both fire on it). Petri nets come with worked-out answers to the questions this design keeps circling: boundedness (can the pending set grow without limit?), liveness (can every node still eventually fire?), and reachability. Worth reaching for that literature before inventing answers.

**Two words, not one: a *run* is not a *token*.** Asked whether "the glowing dot" needed a name, and the answer is that it names a different thing than "run" does. A **token** is one edge instance in flight. A **run** is one whole traversal, which `correlationId` already names. Fan-out is exactly where they come apart: one token enters a fan-out node and three come out, still one run. So "keep the run together" means share a correlation, while "which token came from which" means lineage — and lineage is `causationId`, which is currently a hardcoded `null` placeholder. The vocabulary gap was real: weir had a word for the run and none for the token or the lineage.

**The join key is lineage, not a declaration.** For an `allOf` node with several unconsumed instances per input edge, the combination that fires is the one whose instances share an ancestor — recoverable from the logs rather than declared as a field on the node, which keeps the node contract free of join plumbing. Settled as zip-plus-lineage rather than newest-of-each (drops data at the join) or cartesian product (explodes). Gated on `causationId` becoming real.

**"Enroll in workflow" is the same move one level up — the zoom.** Prior art from ActiveCampaign, which had no "go to" step for pointing back to the top but did let an automation enroll a contact into a workflow. Since a topology and a node are the same from the outside ("Subgraphs are nodes", above), re-enrollment is a node whose body is the graph containing it: recursion by composition, with the wiring staying a DAG. That's `whenThree` calling `whenThree`, at the graph grain. HubSpot's "go to" is the other design — a real backward jump — and that one does need the ambient program counter weir is avoiding. Composite nodes have no representation yet (`types.ts`: "a composite node's body is a subgraph, which has no representation yet"), so this is the furthest-out piece.

**Bounding iteration belongs to the host, not the language.** weir iterates to quiescence with no built-in limit — terminating is the graph author's job via the base-case branch, the same contract a functional runtime offers. The execution environment enforces a step or time budget, because that is where multi-tenancy and billing live: Kleisli must, a local runtime need not. Keeps the language free of a magic number, and matches the three-layer split (weir = substrate, Kleisli = control plane). The sharp edge accepted knowingly: node bodies are agent-authored, so an agent that always takes the continue-branch writes a non-terminating graph, and the host budget is the only thing that stops it.

**Decomposed into four specs in dependency order**, since this is four subsystems rather than one: (1) the log becomes a log — instance retention, identity, per-node consumption, fire-per-unconsumed readiness; (2) causation is real; (3) `allOf` joins by lineage; (4) composite nodes. Each is independently testable, and (1) alone makes single-input recursion run.

## Three axes and a clock — the coordinate model, and why a topology is an `allOf` node from outside

**Four primitives, one of them a shadow.** Edge and node are the two real primitives. A topology is an arrangement of nodes, distinguished from a bare arrangement by being *rooted*. Topology-as-node is the fourth, and it isn't a fifth primitive at all — it's a topology viewed from outside its own membrane. Jordan's framing, and the reason the model needs a dimension that only appears when you change where you're standing.

**x, y, z, and a clock — four numbers that were being conflated as one or two.**

- **x — which sibling of a fan-out.** Not an anonymous index: it's the collection key, since `many` is keyed rather than an array (this file, "`many` is a collection, keyed by index, not an array"). Being a key rather than a position means a fan-out of a fan-out addresses as a *path* of keys, needing no second index, and that order stays non-load-bearing on this axis for the same reason arrival order doesn't matter to `allOf`.
- **y — causal position within one topology traversal.** `envelope.step`. Iteration lives entirely on this axis, which is the check that the recursion framing holds: a node feeding itself extends the chain to step 5, 6, 7 rather than introducing anything new. Had iteration needed an axis of its own, "a cycle is not a loop" would have been wrong.
- **z — how many topologies deep.** Only exists once topology-as-node does. It fixes a real ambiguity: "causal hops from an origin" stops being well-defined the moment a topology can be invoked inside another, because there are then two origins to count from. Splitting nesting off makes each traversal's `step` local and meaningful again.
- **The clock — `seq`, when a token was written.** Deliberately *not* a fourth (time) axis, though the pull to read it that way is strong. Two reasons. First, x, y and z are properties of the *program* and `seq` is a property of one *execution* of it: replay the same topology on the same inputs and every token lands at the same fan key, causal step and depth, while `seq` depends on scheduling — it is reproducible only because the runtime pins a deterministic scan, which is a policy promise rather than a semantic one. So two tokens sharing x/y/z across two runs occupy the same position in the computation, while two tokens sharing a `seq` across two runs have nothing in common, and treating `seq` as a coordinate is an invitation to compare it across runs. Second, a token does not *move* along `seq` the way a thing moves through time — it is stamped once at append and never changes. **Reserve "tick" for the round**, not for this: a round is one pass of the fixpoint scan, a global beat shared by everything firing in it and the unit a host budget counts against, whereas many `seq` values occur inside one round (several firings per round, several tokens per `allOf` firing). x, y and z are positions in the causal structure; `seq` is the log's own write order. They're orthogonal, which is why `seq` is right for "oldest unconsumed first" and wrong for lineage, and why two tokens can agree on all three coordinates across separate iterations while never sharing a `seq`. What it is, formally, is a logical clock in Lamport's sense — a monotonic counter whose total order is consistent with causality. Kept named `seq` rather than anything cuter because that's the conventional name in an append-only log (Kafka's offset, EventStore's position) and a reader guesses right immediately.

**One origin *event*, several origin *nodes* — the root is the trigger, not a node.** `wiring.origins` is a list and `runtime.ts` seeds its queue from all of them, so "a topology has one origin node" would be wrong on its face. `design.md` §5 puts the singularity one level up: *"there is exactly one call to the graph's outer membrane per external event, and every origin-shaped edge it declares needing resolves from that single payload at once."* That still supplies the single root z=0 requires.

**From outside its membrane, a topology *is* an `allOf` node — by definition, not by analogy.** `allOf` means every declared edge must be present together before firing; §5's "resolves from that single payload **at once**" is the same requirement stated from the inside. So the several origin nodes are the several edges of one `allOf`, and the one event is one simultaneous satisfaction of it. The apparent tension between "one origin" and a plural `origins` list dissolves entirely.

**Which makes a composite node's contract derived rather than declared.** Input is `allOf` over the topology's origin edges; output is what its terminal nodes emit — `allOf` for several terminals, `oneOf` where it can finish different ways, both existing output kinds. Nobody writes a composite's interface down, so a composite **cannot lie** about it: the one place a subgraph could drift from its advertised contract is designed out rather than validated. It also buys encapsulation for free — the derived contract names only origin and terminal edges, so rearranging a subgraph's middle changes no consumer-visible hash, and the contract moves only when the actual boundary moves.

**A consequence for build order, since it isn't visible from the dependency list alone:** every topology-as-node entry is `allOf`-shaped, so piece (4) (composite nodes) depends on piece (3) (`allOf` joining by lineage), not only on piece (1). Piece (3) is not merely "John's fan-in gets exact" — without it, (4) is incorrect at its entry point.
